# 謄本取得: 地番を人が確認して入れるポップアップ 設計

> **作成日**: 2026-08-12 / **性質**: 設計のみ(この PR にコード変更は無い)

---

## 0. 背景と発注者の決定

**謄本は「地番」でしか引けない**。住所の末尾の数字は**住居表示**であって地番とは別物(たまたま一致することはある)。地番を知る唯一の手段は、法務省の**地番検索サービス**の地図で**該当の筆をクリックして表示される地番を読む**こと。アプリはこのサービスと一切連携していない。

| 論点 | 決定 |
|---|---|
| 地番の確認 | **人が地図で筆を見て決める**(自動で筆をクリックして読む案は採らない。隣の筆を読むと**誤った土地の謄本を買う**) |
| 見せ方 | **ポップアップ**を出し、地図を開くボタンと地番の入力欄を見せる(発注者「これで進めよう」) |
| 出すタイミング | ⚠**自動操作を始める前**(§2 の理由により、途中で止める案は採れない) |

## 1. 現状(2026-08-12 実測)

- 「所在で謄本を検索」は1コンポーネント内の state 機械。API は**検索**(`POST .../registry/search`)と**取得**(`POST .../registry/auto-fetch`)の2本だけ。
- **地番が空でも `searchable: true`** で実サイトへログインし、**地番欄も範囲欄も未入力のまま**検索する。結果は**その地番区域の地番を最大20ページ読み切って全件**一覧表示(件数の上限も絞り込みも無い)。
- 検索 route が body から読むのは `confirmed` と `liveRef` のみ。**地番を渡す口は無い**(サーバーは必ず DB の `property.lotNumber` から組む)。
- **Playwright セッションは検索 POST の中だけで生存**する(排他 → 起動 → login → 検索 → finally で close)。
- **候補キャッシュの TTL は10分**。取得は**検索時の物件指紋**(所在/地番/家屋番号/不動産番号)一致を前提にする。
- 地番の保存口は **`PATCH /api/properties/[id]` の一本**。`property:write` + `version`(楽観ロック)必須。変更は ChangeLog と AuditLog に残る。`lotNumber` に**バリデーションは実質ゼロ**(任意文字列)。
- **座標(`gpsLat`/`gpsLng`)が入るのは現地調査ピンからの物件化だけ**。登記PDF取込・受付CSV取込で作られた物件は**座標なし**。⚠**本番実測(2026-08-10): 668件中 座標ありは1件**。
- **住所→座標の逆引きは存在しない**(座標→住所の一方向のみ)。
- 外部リンクは素の `<a target="_blank" rel="noopener noreferrer">`(`window.open` はポップアップブロックに掛かる既知の落とし穴)。

## 2. なぜ「自動操作の途中で止める」案を採らないか

当初の案は「検索を始めてから、地番が要る段でポップアップを出して待つ」だった。**採れない**:

1. **セッションを人の待ち時間ぶん占有する**。登記情報提供サービスは**1IDにつき同時1セッション**で、アプリは「1リクエスト = login → 操作 → close」で成立している。人が地図を見る数分間セッションを保持すると、**他の物件の検索・取得が順番待ちになり、課金安全の前提(先発を強制ログアウトさせない)も揺らぐ**。
2. **候補キャッシュの TTL が10分**。地図で筆を探す作業は10分を超え得る。「検索して候補を出してから地番を調べさせる」順序にすると、**取得しようとした時にキャッシュが消えていて 409** が多発する。
3. **地番を保存すると物件の指紋が変わる**。検索の**後**に保存すると、取得時に指紋不一致で **409**。

→ **順序は「ポップアップ → 地番を保存 → 検索 → 候補を選ぶ → 取得」で固定する**。自動操作が始まる前にポップアップは閉じ切っている。

## 3. 画面

### 3.1 いつ出すか

「所在で謄本を検索」を押したとき、**物件の地番(土地)/家屋番号(建物)が空**なら、確認パネルの**前に**ポップアップを出す。

⚠ **判定は既存の preflight API に足す**(単発・所在検索・一括の**3入口が共有**している)。単発ボタンにだけ足すと、**一括と挙動が割れる**。

⚠ **不動産番号を持つ物件では出さない**。番号がある物件は所在検索の経路に入らない(`searchable: false`)。

### 3.2 中身

```
┌─ 地番が必要です ────────────────────────────┐
│                                                        │
│ 謄本は「地番」でしか取れません。住所の番号(住居表示)と  │
│ は別のものです。地図で確認してください。                │
│                                                        │
│ この物件の住所                                          │
│   神奈川県横浜市南区井土ケ谷中町69-2      [コピー]      │
│                                                        │
│   [ 地番検索サービスを開く(無料・別タブ) ]              │
│   ↑ 開いたら住所で検索 → 地図を拡大 → **該当の筆をクリック** │
│      → 出てきた地番をここへ入れてください                │
│                                                        │
│ 地番   [                    ]                          │
│                                                        │
│           [ キャンセル ]  [ 保存して検索へ ]            │
└────────────────────────────────────────┘
```

- **住所をコピーできるようにする**。⚠ 座標が無い物件が大半(本番は668件中667件が座標なし)なので、**地図は住所で検索してもらう**のが現実。
- **座標があれば** `#18/緯度/経度` で**その位置を開く**。無ければ**サービスを開くだけ**。⚠ 既存の「座標が無ければリンクを出さない」作法とは**変える**(出さないと大半の物件で使えない)。
- ⚠ **文言に「該当の筆をクリックして」を必ず入れる**。座標は**建物の位置**であって**筆の代表点ではない**。地図の中心の地番をそのまま写すと**誤った土地を買う**。
- ⚠ **`rel="noopener noreferrer"`**。`noreferrer` が無いと**物件詳細の URL(UUID)が外部へ漏れる**(このアプリは Referrer-Policy を設定していない)。
- ⚠ **費用の書き分け**: 「**この画面の操作では課金されません**(地番検索サービスは無料)。**課金は次の取得のときです**」。既存の候補一覧は「無料/有料/課金/費用」の語を出さないテストで固定されているので、**ポップアップ側にだけ書く**。

### 3.3 建物のとき ⚠**このポップアップで家屋番号は尋ねない**

@codex #370 P1。当初は「ラベルだけ差し替えて家屋番号を尋ねる」としたが、**誤り**:

> **地番検索サービスの地図が返すのは「地番」であって「家屋番号」ではない。**

ラベルだけ変えると、利用者は案内どおり**筆をクリックして地番を読み**、それを**家屋番号として保存**してしまう。そのあと:

- provider は**家屋番号が空でなければ「建物」として検索**するので、**地番を家屋番号として建物検索**することになる
- 一括取得は**候補が1件なら自動で購入**するため、**誤った登記を買って添付・取込まで進む**

→ **建物で家屋番号が空の物件では、入力欄を出さない**。ポップアップは**案内だけ**にする:

```
┌─ 家屋番号が必要です ──────────────────────┐
│ 建物の謄本には「家屋番号」が要ります。               │
│ ⚠ 家屋番号は**地番検索サービスの地図では分かりません**  │
│   (地図が示すのは土地の地番です)。                   │
│                                                    │
│ 権利証・固定資産税の通知・過去の謄本などでご確認のうえ、 │
│ 物件の「家屋番号」欄に入力してから実行してください。    │
│                                    [ 閉じる ]      │
└──────────────────────────────────┘
```

⚠ **保存させない**(誤った値を入れる口を作らない)。

**将来の選択肢(この設計の範囲外)**: 登記情報提供サービスの請求方法には**「土地からの建物検索」**がある(実サイトのラジオで確認済み)。家屋番号が分からない建物はこの経路が本筋なので、**別エピックとして記録**する。

⚠ **既存の穴は別に残る**: 現状**家屋番号が空の建物は「土地」として検索・請求される**(判定が家屋番号の有無だけで、物件の種別を見ていない)。**この設計では直さない**が、**上の案内を出すことで人が誤って進むのは減る**。直すなら別 PR(種別と家屋番号の食い違いを警告する)。

## 4. 入力された地番の扱い

### 4.1 保存してから検索する

**`PATCH /api/properties/[id]` で `lotNumber`(または `buildingNumber`)を保存 → その後に検索を開始**。

- **保存の前に検索してはいけない**(指紋が変わって取得が 409)。
- 保存には **`property:write` と現在の `version`** が要る。ポップアップは**物件の version を受け取り、409(他の人が先に更新)を画面で扱う**。
- 次回以降も使えるようになり、**変更履歴に残る**(誰がいつ入れたか)。

⚠ **権限が2種類に割れる**: 謄本取得は `registry:auto_fetch`、地番の保存は `property:write`。**取得はできるが保存はできない**利用者がいる。その場合は**ポップアップを出さず**、「地番を入力してから実行してください(地番の編集権限が必要です)」と案内する。**「保存せず1回だけ使う」口は作らない**(§4.2)。

### 4.2 「その場限りの地番」を渡す口は作らない

検索 route に地番を渡せるようにする案は**採らない**:

- サーバーが DB から読む前提が崩れ、**指紋・候補キャッシュ・二重課金の鍵**がすべて「渡された値」と「保存された値」の二重管理になる。
- 同じ物件で**違う地番を入れた2つのタブ**が同じ指紋を持ち、後勝ちで候補が入れ替わる。

### 4.3 入力の検査

⚠ **「正規化して数字が残るか」だけの検査では足りない**(@codex #370 P1)。`normalizeChibanForDialog` は**数字とハイフン以外をすべて削除する**ので、`abc1x2` も `1号2` も**同じ `12`** になる。`12` は**別の筆**を指し得るうえ、**一括取得は候補が1件なら自動で買う**ので、**誤った登記を買って添付・取込まで進む**。

→ **受理する書式を明示して、それ以外は弾く**(黙って落とさない):

| 受理する | 例 |
|---|---|
| 数字 | `69` |
| 数字とハイフン | `69-2` / `1-1-1` |
| 「番」「の」を区切りに使ったもの | `69番2` / `69の2` |
| 前後の空白・全角数字 | `６９－２`(正規化して受理) |

**上記以外の文字が1つでも混じっていたら拒否**し、「地図に表示された地番をそのまま入れてください」と案内する。

⚠ **拒否のテストを必ず書く**: `abc1x2` / `1x2` / `69-2 の隣` のように**数字と未対応の文字が同居する**ケース(通ってしまうと別の筆を買う)。
- ⚠ **新しい正規化を作らない**。既存は `normalizeChibanForDialog`(自動操作用)と `normalizeLotNumber`(二重課金の鍵用)の**2つに分かれていて「号」の扱いが食い違う**。3つ目を作らず、**入力の検査は `normalizeChibanForDialog` に寄せる**。
- ⚠ **住所から地番を自動生成・自動補完しない**。所在欄に地番まで入れて実機で失敗した前例がある。ポップアップは「**人が地図で読んだ値を入れる**」入口に徹する。

## 5. 壊してはいけない安全装置

| 装置 | 壊れ方 | 守り方 |
|---|---|---|
| **課金スイッチ(501)と30日の二重課金台帳** | ⚠**`locationCandidate` を渡し かつ 不動産番号が空のときだけ発動**する。入力した地番を別の引数(番号相当)で流すと**両方すり抜ける** | 入力した地番は**必ず「検索 → 候補 → `locationCandidate`」の既存経路に合流**させる。購入判定の分岐を必ず通す |
| **二重課金の鍵** | 鍵は**サイトが返した候補の地番**から作る。人が入力した値を直接鍵にすると、サイトの正規表記と食い違って**同じ登記を2回買える** | 鍵の材料は**サイト由来の候補値に固定**(現行のまま。変えない) |
| **取得前の警告(preflight)** | ⚠ `confirmObtain` の state でだけ発火し、確認完了まで実行ボタンを disabled にしている。**新しい state を挟むと警告なしで課金に進む** | 新 state でも preflight を **active にし、実行ボタンに `disabled={preflight.pending}` を付け直す** |
| **一括取得の歯止め** | 一括は「候補が複数なら自動で買わない(`ambiguous_candidate` で skip)」で誤課金を防いでいる | 地番入力で**1件に絞れたときだけ**進め、絞れなければ**従来どおり skip**。歯止めを緩めない |
| **中止の規則** | 「課金前だけ止める・受け付けた中止は必ず効く」 | 有料取得側に中止の節目を**新設しない**。`endCancelable` の後にもう一度見る対を壊さない |
| **地番は秘匿情報** | ログ・監査・実況パネル・エラー文言に出さない運用 | ポップアップの入力値を**これらに出さない**(件数と分類コードのみ) |

## 6. 文言の整合

`location_rejected` の固定文言は「住所に地番まで含まれている/丁目まで整えて地番は地番欄へ」と案内している。**ポップアップができると利用者の対処手順が変わる**ので、文言を導線と矛盾させない(422 = 入力の問題、という分類自体は維持)。

## 7. テスト方針

- **出す/出さないの判定**: 地番あり→出さない/地番なし→出す/不動産番号あり→出さない/建物で家屋番号なし→家屋番号で出す。
- **順序**: 保存 → 検索 の順であること(逆順だと取得が 409 になる回帰)。
- **権限**: `registry:auto_fetch` はあるが `property:write` が無い利用者 → ポップアップを出さず案内。
- **preflight**: 新しい state でも警告が出て、確認が終わるまで実行できないこと。
- **入力の検査**: 数字が残らない値を弾くこと。
- **外部リンク**: `target="_blank"` と **`rel="noopener noreferrer"`** がソースにあること(走査型)。
- **秘匿**: 入力した地番がログ・監査・実況に出ないこと(走査型)。
- **一括**: 候補が複数なら従来どおり skip されること。

## 8. レビューで特に見てほしい論点

1. §2 の「途中で止めない」判断(セッション占有・TTL・指紋の3点)は妥当か。
2. §4.1 の「保存してから検索」に伴う `version` 409 の扱いと、権限が割れる利用者への案内。
3. §5 の課金安全(とくに **`locationCandidate` 経路に合流させる**)が、実装でどう担保されるか。
4. 座標が無い物件が大半である前提で、地図を「開くだけ」にする縮退が実務に耐えるか。
5. 家屋番号が空の建物を「土地」として扱っている既存挙動に、この導線で手を入れるべきか(別 PR にすべきか)。
