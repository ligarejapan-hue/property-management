# 謄本取得: 地番を人が確認して入れるポップアップ 設計

> **作成日**: 2026-08-12 / **性質**: 設計のみ(この PR にコード変更は無い)

---

## 0. 背景と発注者の決定

**謄本は「地番」でしか引けない**。住所の末尾の数字は**住居表示**であって地番とは別物(たまたま一致することはある)。地番を知る唯一の手段は、法務省の**地番検索サービス**の地図で**該当の筆をクリックして表示される地番を読む**こと。アプリはこのサービスと一切連携していない。

| 論点 | 決定 |
|---|---|
| 地番の確認 | **人が地図で筆を見て決める**(自動で筆をクリックして読む案は採らない。隣の筆を読むと**誤った土地の謄本を買う**) |
| 見せ方 | **ポップアップ**を出し、地図を開くボタンと地番の入力欄を見せる(発注者「これで進めよう」) |
| 出すタイミング | ⚠**自動操作を始める前**(§2 の理由により、途中で止める案は採れない) |

## 1. 現状(2026-08-12 実測)

- 「所在で謄本を検索」は1コンポーネント内の state 機械。API は**検索**(`POST .../registry/search`)と**取得**(`POST .../registry/auto-fetch`)の2本だけ。
- **地番が空でも `searchable: true`** で実サイトへログインし、**地番欄も範囲欄も未入力のまま**検索する。結果は**その地番区域の地番を最大20ページ読み切って全件**一覧表示(件数の上限も絞り込みも無い)。
- 検索 route が body から読むのは `confirmed` と `liveRef` のみ。**地番を渡す口は無い**(サーバーは必ず DB の `property.lotNumber` から組む)。
- **Playwright セッションは検索 POST の中だけで生存**する(排他 → 起動 → login → 検索 → finally で close)。
- **候補キャッシュの TTL は10分**。取得は**検索時の物件指紋**(所在/地番/家屋番号/不動産番号)一致を前提にする。
- 地番の保存口は **`PATCH /api/properties/[id]` の一本**。`property:write` + `version`(楽観ロック)必須。変更は ChangeLog と AuditLog に残る。`lotNumber` に**バリデーションは実質ゼロ**(任意文字列)。
- **座標(`gpsLat`/`gpsLng`)が入るのは現地調査ピンからの物件化だけ**。登記PDF取込・受付CSV取込で作られた物件は**座標なし**。⚠**本番実測(2026-08-10): 668件中 座標ありは1件**。
- **住所→座標の逆引きは存在しない**(座標→住所の一方向のみ)。
- 外部リンクは素の `<a target="_blank" rel="noopener noreferrer">`(`window.open` はポップアップブロックに掛かる既知の落とし穴)。

## 2. なぜ「自動操作の途中で止める」案を採らないか

当初の案は「検索を始めてから、地番が要る段でポップアップを出して待つ」だった。**採れない**:

1. **セッションを人の待ち時間ぶん占有する**。登記情報提供サービスは**1IDにつき同時1セッション**で、アプリは「1リクエスト = login → 操作 → close」で成立している。人が地図を見る数分間セッションを保持すると、**他の物件の検索・取得が順番待ちになり、課金安全の前提(先発を強制ログアウトさせない)も揺らぐ**。
2. **候補キャッシュの TTL が10分**。地図で筆を探す作業は10分を超え得る。「検索して候補を出してから地番を調べさせる」順序にすると、**取得しようとした時にキャッシュが消えていて 409** が多発する。
3. **地番を保存すると物件の指紋が変わる**。検索の**後**に保存すると、取得時に指紋不一致で **409**。

→ **順序は「ポップアップ → 地番を保存 → 検索 → 候補を選ぶ → 取得」で固定する**。自動操作が始まる前にポップアップは閉じ切っている。

## 3. 画面

### 3.1 いつ出すか

「所在で謄本を検索」を押したとき、**物件の地番(土地)/家屋番号(建物)が空**なら、確認パネルの**前に**ポップアップを出す。

⚠ **判定は既存の preflight API に足す**(単発・所在検索・一括の**3入口が共有**している)。単発ボタンにだけ足すと、**一括と挙動が割れる**。

⚠ **不動産番号を持つ物件では出さない**。番号がある物件は所在検索の経路に入らない(`searchable: false`)。

### 3.1.0 ⚠**一括ではポップアップを出さない**(@codex #370 R3 P2)

ポップアップは**1件ぶん**の作り(住所1つ・入力欄1つ・version 1つ・PATCH 1回)。一括で選んだ中に**番号の無い物件が複数**あったり、**土地と建物が混ざったり**すると、この作りでは扱えない。**1件ずつモーダルを出すのは運用に耐えない**。

→ **一括では聞かない。除外して知らせる**(既存の「取得済み」警告と同じ形):

1. ジョブ作成時に、**§3.1.1 の表で必要な番号が無い物件を対象から外す**
2. 画面に**外した理由ごとに件数と対象の一覧**を出す(黙って減らさない)。⚠**すべてを「地番が未入力」と書かない**(@codex #370 R5 P2)。**理由によって、利用者がやるべきことが違う**:

⚠ **既存の除外理由も同じ表に載せる**(@codex #370 R7 P2)。`buildRegistrySearchRequest` は**今も**「住所が無い」「不動産番号がある」で除外しており、§4.4 で「**形式が読めない**」が加わる。**全部を理由ごとに出す**(1つでも落ちると、その利用者は理由が分からず詰まる):

| 理由 | 表示 | 利用者がやること |
|---|---|---|
| 土地で地番が無い | 「**地番が未入力**: ◯件」 | 物件ページで**地番を入れる**(ポップアップから地図へ行ける) |
| **地番も家屋番号も無い** | 「**地番・家屋番号が未入力**: ◯件」 | **地番**を入れる(ポップアップから地図へ行ける)か、**家屋番号**を入れる(⚠家屋番号は**地図では分からない**。権利証・固定資産税の通知・過去の謄本で確認) |
| **住所が未入力**(既存) | 「**住所が未入力**: ◯件」 | 物件の**住所を入れる** |
| **番号の形式が読めない**(§4.4) | 「**地番/家屋番号の書き方**: ◯件」 | **地図に出たとおりの表記**に直す(`69-2` など) |
| **不動産番号がある**(既存) | 「**所在検索の対象外**: ◯件」 | ⚠**所在で探す経路の対象外**(番号があれば所在は要らないため)。⚠ただし**番号で取得する経路も現状は完走しない**(下記)。**別の方法で取得する** |

⚠ 最後の1つは「直せば通る」ものではない。**番号を持つ物件は所在検索から外れるのに、番号での取得も完走しない**という**既存の行き止まり**なので、**そう見えるように書く**(「対象外」であって「入力の不備」ではない)。

⚠ **「配線が無い」ではなく「途中で止まる」**(@codex #370 R15 P2 への回答)。実コードを読むと:

- `POST /api/properties/[id]/registry/auto-fetch` は物件の `realEstateNumber` を
  `runRegistryAutoFetch` へ**渡している**(呼び出しの配線はある)
- ところが公式プロバイダの `searchByRealEstateNumber` は、**実サイトに触れる前に止める**
  実装になっている(`auto-fetch.ts` の該当箇所に理由つきのコメントがある)。段階②
  (確定 → マイページで請求 → PDF)が未実装で、**確定まで進めるとカートに `未請求` の行だけが
  残り、再試行のたびにゴミ行が積み上がる**ため、**何も触らずに失敗する**方を選んでいる
- 呼び出し側から見た結果は `provider_error`。**PDF は取得できない**

→ 画面の文言は「**この経路では取得できません**」でよい(利用者にとっては同じ)。
⚠ ただし**設計上の言い方は「未配線」ではなく「段階②が未実装で、実サイトに触れる前に止まる」**
とする。前者だと「呼び出しを足せば動く」と読めてしまい、**カートを汚す実装を足す**方向へ誘導する。

3. **残りの物件でジョブは作れる**(全体を止めない)
4. 外された物件は、**物件ページで1件ずつ**対応してもらう

⚠ **ジョブ作成が許されるのは「1件でも対象が残るとき」**。全件が対象外なら作成せず、その旨を出す。

### 3.1.0.1 ⚠**作成の時点で「実際に使う番号」を固定する**(@codex #370 R13 P1)

§4.4 の処理時の検査は「**消えていないか / 読めない形になっていないか**」しか見ない。
ところが一括は**作成から処理までに時間が空く**(順番待ち)。その間に誰かが地番を
**別の正しい値へ書き換える**と、検査は素通りし、`runRegistrySearch` は**書き換え後の筆**を
探し、**候補が1件なら自動で購入される**。利用者が確認したのは**書き換え前の番号**なので、
**別の筆の登記を、確認なしで買った**ことになる。

→ **ジョブの各行に、作成時点の「検索に渡すもの一式」を控える**(値そのものではなく**指紋**でよい。
⚠地番は秘匿情報＝§5 の規則に従い生値を残さない)。

⚠ **番号だけを控えても足りない**(@codex #370 R15 P1)。`runRegistrySearch` は処理の時点で
**物件を読み直して住所も使う**ので、番号が同じでも**住所が書き換われば別の場所を探す**。
また、**同じ数字が `buildingNumber` と `lotNumber` の間で移動する**と、
番号の文字列は変わらないのに**取りに行くもの(土地/建物)が変わる**。

→ **指紋には次の3つを全部入れる**。1つでも変われば「変わった」とみなす:

| 指紋に入れるもの | 変わると何が起きるか |
|---|---|
| **住所**(所在の検索に渡す文字列) | 別の地番区域を探し、**別の場所の登記**が候補になる |
| **選ばれた番号の種類**(地番 / 家屋番号) | 同じ数字でも**土地と建物が入れ替わる** |
| **正規化した番号の値** | 別の筆を探す |

処理時の判定は次のとおり:

| 処理時の状態 | 振る舞い |
|---|---|
| 控えた指紋と一致 | そのまま処理する |
| **番号が消えた / 読めない形になった** | 従来どおり skip(理由つき) |
| ⚠**別の正しい値に変わっていた** | **skip して「内容が変わりました。確認して選び直してください」**。⚠**黙って新しい番号で買わない** |

⚠ **「変わった」と「消えた」を別の理由コードにする**。利用者のやることが違う
(前者=もう一度選ぶ / 後者=番号を入れる)。

**テスト**(3つとも書く): ジョブ作成後に (1) **地番を別の正しい値へ**書き換える (2) **住所だけ**
書き換える (3) 同じ数字を**地番から家屋番号へ移す** → いずれもその行が **skip され、
実サイトに触れず、課金も発生しない**こと。

### 3.1.1 ⚠**種別ごとに「どの番号が要るか」を全部決める**(@codex #370 R2 P1)

`PropertyType` は土地/建物の2値ではなく**14値**ある。現在の provider は**「`buildingNumber` が入っているか」だけで土地/建物を判定**しており、**まさにその欄が空**の場面ではどちらとも決められない。決めずに実装すると**種別を推測して誤った登記を買う**。

> ⚠ **発注者判断(2026-08-12): 止めない**。当初案は「必要な番号が無ければ実行を止める」だったが、**業務上困る**との回答。理由は明快で、**建物の物件でも、地番があれば「土地の謄本」は取れる**(所有者を調べる用途ではむしろそれが要る場面がある)。止めると**使えていたものが使えなくなる**。
>
> → **止める設計をやめ、「何を取ろうとしているかを明示し、種別と食い違えば警告する」に変える**。

**登記の種別(土地/建物)は、持っている番号で決まる**(既存どおり):

| 持っている番号 | 何を取りに行くか |
|---|---|
| **家屋番号がある** | **建物**の登記 |
| **家屋番号が無く、地番がある** | **土地**の登記 |
| **どちらも無い** | ⚠ 実行できない(下記) |

**物件の種別は「警告の材料」として使う**(実行を止める材料にはしない):

| 物件の種別 | 期待される登記 | 食い違ったときの表示 |
|---|---|---|
| `land` 土地 | 土地 | 家屋番号があるとき →「この物件は**土地**ですが、**建物**の登記を取得します」 |
| `house` 戸建 / `apartment_unit` 区分 / `apartment_building` 一棟マンション / `apartment_block` 一棟アパート / `store` 店舗 / `office` 事務所 / `warehouse` 倉庫 / `factory` 工場 / `building`(旧) / `unit`(旧) | 建物 | 家屋番号が無く地番で取るとき →「この物件は**建物**ですが、**土地**の登記を取得します(建物の謄本には家屋番号が必要です)」 |
| `parking` 駐車場 / `other` その他 / `unknown` 不明 | 決められない | 警告は出さない(どちらもあり得る)。**何を取りに行くかだけ**は必ず表示する |

⚠ **警告は「見せて止めない」**。既存の取得前警告(取得済み・所有者あり)と同じ扱いで、**確認したうえで実行できる**。

⚠ **「どちらの番号も無い」ときだけ実行できない**。これは止めているのではなく、**サイトに渡すものが無い**(番号なしで検索するとその地番区域が丸ごと候補になり、選びようがない)。この場合に §3.2 のポップアップを出す。

⚠ **この警告が読み込めなかったときは実行させない**(@codex #370 R14 P1)。既存の
`useRegistryPreflight` は、**取得前警告の取得に失敗すると `settledKey` を立てて実行ボタンを
戻す**(`registry-preflight-warnings.tsx`)。これは「取得済み・所有者あり」のような
**参考情報**なら妥当だが、**この分類は参考ではない**——「土地と建物のどちらを買うのか」は
**買う対象そのもの**で、分からないまま実行すると**候補1件で自動購入まで進む**。

→ **この分類だけは fail closed** にする:

- 分類が**読み込めていない**間は、実行ボタンを**押せないままにする**(既存の失敗時の
  「戻す」挙動を、この項目には**適用しない**)
- 画面には「**何を取りに行くか確認できませんでした。もう一度お試しください**」と出す
- ⚠ **一括でも同じ**。ジョブの作成/実行の応答に**分類を含めて返し**、それが無い行は
  **進めない**(画面の警告表示だけに頼らない=画面を経由しない呼び出しで素通りするため)

**テスト**: 分類の取得を失敗させる → **実行ボタンが押せないまま**であること・
**一括でも進まない**こと。

⚠ **この表は「所在で探す」経路にだけ効く**(@codex #370 R4 P2)。**不動産番号を持つ物件は対象外**(番号があれば所在も地番も要らない)。番号ありの物件にこの表を当てると、**家屋番号の無い建物や種別が曖昧な物件で、番号による取得までできなくなる**(既存経路の劣化)。§3.1 の「番号があればポップアップを出さない」と揃える。

### 3.1.2 ⚠**土地か建物かは「持っている番号」で決める。物件の種別では決めない**(@codex #370 R4 P1・発注者判断 2026-08-12 で向きを反転)

現在の provider は **`buildingNumber` が空でなければ建物として検索**する。ところがスキーマ・編集画面・取込のいずれも、**土地の物件に家屋番号が残っていること**を許している。すると:

> 種別=土地・地番あり・**家屋番号も残っている** → 「必要な番号はある」の検査は通る
> → `buildRegistrySearchRequest` が**両方**を渡す → provider が**建物として検索**
> → **土地の物件に対して建物の登記が返り、一括なら自動で購入される**

→ **登記の種別は「持っている番号」で決まる**(既存どおり・発注者判断により種別では決めない):

- **家屋番号がある** → **建物**の登記(`buildingNumber` を渡す)
- **家屋番号が無く地番がある** → **土地**の登記(`lotNumber` を渡す)
- **両方ある** → **家屋番号が優先**(= 建物)。⚠ **物件の種別が「土地」ならここで警告を出す**(§3.1.1)

⚠ **決まらなかった方の番号は渡さない**(呼び出し側で落とす)。両方渡すと、provider の判定と呼び出し側の意図が**二重管理**になる。**渡すのは1つだけ**にして、provider の `isBuilding` 判定と必ず一致させる。

**テスト**: 土地の物件に家屋番号が残っている状態で検索 → **建物として検索され、かつ「土地の物件ですが建物の登記を取得します」の警告が出る**。

⚠ **種別は指紋に入れない**(@codex #370 R6 P1 は**この方針変更で解消**)。R6 の懸念は「種別が土地/建物を決める根拠なのに、検索と取得の間に種別が変わると指紋が一致してしまう」だった。**種別は根拠でなくなり、根拠は番号(既に指紋に入っている)**なので、**種別を指紋に加える必要は無い**。
⚠ 種別が変わっても**取りに行くものは変わらない**(番号が変わっていないため)。変わるのは**警告の文言だけ**なので、**取得を 409 で止めない**(不要な取り直しを増やさない)。

### 3.2 中身

```
┌─ 地番が必要です ────────────────────────────┐
│                                                        │
│ 謄本は「地番」でしか取れません。住所の番号(住居表示)と  │
│ は別のものです。地図で確認してください。                │
│                                                        │
│ この物件の住所                                          │
│   神奈川県横浜市南区井土ケ谷中町69-2      [コピー]      │
│                                                        │
│   [ 地番検索サービスを開く(無料・別タブ) ]              │
│   ↑ 開いたら住所で検索 → 地図を拡大 → **該当の筆をクリック** │
│      → 出てきた地番をここへ入れてください                │
│                                                        │
│ 地番   [                    ]                          │
│                                                        │
│           [ キャンセル ]  [ 保存して検索へ ]            │
└────────────────────────────────────────┘
```

- **住所をコピーできるようにする**。⚠ 座標が無い物件が大半(本番は668件中667件が座標なし)なので、**地図は住所で検索してもらう**のが現実。
- **座標があれば** その位置を開く。無ければ**サービスを開くだけ**。⚠ 既存の「座標が無ければリンクを出さない」作法とは**変える**(出さないと大半の物件で使えない)。

**開く先(@codex #370 R8 P2)**:

| 状況 | URL |
|---|---|
| 座標あり | `https://minji-houmu.rmp.glbs.jp/view/chiban_search/map/#18/<緯度>/<経度>` |
| 座標なし | `https://minji-houmu.rmp.glbs.jp/view/chiban_search/map/` |

- 名称: **法務省「登記所備付地図データ」の地番検索サービス**(無料)。
- ズーム `18` は**筆界と地番が見える倍率**(発注者の実機画面で確認済み。`#15` では筆界が出ない)。
- 緯度・経度は**小数6桁程度**でよい(実機の例: `#18/35.430368/139.601094`)。
- ⚠ **これは「物件の位置を外部サービスへ渡す機能」として扱う**(@codex #370 R9 P1)。

  当初「座標はフラグメント(`#` 以降)なので外部サーバーへ送信されない」と書いたが、**誤り**。最初の HTTP リクエストに載らないだけで、**そのサービスの JavaScript が `location.hash` を読む**(読まなければ地図をその位置に寄せられない)。**地図データの取得も その座標の範囲について行われる**。よって**座標は相手に渡っている**。

  → **「外部送信ではない」として扱わない**。次の扱いにする:

  - **利用者がボタンを押したときだけ**渡す(自動では開かない・自動では送らない)
  - **画面に明示する**:「**この物件の位置を地図サービスへ渡して開きます**(法務省の無料サービス)」
  - **座標が無い物件では、住所も渡さない**(サービスのトップを開くだけ。住所は画面でコピーしてもらう)
  - ⚠ **`rel="noopener noreferrer"`**(referrer で物件詳細の URL を渡さない)

  **同種の前例がある**: このアプリは既に**物件の座標で Google マップを別タブで開く**導線を持っている(現地調査・物件化フォーム)。**扱いをそちらに揃える**(新しい種類の開示ではない)。⚠ ただし「送信されない」という説明だけは**しない**。
- ⚠ **URL の形は発注者の実機画面から採った実測値**。実装時に**一度実URLで開いて確認する**(仕様書がある類のものではない)。
- **両方の分岐のテストを書く**(座標あり→座標入りのURL/座標なし→トップのURL)。
- ⚠ **文言に「該当の筆をクリックして」を必ず入れる**。座標は**建物の位置**であって**筆の代表点ではない**。地図の中心の地番をそのまま写すと**誤った土地を買う**。
- ⚠ **`rel="noopener noreferrer"`**。`noreferrer` が無いと**物件詳細の URL(UUID)が外部へ漏れる**(このアプリは Referrer-Policy を設定していない)。
- ⚠ **費用の書き分け**: 「**この画面の操作では課金されません**(地番検索サービスは無料)。**課金は次の取得のときです**」。既存の候補一覧は「無料/有料/課金/費用」の語を出さないテストで固定されているので、**ポップアップ側にだけ書く**。

### 3.3 建物のとき ⚠**このポップアップで家屋番号は尋ねない**

@codex #370 P1。当初は「ラベルだけ差し替えて家屋番号を尋ねる」としたが、**誤り**:

> **地番検索サービスの地図が返すのは「地番」であって「家屋番号」ではない。**

ラベルだけ変えると、利用者は案内どおり**筆をクリックして地番を読み**、それを**家屋番号として保存**してしまう。そのあと:

- provider は**家屋番号が空でなければ「建物」として検索**するので、**地番を家屋番号として建物検索**することになる
- 一括取得は**候補が1件なら自動で購入**するため、**誤った登記を買って添付・取込まで進む**

→ **建物で家屋番号が空の物件では、入力欄を出さない**。ポップアップは**案内だけ**にする:

```
┌─ 家屋番号が必要です ──────────────────────┐
│ 建物の謄本には「家屋番号」が要ります。               │
│ ⚠ 家屋番号は**地番検索サービスの地図では分かりません**  │
│   (地図が示すのは土地の地番です)。                   │
│                                                    │
│ 権利証・固定資産税の通知・過去の謄本などでご確認のうえ、 │
│ 物件の「家屋番号」欄に入力してから実行してください。    │
│                                    [ 閉じる ]      │
└──────────────────────────────────┘
```

⚠ **保存させない**(誤った値を入れる口を作らない)。

**将来の選択肢(この設計の範囲外)**: 登記情報提供サービスの請求方法には**「土地からの建物検索」**がある(実サイトのラジオで確認済み)。家屋番号が分からない建物はこの経路が本筋なので、**別エピックとして記録**する。

⚠ **建物で家屋番号が空でも「止めない」**(発注者判断 2026-08-12)。**地番があれば土地の登記として取得できる**ようにする(既存どおり)。ただし **§3.1.1 の警告**を出す:

> 「この物件は**建物**ですが、**土地**の登記を取得します(建物の謄本には家屋番号が必要です)」

**地番も無い**ときだけ、上のポップアップを出す。⚠ただし**案内だけで終わらせない**(@codex #370 R11 P2)。

家屋番号も地番も空の建物は、案内だけを出して閉じると**この画面からは何もできない**。発注者判断で「建物でも地番があれば土地の登記を取れる」ことにした以上、**その地番を入れる口をここに用意しないと、新しく取れるようにした経路へ到達できない**。

→ ポップアップに**2つの道**を出す:

| 選ぶもの | 中身 |
|---|---|
| **建物の登記を取る**(本筋) | 案内のみ。家屋番号を権利証・固定資産税の通知・過去の謄本で調べて、物件の「家屋番号」欄に入れてから実行してもらう。⚠**この画面からは保存させない**(地図では家屋番号は分からないため) |
| **土地の登記を取る** | §3.2 の地図の流れ(地番検索サービス)へ進み、**`lotNumber` にだけ保存**する。§3.1.1 の「建物ですが土地の登記を取得します」の警告を出す |

⚠ **地図で調べた値を `buildingNumber` に保存することは、引き続き禁止**(地図が返すのは地番であって家屋番号ではない)。保存先を利用者に選ばせない=「土地の登記を取る」を選んだときだけ `lotNumber` に入る、という一方向にする。

## 4. 入力された地番の扱い

### 4.1 保存してから検索する

**`PATCH /api/properties/[id]` で `lotNumber` を保存 → その後に検索を開始**。

⚠ **保存の直後に検索を投げない**(@codex #370 R9 P2)。既存の画面は**検索の前に確認パネル**を出しており、そこで「この操作で料金が発生することがある」旨を見せて、**利用者がもう一度押して初めて**検索が走る。ポップアップから直接検索を投げる実装にすると、**この確認を飛ばす**ことになる(§3.1 の「ポップアップは確認パネルの**前に**出す」とも矛盾する)。

→ **保存が成功したら、ポップアップを閉じて `confirmSearch`(既存の確認パネル)へ進むだけ**にする。**検索の API を呼ぶのは、利用者が確認パネルで押したとき**。

```
ポップアップ(地番を入れる) → [保存] → 保存成功 → ポップアップを閉じる
  → 既存の確認パネル(confirmSearch) → [検索する] → 検索の API
```

**テスト**: ポップアップで保存しただけでは**検索の API が呼ばれない**こと。

⚠ **この経路で `buildingNumber` は保存しない**(@codex #370 R2 P1)。§3.3 のとおり**家屋番号は地図では分からない**ので、この導線から家屋番号が保存される口を**一切作らない**。⚠**保存できるのは `lotNumber` だけ**(建物で地番も家屋番号も無いときは §3.3 の「**土地の登記を取る**」を選んだ場合に限り、地図で確認した地番を `lotNumber` へ保存する。「**建物の登記を取る**」側は**案内のみ**で入力欄を出さない)。

- **保存の前に検索してはいけない**(指紋が変わって取得が 409)。
- 保存には **`property:write` と現在の `version`** が要る。ポップアップは**物件の version を受け取り、409(他の人が先に更新)を画面で扱う**。
- 次回以降も使えるようになり、**変更履歴に残る**(誰がいつ入れたか)。

⚠ **権限が2種類に割れる**: 謄本取得は `registry:auto_fetch`、地番の保存は `property:write`。**取得はできるが保存はできない**利用者がいる。その場合は**ポップアップを出さず**、「地番を入力してから実行してください(地番の編集権限が必要です)」と案内する。**「保存せず1回だけ使う」口は作らない**(§4.2)。

### 4.2 「その場限りの地番」を渡す口は作らない

検索 route に地番を渡せるようにする案は**採らない**:

- サーバーが DB から読む前提が崩れ、**指紋・候補キャッシュ・二重課金の鍵**がすべて「渡された値」と「保存された値」の二重管理になる。
- 同じ物件で**違う地番を入れた2つのタブ**が同じ指紋を持ち、後勝ちで候補が入れ替わる。

### 4.3 入力の検査

⚠ **「正規化して数字が残るか」だけの検査では足りない**(@codex #370 P1)。`normalizeChibanForDialog` は**数字とハイフン以外をすべて削除する**ので、`abc1x2` も `1号2` も**同じ `12`** になる。`12` は**別の筆**を指し得るうえ、**一括取得は候補が1件なら自動で買う**ので、**誤った登記を買って添付・取込まで進む**。

→ **受理する書式を明示して、それ以外は弾く**(黙って落とさない):

⚠ **受理する範囲は `normalizeChibanForDialog` が扱える表記に合わせる**(@codex #370 R16 P2)。
表を勝手に狭めると、**既に保存されている物件や取込済みのCSV**が新しい検査で 422 になったり
一括から外れたりする(**今まで取れていたものが取れなくなる**)。

| 受理する | 例 |
|---|---|
| 数字 | `69` |
| 数字と区切り記号 | `69-2` / `1-1-1` |
| 「番地」「番」「の」「ノ」を区切りに使ったもの | `1番地2` / `69番2` / `69の2` / `1ノ2` |
| 各種ダッシュ・長音記号 | `69‐2` / `69ー2` / `69－2`(ハイフンへ寄せて受理) |
| 前後の空白・全角数字 | `６９－２` |

**上記以外の文字が1つでも混じっていたら拒否**し、「地図に表示された地番をそのまま入れてください」と案内する。

⚠ **判定は「正規化してみて、元の文字が全部説明できるか」で書く**。表を人手で写した allowlist にすると、
正規化側に表記が足された/削られたときに**片方だけずれる**。**同じ関数の対応表から導く**こと。

⚠ **拒否のテストを必ず書く**: `abc1x2` / `1x2` / `69-2 の隣` のように**数字と未対応の文字が同居する**ケース(通ってしまうと別の筆を買う)。
- ⚠ **受理のテストも必ず書く**: `1番地2` / `1ノ2` / `69ー2` が**通る**こと(既存データが新しい検査で落ちない)。
- ⚠ **新しい正規化を作らない**。既存は `normalizeChibanForDialog`(自動操作用)と `normalizeLotNumber`(二重課金の鍵用)の**2つに分かれていて「号」の扱いが食い違う**。3つ目を作らず、**入力の検査は `normalizeChibanForDialog` に寄せる**。
- ⚠ **住所から地番を自動生成・自動補完しない**。所在欄に地番まで入れて実機で失敗した前例がある。ポップアップは「**人が地図で読んだ値を入れる**」入口に徹する。

## 4.4 ⚠**画面の判定だけでは塞げない。サーバー側でも同じ検査をする**

@codex #370 R2 P1。ポップアップと preflight は**画面の都合**であって、**実行経路は素通りできる**:

- 権限のある利用者は**検索 API / 一括ジョブの作成 API を直接叩ける**。`buildRegistrySearchRequest` は**住所さえあれば searchable** なので、番号なしのまま実サイトを検索してしまう。
- **一括は処理時にもう一度検索する**。preflight を通った後・処理される前に**番号が消される**と、番号なしで検索し、**候補が1件なら自動で購入**する。

→ **provider を呼ぶ直前に、もう一度検査する**。⚠**検査するのは「種別に合う番号か」ではなく「地番か家屋番号のどちらかが有り、それが読める形か」**(発注者判断により**種別では止めない**ため)。どちらも無い/読めないなら **422**(入力の問題)で止め、**実サイトに触れない**。⚠**不動産番号を持つ物件はこの検査の対象外**(§3.1.1 の注記)。

⚠ **検査は「有るか」だけでなく「読める形か」まで見る**(@codex #370 R4 P1)。§4.3 の書式の検査を**ポップアップにしか置かない**と、**編集画面・PATCH API・CSV取込**から入った `abc1x2` のような値が:

1. **空ではない**ので presence の検査を通り
2. `normalizeChibanForDialog` で **`12`** に潰され
3. **別の筆**を検索し、**一括なら候補1件で自動購入**される

→ **§4.3 の受理する書式を、provider を呼ぶ直前でも適用する**(ポップアップと同じ判定関数を共有する)。読めない形なら **422** で止める。

⚠ **判定関数は1本にする**(ポップアップ・検索の入口・一括の処理時が同じものを使う)。3箇所で別々に書くと必ずずれる。

| 検査を入れる場所 | 理由 |
|---|---|
| `buildRegistrySearchRequest`(単発・一括の**共通の入口**) | ここが「検索してよいか」の唯一の判定。⚠**判定に足すのは「§3.1.2 の家屋番号優先で選ばれた番号が有るか」「その番号が読める形か」の2つだけ**。**種別との組み合わせは見ない**(発注者判断=種別では止めない) |
| 一括の**処理時**(`processNextBulkItem`) | 作成時に通っても、**処理時に消えている**ことがある。処理の直前にもう一度見る |
| ⚠**単発の取得**(`POST /api/properties/[id]/registry/auto-fetch` → `runRegistryAutoFetch`) | @codex #370 R8 P1。**この経路は上の2つを通らない**(検索とは別の入口で、直接 provider を呼ぶ)。ここを塞がないと、**番号が無い/読めない物件に対して取得だけ直接叩ける** |

⚠ **「検索」と「取得」は別の入口**。検索側だけ塞いでも、取得の API を直接呼ばれると素通りする。**取得の直前にも同じ判定関数を通す**(⚠不動産番号がある物件は対象外、の例外も同じく適用)。

⚠ **「共通の入口で判定する」と「呼び出し側で止め方を変える」を分ける**(@codex #370 R7 P2)。共通の入口で**例外を投げてはいけない**し、既存の返し方のままでも**422 にならない**:

- `runRegistrySearch` は**検索できない結果をすべて `{ searchable: false }` に畳んで 200 で返す** → **足すだけでは 422 にならない**
- 逆にここで **422 を投げると、一括のジョブ作成が丸ごと落ちる** → §3.1.0 の「残りの物件で作れる」と矛盾する

→ **共通の入口は「理由」を返すだけにする**(`missing_identifier` / `malformed_identifier` を既存の `insufficient_location` などと同じ形で追加。⚠**`ambiguous_type` は作らない**=種別では止めないため)。**止め方は呼び出し側が決める**:

| 呼び出し側 | 新しい理由が返ったときの振る舞い |
|---|---|
| 単発の検索 API | **422**(入力の問題)で止める。実サイトに触れない |
| 一括のジョブ作成 | **その物件だけ除外**し、§3.1.0 の理由別の一覧に載せる。**ジョブ自体は残りで作る** |
| 一括の処理時 | **その項目を skip**(既存の skip と同じ扱い・理由コードを残す) |

⚠ **preflight は「早く知らせる」ためのもので、止めるのはサーバー**。両方に置く(片方だけだと fail-open)。

**テスト**: 番号を空にした物件で**検索 API を直接叩いて 422**(実サイトへ行かない)/**一括で作成後に番号を消してから処理して skip**。

## 5. 壊してはいけない安全装置

| 装置 | 壊れ方 | 守り方 |
|---|---|---|
| **課金スイッチ(501)と30日の二重課金台帳** | ⚠**`locationCandidate` を渡し かつ 不動産番号が空のときだけ発動**する。入力した地番を別の引数(番号相当)で流すと**両方すり抜ける** | 入力した地番は**必ず「検索 → 候補 → `locationCandidate`」の既存経路に合流**させる。購入判定の分岐を必ず通す |
| **二重課金の鍵** | 鍵は**サイトが返した候補の地番**から作る。人が入力した値を直接鍵にすると、サイトの正規表記と食い違って**同じ登記を2回買える** | 鍵の材料は**サイト由来の候補値に固定**(現行のまま。変えない) |
| **取得前の警告(preflight)** | ⚠ `confirmObtain` の state でだけ発火し、確認完了まで実行ボタンを disabled にしている。**新しい state を挟むと警告なしで課金に進む** | 新 state でも preflight を **active にし、実行ボタンに `disabled={preflight.pending}` を付け直す** |
| **一括取得の歯止め** | 一括は「候補が複数なら自動で買わない(`ambiguous_candidate` で skip)」で誤課金を防いでいる | 地番入力で**1件に絞れたときだけ**進め、絞れなければ**従来どおり skip**。歯止めを緩めない |
| **中止の規則** | 「課金前だけ止める・受け付けた中止は必ず効く」 | 有料取得側に中止の節目を**新設しない**。`endCancelable` の後にもう一度見る対を壊さない |
| **地番は秘匿情報** | ログ・監査・実況パネル・エラー文言に出さない運用 | ポップアップの入力値を**これらに出さない**(件数と分類コードのみ) |

## 6. 文言の整合

`location_rejected` の固定文言は「住所に地番まで含まれている/丁目まで整えて地番は地番欄へ」と案内している。**ポップアップができると利用者の対処手順が変わる**ので、文言を導線と矛盾させない(422 = 入力の問題、という分類自体は維持)。

## 7. テスト方針

- **出す/出さないの判定**(⚠**種別で止めない**方針に合わせる):
  - **地番か家屋番号のどちらかがある** → **ポップアップを出さない**(種別を問わず、そのまま実行できる)
  - **どちらも無い** → **ポップアップを出す**
    - 種別が**土地** → **入力欄つき**(地図で地番を確認して入れる)
    - 種別が**建物系** → ⚠**2つの道**が出ること(§3.3):
      - 「**建物の登記を取る**」= **案内のみ**。⚠**入力欄も保存も無い**こと(家屋番号は地図では分からない)
      - 「**土地の登記を取る**」= 地図の流れへ進み、⚠**保存先が `lotNumber` だけ**であること。**地図で得た値が `buildingNumber` に入らない**ことを固定する
    - 種別が**駐車場・その他・不明** → **入力欄つき**(地番を入れれば土地の登記が取れる)+ 「建物の謄本には家屋番号が必要です」の一文
  - **不動産番号あり** → 出さない(種別を問わず)
- **警告(止めない)**(§3.1.1):
  - 種別=土地・**家屋番号あり** → 「土地の物件ですが**建物**の登記を取得します」が出て、**それでも実行できる**
  - 種別=建物系・家屋番号なし・**地番あり** → 「建物の物件ですが**土地**の登記を取得します」が出て、**それでも実行できる**
  - 種別=駐車場・その他・不明 → **警告は出さない**が、**何を取りに行くか**は表示される
- **渡す番号は1つだけ**: 土地の物件に家屋番号が残っていても、**渡すのは家屋番号だけ**(両方渡さない)。
- **順序**: 保存 → 検索 の順であること(逆順だと取得が 409 になる回帰)。
- ⚠**保存だけでは検索 API を呼ばない**(既存の確認パネルを経由する)。
- **権限**: `registry:auto_fetch` はあるが `property:write` が無い利用者 → ポップアップを出さず案内。
- **preflight**: 新しい state でも警告が出て、確認が終わるまで実行できないこと。
- **入力の検査**: 数字が残らない値を弾くこと。
- **外部リンク**: `target="_blank"` と **`rel="noopener noreferrer"`** がソースにあること(走査型)。
- **秘匿**: 入力した地番がログ・監査・実況に出ないこと(走査型)。
- **一括**: 候補が複数なら従来どおり skip されること。
- ⚠**一括で番号が変わったとき**: ジョブ作成後に地番を**別の正しい値**へ書き換える → その行が **skip され、実サイトに触れず課金も発生しない**こと(§3.1.0.1)。
- ⚠**分類が読めないとき**: 何を取りに行くかの分類の取得を失敗させる → **実行ボタンが押せないまま**であること・**一括でも進まない**こと(§3.1.1・fail closed)。

## 8. レビューで特に見てほしい論点

1. §2 の「途中で止めない」判断(セッション占有・TTL・指紋の3点)は妥当か。
2. §4.1 の「保存してから検索」に伴う `version` 409 の扱いと、権限が割れる利用者への案内。
3. §5 の課金安全(とくに **`locationCandidate` 経路に合流させる**)が、実装でどう担保されるか。
4. 座標が無い物件が大半である前提で、地図を「開くだけ」にする縮退が実務に耐えるか。
5. **(解決済み・発注者判断 2026-08-12)** 「種別に合う番号が無ければ止める」案は**業務上困る**との回答により**撤回**。**止めずに、何を取りに行くかを明示し、種別と食い違えば警告する**形にした(§3.1.1)。**実行できないのは「地番も家屋番号も無い」ときだけ**。
6. **(解決済み・発注者判断 2026-08-12)** **不動産番号による検索・取得は今後も作らない**。かつ **(b) 不動産番号を入れない運用**とする。
   → **この設計では何も変更しない**(番号がある物件が所在検索の対象外である既存の挙動はそのまま)。本番は該当ゼロ。
   ⚠ **運用上の申し送り**: 番号を入れると**その物件は謄本を取得できなくなる**。取込のCSVに「不動産番号」列があるので、**入れ直しのときにこの列を使わない**。将来この前提が変わったら、番号を無視して所在検索へ回す(旧(a)案)を検討する。
