# マンション名簿(セルフインの一覧)で物件登録を自動補完する — 設計

- 日付: 2026-10-18
- 発注者の決定: 使い道=**物件登録の自動補完**/入れ方=**案A(裏の名簿にして、使うときに棟にする)**/検索窓で名簿も出す
- 前提: 発注者が運営会社(株式会社リニュアル仲介・セルフイン)から利用の許可を取得(2026-10-17)。規約 https://self-in.com/rule 第3条・第5条の「システム管理会社が認める場合」に当たる。

## 1. ねらい

区分マンションを登録するとき、建物名を入れるだけで、その建物の
**竣工年月・階数(地上/地下)・総戸数・構造・管理会社**が入った「マンション棟」に自動でつながる。
社内でまだ棟が無い建物でも、名簿にあればその場で棟ができる。

「マンション棟」の一覧は、これまでどおり**自社の物件がある棟だけ**を並べる(名簿の8万8千件は並べない)。
検索窓で探したときだけ、名簿の建物も別の段に出す。

## 2. 元データ

- 集め方: 本番サーバーの `selfin-collect.service`(アプリとは別・1分に1ページ・2026-10-17 開始)。
  一都三県(東京45,851・神奈川23,049・埼玉9,455・千葉9,266=計87,621件)。
- 1件の形(JSONL・1行1件):
  `{ pref, page, fetchedAt, id, name, address, stations[], completed, structure, floors, units, developer, manager }`
- 実データで見た値の形(東京26,640件で実測):
  - 竣工 `2026年9月`(26,633件)/`不明`(7件)
  - 階建 `地上14階建`(18,729)/`地上10階建 地下1階`(7,911)
  - 総戸数 `155戸`(26,147)/`総戸数不明`(493)
  - 構造 `RC（鉄筋コンクリート）` など12種類・`不明` 6件
- ⚠並びの同点で、同じ建物が2ページに出る(取った4,040件中18件)。名簿の鍵(下記)で1件にまとめる。
  同じ数だけ取りこぼしもあるので、取り終わったら件数の差を数え、別の並び順で取り直して埋める(運用・この設計の外)。

## 3. データの持ち方(migration 1本・足すだけ)

### 3.1 新しい表 `mansion_catalog`(名簿)

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid | |
| source | text | `selfin`(将来ほかの名簿を足せるように) |
| source_id | text | セルフインの建物番号(`/mansion/<番号>.html`) |
| name | text | 建物名(取ったまま) |
| address | text | 住所(取ったまま) |
| pref_code | text | `13` など |
| stations | text[] | 「九品仏駅より 徒歩5分」など(取ったまま) |
| built_year / built_month | int? | 竣工年月を数字にしたもの。読めなければ null |
| total_floors / basement_floors | int? | 地上・地下の階数 |
| total_units | int? | 総戸数 |
| structure_type | text? | 構造(取ったまま・`不明` は null) |
| developer | text? | 分譲会社 |
| management_company | text? | 管理会社 |
| raw | jsonb | 取った1件をそのまま(数字に直す前の文字も残す) |
| name_key / area_key | text? | 棟と同じ比べる形(`src/lib/building-identity.ts` の `buildingNameKey`・`areaKey`) |
| fetched_at | timestamptz | 取った時刻 |
| created_at / updated_at | timestamptz | |

- 一意: `(source, source_id)`。索引: `(area_key, name_key)`・`name_key`・`name`。
- 個人の情報は含まない(公開されている建物の情報だけ)。

### 3.2 `buildings` に1列足す

- `catalog_id uuid null unique` → `mansion_catalog.id`(名簿のどの建物から作った/埋めたか)。
  - 同じ名簿の建物から棟を2つ作らないための鍵。
  - 「名簿にあるマンション」の段に、すでに棟になったものを出さないために使う。

## 4. 名簿に入れる(読み込み)

- 秘密の合言葉つきの口 `POST /api/mansion-catalog/load-run`(国交省の業者一覧の `crawl-run` と同じ作り)。
  - 合言葉が未設定なら 503(休眠)。違えば 403。
  - サーバー内の決まったフォルダ(`MANSION_CATALOG_DIR`)の `buildings-*.jsonl` を読む。
  - 500件ずつ `(source, source_id)` で入れる/更新する。
  - ⚠集める側のフォルダはアプリから読めない(DynamicUser の私有フォルダ)。読み込む前に、root で決まったフォルダへ写す(反映手順に書く)。
  - 返すのは件数だけ(入れた・更新した・読めなかった行の数)。ログにも件数とコードだけ。
- 取り直したときは**名簿だけ**を更新する。すでにできている棟の値は変えない(社内で直した値を守る)。
- 文字を数字に直す処理は純関数 `src/lib/mansion-catalog/parse.ts`(DB を触らない)。
  - `2026年9月` → 2026, 9
  - `地上10階建 地下1階` → 10, 1
  - `155戸` → 155
  - `不明`・`総戸数不明`・読めない形 → null

## 5. 名簿から棟にする(取り込み) — 1か所の関数に集める

`adoptCatalogBuilding(tx, catalogId, userId)` を `src/lib/mansion-catalog/adopt.ts` に置く。どの入口もこれを通す。

1. 名簿の建物の鍵 `(area_key, name_key)` でロックを取る(`applyBuildingLink` と**同じロックの鍵**
   `buildingLinkLockKey`)。これで、同時に来た物件の保存と取り込みが同じ棟を2つ作らない。
2. ロックのあとに読み直す:
   - その名簿の建物を `catalog_id` に持つ棟があれば、それを返す(もう棟になっている)。
   - 同じ鍵の自社の棟が**ちょうど1つ**で `catalog_id` が空なら、その棟に `catalog_id` を付け、
     **空いている欄だけ**を名簿の値で埋めて返す。
   - 同じ鍵の自社の棟が2つ以上なら、どれにも付けない。新しい棟も作らず「選んでください」を返す
     (人が選ぶ。勝手にどれかへ寄せない)。
   - どれも無ければ、名簿の値を入れた棟を作る(名前・住所・竣工年月・階数・戸数・構造・管理会社・`catalog_id`)。
3. 監査ログ `building.catalog_adopt`(棟の id と名簿の id だけ・住所は書かない)。

## 6. 入口ごとの動き

### 6.1 物件の保存(自動のつなぎ込み)

`applyBuildingLink` が「新しい棟を作る」と決めたとき(`create`)だけ、作る前に名簿を見る。

- 同じ鍵の名簿の建物が**ちょうど1件**で、まだ棟になっていない → その値を入れて棟を作る(`catalog_id` 付き)。
- 0件・2件以上 → これまでどおり、名前と住所だけの棟を作る(名簿の値は入れない)。
- ロックは今のロックの中でそのまま行う(同じ鍵なので取り直さない)。

これで、貼り付け・Excel・CSV・新規登録・編集のどの入口から入れても、同じように埋まる
(全部の入口が `applyBuildingLink` を通るため)。

### 6.2 物件名の候補(`GET /api/buildings/suggest`)

- 今の候補(自社の棟)のあとに、名簿の建物を最大5件足す。
  - 同じ名前+同じ丁目 → 同じ名前 → 名前の一部が一致、の順に並べる。
  - すでに棟になった名簿の建物は出さない。
- 返す住所は今と同じく**町丁目まで**(番地はURLにもログにも載せない決まりを守る)。
  竣工年・階数・戸数も一緒に返し、候補の行に小さく出す。
- 名簿の候補を選ぶと、**建物名がその表記で入るだけ**(選び方は「自動」のまま)。保存したときに 6.1 で
  名簿の値の入った棟ができる。
  - ⚠(2026-10-18 計画時に変更)選んだ時点で棟を作ると、登録をやめたときに空の棟が残るため。
  - 丁目が違う名簿の建物には「丁目が違います」を付ける(その場合、保存しても名簿の値は入らない=6.1 の一致条件)。

### 6.3 「マンション棟」の一覧の検索窓(`GET /api/buildings?keyword=`)

- 2文字以上で探したときだけ、自社の棟の段の下に「名簿にあるマンション」の段を出す(最大20件)。
- 1件ごとに 名前・住所・竣工年月・階数・戸数・管理会社 と、[マンション棟に登録] のボタンを出す。
- ボタンは物件を書き込める人だけ(`property:write`)。押すと 6.2 と同じ adopt を呼び、できた棟の画面へ移る。
- 何も入れずに開いたときは、これまでどおり自社の棟だけ。

### 6.4 今ある16棟

- 読み込みのあとで1回、今ある棟のうち `catalog_id` が空のものを、同じ鍵の名簿の建物が**ちょうど1件**なら
  5. の 2 と同じやり方でつなぐ(空いている欄だけ埋める)。合言葉つきの口の後処理として行う。

## 7. 権限

- 名簿を読む(候補・検索) … `property:read`(棟と同じ)。
- 名簿から棟にする … `property:write`(棟を作るのと同じ)。
- 名簿の読み込み … 合言葉(人の権限ではない)。

## 8. 失敗と例外

- 名簿の行が読めない(JSONとして壊れている・名前か住所が無い) → その行は飛ばして数える。
- 名簿が空・読み込み前 → 候補や検索に名簿の段が出ないだけ。保存は今までどおり。
- adopt で名簿の建物が見つからない → 404。同じ鍵の棟が複数 → 409「選んでください」。

## 9. テスト

- `parse.ts`: 実データにある形を全部(竣工・階建・戸数・構造・不明)。
- adopt: もう棟がある/自社の棟1つにつなぐ(空欄だけ埋まる・手で入れた値は変わらない)/複数で止まる/新しく作る。
  - 物件の保存と取り込みが同時に来たときの順番を総当たり(同じ棟が2つできない)。
- `applyBuildingLink`: create のとき名簿1件なら埋まる・0件/2件なら今まで通り。
- 候補と検索: 名簿の段の並び・棟になったものを出さない・住所は町丁目まで・権限。
- 読み込みの口: 合言葉なし=503/違う=403/件数だけ返す/同じ行を2回入れても1件。

## 10. この設計でやらないこと

- 毎月の取り直し(新しい建物の追加)の自動化 … 一覧を取り終わってから、別に決める。
- 取りこぼしを埋めるための取り直し … 件数の差を見てから運用で行う。
- 名簿を地図に出す・DMの対象さがしに使う … 今回は入れない。
- 社内の棟の値を、名簿の新しい値で上書きすること … しない。
