# 販売図面 F3 — 物件データに「販売」の欄を作る(設計)

作成日: 2026-09-19 / 前段: 第①段(消費者向けひな型)・仕上げ段・第②段(写真) / 第③段(規約必須項目)は発注者判断で見送り

## 1. 目的

販売図面を作るたびに、価格・交通・面積・築年月などを**毎回手で入力し直している**。これらを物件の正式なデータとして持たせ、図面を作るときに自動で入り、図面で直した値は物件にも戻るようにする。

将来の一覧表示・CSV・絞り込みの土台にもなるが、**この段では作らない**(§3)。

## 2. 発注者判断

### 2026-09-14

1. 持たせ方 = **案1「物件の正式なデータ(列)」**。物件編集画面に「販売」区分を新設する。案2(前回入力を丸ごと覚える)・案3(併用)は不採用。
2. 図面の作成画面で入れた/変えた値は**物件にも保存する**(「物件にも保存する」チェック・既定ON・外せばその図面だけの値)。変更履歴に残す。
3. 範囲 = 主要項目(価格・消費税・交通・土地面積(公簿/実測)・建物面積(延床)・築年月・構造・地上/地下階・駐車場・総戸数・想定利回り・満室想定収入)+ 区分マンションの既存欄(専有面積・バルコニー・間取り・向き・所在階・管理費・修繕積立金)を物件編集画面から直せるようにする。取引態様・報酬・広告・担当者・取引士・特記・備考は図面側に残す。

### 2026-09-19

4. 区分マンションで**棟が共有している項目**(構造・地上階・地下階・総戸数・築年月)を図面で変えたら、**棟に保存する**。保存前に「同じ棟の◯部屋にも反映されます」と表示する。
   - ⚠**2026-09-20 実装確定(Task10 レビュー対応)**: 実際に棟へ保存する(=図面から変更できる)のは**築年月と地下階の2項目だけ**。構造・地上階・総戸数は既存設計どおり**棟の値が正**のままとし、F3では図面からの変更対象に含めない(この判断4は当初の意図を残すが、実装範囲は §4.4 の注記を正とする)。理由と詳細は §4.4 参照。
5. この段の範囲は**入力と図面まで**。一覧表示・CSV・絞り込みは次の段。
6. 保存済みの図面は**作った時点の写し**のまま。物件を後から直しても図面は変わらない。作り直せば最新の値が入る。
7. 作り方 = **物件に列を足す(A)** + **図面を作る処理の中で物件・棟も一緒に保存する(P)**。

## 3. 範囲外

- 物件一覧への表示、CSV出力・取込、価格帯や面積での絞り込み(次の段)
- 保存済みの図面へ物件の最新値を取り込むボタン(次の段以降・必要になったら)
- 図面の編集画面(エディタ)の表の文字から物件へ戻すこと(§7 の理由で恒久的に行わない)
- ㎡単価・坪単価(価格と面積から計算する値のため持たない)
- 規約必須項目(第③段・見送り済み)
- §4.4 の対応表に無い図面の項目は**図面だけに残す**。例: 私道負担・地目・地勢・セットバック・建築条件・都市計画・地域地区・設備条件・現況・引渡時期・備考・取引態様・報酬・広告・担当者・取引士・特記事項
- 戸建の「間取り」(`layout`)。物件の `layoutType` は区分の欄として使っており、戸建へ広げるかは次の段で判断する
- 「物件種目」(`propertyType`・新築/中古など)。DB の種別(`propertyType` enum)とは軸が違うため自動反映せず、図面の手入力のままとする(2026-09-14 の判断を踏襲)

## 4. データ設計

### 4.1 Property に足す列(区分マンション以外で使う)

|---|---|---|---|---|---|
| `salePrice` | `sale_price` | `Decimal(12,1)?` | 万円 | 価格 | 全種別 |
| `saleTaxType` | `sale_tax_type` | `String?` | — | 消費税 | 区分・戸建・一棟 |
| `saleTaxAmount` | `sale_tax_amount` | `Decimal(12,1)?` | 万円 | うち消費税 | 区分・戸建・一棟 |

| `landArea` | `land_area` | `Decimal(10,2)?` | ㎡ | 土地面積 | 土地・戸建・一棟 |
| `landAreaMethod` | `land_area_method` | `String?` | — | 面積計測方式(公簿/実測) | 土地・戸建・一棟 |
| `totalFloorArea` | `total_floor_area` | `Decimal(10,2)?` | ㎡ | 建物面積(延べ)/延床面積 | 戸建・一棟 |

すべて null 許容・既定値なし(既存行は空で始まる)。

### 4.2 Building に足す列(区分マンション用)

| Prisma | 列名 | 型 | 単位 |
|---|---|---|---|
| `builtMonth` | `built_month` | `Int?` | 月(1〜12) |
| `basementFloors` | `basement_floors` | `Int?` | 階 |

構造(`structureType`)・地上階(`totalFloors`)・総戸数(`totalUnits`)・築年(`builtYear`)は既存の列を使う。

### 4.3 既存の列を使う項目(列を足さない)

専有面積 `exclusiveArea` / バルコニー面積 `balconyArea` / 間取り `layoutType` / 向き `orientation` / 所在階 `floorNo` / 管理費 `managementFee` / 修繕積立金 `repairReserveFee`。データはあるが**物件編集画面に出ていない**ため、§5.1 で「販売」区分に出す。

### 4.4 図面の項目 → 保存先の対応

| 種別 | 図面の項目(field-model の key) | 保存先 |
|---|---|---|
| 区分(`apartment_unit`/`unit`) | `price` `tax` `taxAmount` `access` `parking` | Property(新しい列) |
| 区分 | `exclusiveArea` `balconyArea` `layout` `balconyDir` `floorNo` `managementFee` `repairFee` | Property(既存の列)※1 |
| 区分 | `basementFloors` `builtYearMonth` | **Building**※2 |
| 土地(`land`) | `price` `access` `landArea` `areaMethod` | Property |
| 戸建(`house`) | `price` `tax` `taxAmount` `access` `landArea` `areaMethod` `buildingArea` `structure` `aboveFloors` `basementFloors` `builtYearMonth` `parking` | Property |
| 一棟(`apartment_building`/`apartment_block`) | 戸建と同じ + `totalFloorArea` `totalUnits` `grossYield` `expectedIncome` | Property |

⚠ 一棟の物件が棟(Building)に紐づいていても、**棟へは保存しない**(棟へ保存するのは区分だけ)。一棟は物件1件がその建物を指すため。

※1 **区分マンションの部屋7項目(専有面積・バルコニー面積・間取り・向き・所在階・管理費・修繕積立金)は、図面の作成画面では「物件の値の自動表示(編集不可)」のままとする**。図面上から手入力で上書きすることはできず、値を直すのは物件編集画面(§5.1)から行う。書き戻しの規則(`property-writeback/build-writeback.ts` の規則表)自体は API 経由でこれらの列へ到達する一般化として残す(将来 API を直接叩く経路や別の入力元が増えても同じ規則で読み取れるようにするため)。

※2 **区分マンションの構造・地上階(`totalFloors`)・総戸数は、既存設計どおり棟の値が正で、図面からは変更できない(F3ではこの3項目を対象外のまま維持する)**。図面から棟へ実際に保存されるのは**築年月と地下階の2項目だけ**。作成ダイアログが「同じ棟の◯部屋にも反映されます」と案内するのもこの2項目を触ったときだけ(§5.2)。§2 判断4 の原文は構造・地上階・総戸数も含めて書かれているが、実装確定時にこの2項目へ絞った(2026-09-20)。

### 4.5 migration

列を足すだけ(additive)。既存データの書き換えなし。enum の追加なし。**元に戻すときはアプリだけ戻せばよい**(列は残しても害がない)。

## 5. 画面

### 5.1 物件の編集画面に「販売」区分を新設

- 物件の種別に合う欄だけを出す(§4.4 の対応表と同じ)。
- 区分マンションは、部屋の欄(専有面積・バルコニー面積・間取り・向き・所在階・管理費・修繕積立金・価格・消費税・交通・駐車場)をここで直せる。
- 区分マンションの**棟の項目**(構造・地上階・地下階・総戸数・築年月)は**読み取り専用**で表示し、「棟の画面で直す」リンクを付ける。1部屋の画面から棟全体の値が変わるのを防ぐため。
- 棟の編集画面に「築月」「地下階」の欄を足す。

### 5.2 図面の作成画面

- 物件(区分は棟も)に値があれば、今までどおり最初から入っている。§4.1 で足した欄も対象。
- ボタンの上に **「入れた値を物件にも保存する」チェック(既定ON)**。
- 区分マンションで**棟の項目を変えたときだけ**、チェックの下に補足を出す: 「構造・築年月などは棟『◯◯マンション』の値です。同じ棟の N部屋 にも反映されます」(N = 同じ棟に属する物件数)。
- 保存するのは**物件(棟)の今の値から変わった欄だけ**。触っていない欄では変更履歴を作らない。

### 5.3 作成後の知らせ

エディタを開いた直後、画面上部に1行で結果を出す(閉じられる)。

- 保存できたとき: 「価格・交通・築年月を物件に保存しました」(項目名を並べる)
- 保存しなかったとき: 理由を出す。**項目名だけを出し、入力された文字そのものは画面に引用しない**(外部由来の文字を画面に出さない方針・`redaction-allowlist-not-pattern` と同じ考え方)。
  - 「他の人が先に物件を更新していたため、物件には保存していません(図面は作成済みです)」
  - 「価格・築年月は数値や年月として読み取れなかったため、物件には保存していません」(読み取れなかった項目名を並べる。範囲外・非整数(§8/§6.1)も同じ扱い)

## 6. 保存の流れ

図面作成 API(`POST /api/properties/[id]/sales-sheets/new`)の中で、1つのトランザクションとして行う。

1. 物件の行を**先にロック**する(区分なら棟の行も)。物件配下を書き換えるときは親の物件行を先にロックする既存の決まりに合わせる。
2. 図面(`SalesSheetDesign`)を作る。
3. チェックが入っているときだけ、**変わった欄だけ**を物件・棟へ書き、`ChangeLog` に1欄1行を残す(`targetTable` = `properties` / `buildings`、`source` = `manual`)。
4. まとめて確定する。途中で失敗したら全部取り消す(図面だけできる/物件だけ変わる、は起きない)。

### 6.1 うまくいかないときの決まり

| 起きること | どうする |
|---|---|
| 作成画面を開いている間に他の人が物件(棟)を更新した(version 不一致) | **物件・棟には保存しない。図面は作る。**理由を §5.3 で出す |
| 数値として読めない値(「応談」など) | その欄だけ物件に保存しない。図面には入力どおり出る |
| 年月として読めない築年月(「築15年」など) | 築年・築月を物件に保存しない。図面には入力どおり出る |
| 図面で欄を空にした | 物件の値は**消さない**(空は「変更なし」として扱う) |
| データベースの障害 | 全部取り消し。「作成できませんでした」と出す |

### 6.2 権限

- 図面作成・物件への保存とも `property:write`(今と同じ)。持っていない人は作成自体ができない。
- 担当物件しか触れない担当者(`field_staff`)の範囲も既存の規則のまま。区分の棟へ書くときも、その物件が範囲内であることを同じ規則で確かめる。

## 7. 物件へ戻すのは作成画面からだけ

エディタで直せるのは図面の表の**文字**(例: 「125.30㎡(実測)」)であり、元の欄との対応が取れない。文字から数値へ戻すと誤った値が物件に入る恐れがあるため、**エディタからの書き戻しは行わない**。

## 8. 値の読み取り規則(純関数)

図面の入力は自由な文字。物件へ保存するときだけ次の規則で読み取る。読み取れない値は**保存しない**(図面の表示は入力のまま)。

- **数値**: 全角数字を半角にし、カンマと前後の空白を除く。単位の文字(「万円」「㎡」「%」「％」「階」「戸」)が末尾に付いていれば取り除く。残りが `^\d+(\.\d+)?$` なら数値として採用。それ以外は読み取れない。
- **築年月**: 次の書き方を読み取る。
  - 西暦: `2008年3月` / `2008/3` / `2008-03` / `2008年3月1日`(日は捨てる) / `2008年`(月なし=年だけ保存)
  - 和暦: `平成20年3月` / `昭和58年` / `令和2年5月`(昭和 = 1925+N、平成 = 1988+N、令和 = 2018+N)
  - 月は 1〜12 の範囲のみ。範囲外は月なしとして扱う。
  - 上のどれにも当てはまらない(「築15年」「新築」など)は読み取れない。
- **選択肢の項目**(消費税・面積計測方式・構造・駐車場): 図面の選択肢(`option-master`)にある値だけを保存する。自由入力で選択肢に無い値は保存しない。

## 9. テスト

- **読み取り規則**(§8)は画面から切り離した純関数にして、読める書き方・読めない書き方・境界(全角・カンマ・単位付き・月が13・和暦の元号境界)を固定する。
- **保存の流れ**は作成 API のテストで確かめる: 変わった欄だけ保存される/空欄では消えない/version 不一致では物件を保存せず図面はできる/区分では棟に保存される/一棟では棟に保存しない/権限のない人は作成できない/`ChangeLog` が1欄1行で残る/失敗時に全部取り消される。
- **画面**は、種別ごとに「販売」区分へ出る欄が正しいこと、区分で棟の項目が読み取り専用になっていること、チェックの既定がONであることを確かめる。
- 出す前に `npx tsc --noEmit` / `npx vitest run`(全体) / `npx eslint <変更ファイル>` / `npm run build` を通す。

## 10. 本番に出すときの注意

- **この段で唯一のデータベース変更(列の追加)がある**。適用は反映手順の `prisma migrate deploy` で行う。
- 既存データは書き換えない。足した列は空で始まり、図面作成や編集画面の入力で埋まっていく。
- 元に戻すときはアプリだけ戻せばよい(列を残しても既存の動きに影響しない)。
- 画面を開いたままの人は、反映後に一度読み込み直しが必要。
