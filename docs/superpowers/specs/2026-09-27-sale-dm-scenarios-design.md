- 日付: 2026-09-27

- 位置づけ: 2026-09-08 設計書(`2026-09-08-sale-dm-lp-autobuild-design.md`)の「第2段階=シナリオ台帳」を具体化したもの
- 前提(本番): 第1〜4段(LP型・写真と図・公開LP・申込フォーム・メール通知)は反映済み。送付済みの宛先は0件

## 0. 発注者と確定した方針(再提案しない)

1. **1回の発送の中に相続と空き家が混ざることがある** → 発送単位ではなく**宛先ごと**に種類を決め、その種類の手紙とLPを組にして付ける。
2. 宛先の種類は**自動で決め、あとで直せる**。直す場所は**物件の「DMの種類」欄**(空欄=自動)。翌月以降の発送にも効かせるため、発送ごとの宛先一覧ではなく物件に持たせる。
3. 手紙の文面とLPは**種類ごとに一度作って使い回す**(台帳)。文面を直すと、直した後に作る発送から新しい文面になる。**送った分は送ったときの内容のまま**。
4. 方式は**案A=発送を作る瞬間に台帳を発送へ写し取る**。台帳を宛先から直接参照する方式(案B)は、公開ページ・集計・凍結を作り直すことになるため採らない。
5. 同じ種類の中のA/B(2本目)は作らない(2026-09-16 の決定どおり)。
6. 今あるキャンペーン(本番で下書き102件)は今の作りのまま残す。種類の仕組みは新しく作る発送から。

## 1. 現状(2026-09-27・origin/main `fd4181b1`)

- `DmCampaign` の配下に `DmVariant`(手紙の型)と `DmLpVariant`(LPの型)が**別々**にある。
- 作成(`POST /api/properties/sale-dm/campaigns`)で型「A」を1つ作り、全宛先に付ける。LP型は付けない(NULL)。
- 割り当て(`POST campaigns/[id]/assign`)は `assignCrossEvenly`(`src/lib/sale-dm-letter/assign.ts`)で**手紙×LPの全組み合わせを均等**に割り振る。手での割り当て(`applyManualAssignment`)もある。→ **1つの発送に相続の手紙と空き家のLPがあると、相続の手紙に空き家のLPが付き得る**(本件の問題)。
- 手紙: 指示文(`prompt`)→外部AI→貼り戻し(`template` PUT で `bodyTemplate`)→差し込み(`apply` で `expandLetterTags`)。
- LP: 同様に貼り戻し(`rawTemplate` と切り分けた `headline/lead/bodyText/faqJson`)。写真と図は `DmLpVariantMedia`(写真は全体共通のライブラリ `DmLpAsset` を指す)。LPは閲覧のたびに組み立てる。
- 凍結(`freeze.ts`): `templateFrozenAt` または配下に confirmed/sent があれば凍結。
- 型を写す機能は無い(同じ発送の中で手紙の設定をLPの入力欄へ写す `copyFromDm` だけ)。
- 導入ルート: `Property.introductionRoute`(文字列)。受付帳取込=`reception_csv`、現地調査からの物件化=`field_survey`、貼り付け=`web_inquiry`。物件編集画面には欄が無い。

## 2. 使う人から見た流れ

### 2.1 台帳の登録(管理者・最初に一度)
- 設定に画面「DMの種類」を新設する。最初から**相続**と**空き家**の2件を用意しておく(中身は空)。
- 種類ごとに次の2つを登録する。
  - **手紙の文面**: 書き方の設定(デザイン・語調・長さ・訴求・強さ・追加の指示)→指示文をコピー→外部AI→貼り戻し。今の型の画面と同じ操作。
  - **LPのページ**: 同じく貼り戻し。写真と図の割り付けも今と同じ操作(写真は「LPの写真」ライブラリ)。プレビューもある。
- 管理者は種類を増やせる(例: エリア別)。自動で振り分けるのは相続と空き家だけで、増やした種類は物件の欄で手で付ける。
- 使ったことのある種類は消せず、「使わない」にできるだけ(過去の成績表の行名を残すため)。使ったことのない種類は消せる。**ただし最初から入っている相続と空き家(自動の振り分け先=`auto_key` あり)は、使ったことが無くても消せない**(消すと受付帳取込・現地調査の物件の自動の行き先が永久に無くなり、戻す手段も無いため)。止めたいときは「使わない」にする。
- 台帳には凍結が無い。いつでも直せる(発送側は写しなので影響しない)。

### 2.2 物件の「DMの種類」欄
- 物件の編集画面に選択欄「DMの種類」を足す。選択肢は「自動(空欄)」と台帳の有効な種類。
- 物件の詳細画面にも、今の種類(自動の場合は「自動: 相続」のように決まり方も)を表示する。

### 2.3 発送の作成
- 今の作成画面に「**既定の種類**」の選択を1つ足す(導入ルートで決まらない物件に使う)。
- 作成した瞬間に、宛先ごとに種類が決まり、**その種類の手紙の型とLPの型が組で付き、本文も差し込まれる**。型作り・貼り戻し・割り当ての手間は無くなる。
- 登録が足りない種類が混ざっていたら、作る前に止める(§4)。
- 発送画面の宛先一覧に「種類」の列を出す。手で直す操作は「**種類を変える**」だけ(手紙もLPも一緒に切り替わる)。
- 成績表は種類の名前で行が分かれる(型の名前=種類の名前にするので、今の表がそのまま使える)。

### 3.2 種類の決め方(純関数・`src/lib/sale-dm-letter/scenario-resolve.ts`)
順に見て最初に決まったもの:
1. 物件の `dm_scenario_id`(有効な種類なら)
2. 導入ルート: `reception_csv` → `auto_key=inheritance` / `field_survey` → `auto_key=vacant`。**その種類が「使わない」なら、ここでは決めずに 3 へ進む**(自動の振り分けでも「使わない」種類は使わない)
3. 発送の既定の種類
- 物件の欄が「使わない」になった種類を指していたら、2 以降で決める(黙って古い種類で送らない)。
- 原則: **どの段でも「使わない」種類は返さない**。3 の既定の種類は作成時に有効性を検査済み(§4)。
- 入力=物件の欄・導入ルート・既定・台帳の一覧 / 出力=種類の id と「どの段で決まったか」。DB を読まない。

### 3.3 発送の作成(既存の作成処理を広げる)
既存の1つのトランザクションの中で、今の宛先作成の手前で行う。
1. 既定の種類が指定されていれば「種類つきの発送」として作る。指定が無ければ今までどおり(型「A」1つ・LP型なし)=**古い呼び出しは挙動不変**。
2. **(順序の注意)物件のロックが先・台帳が後**: 今の作成処理どおり所有者→物件を押さえた**後で**台帳を押さえる(§3.3.1 の全体順)。物件を先に押さえれば、物件の欄の保存(物件 `FOR UPDATE`)は待たされるので、物件が指している種類は押さえる前に確定済み=台帳を押さえたときには必ず存在する。**それでも物件の欄が指す id が押さえた台帳の中に見つからないときは、自動・既定に落とさず 409 で止める**(黙って別の種類にしない=最後の防御)。台帳の新規追加と物件の選択が同時に走るケースのテストを加える。
   **台帳の行をまとめて押さえてから種類を決める**: 台帳の全行(種類は数件しかない)を1本の問い合わせで `FOR SHARE`・`ORDER BY id` で押さえる。写す側は読むだけなので `FOR SHARE`(作成どうしは互いに待たない=逆順の取り合いによるデッドロックも起きない)、書く側(§3.3.1)は `FOR UPDATE` なので、押さえている間は台帳の中身も「使う/使わない」も変わらない。**候補を先に絞ってから押さえると**、ロック前は「使わない」だった上位の候補(物件の欄・自動の種類)が押さえる前に「使う」に戻され、下位の既定の種類で作ってしまう隙間が残るため、全行を押さえてから決める。
3. 押さえた状態で、宛先の物件ごとに §3.2 で種類を決める(共有者が何人いても物件単位で1つ)。**判定に使う物件の `dm_scenario_id` と導入ルートは、物件をロックした後にトランザクションの中で読み直した値を使う**(今の作成処理はトランザクションの前に物件を読み、ロック後に読み直すのは所有者のつながりだけ=その値を使うと、ロック直前に変わった種類が反映されない)。台帳の一覧もロック後に読んだものを使う。同時更新(物件の種類の変更・台帳の「使わない」⇄「使う」)のテストを加える。
4. §4 の検査に通らなければ作らずに返す。
5. 種類ごとに、台帳から `DmVariant` を1つ(label=種類名・`scenario_id` 付き・`body_template`/`prompt_text` を写す)、LPの文面があれば `DmLpVariant` を1つ(同じく写す)と `DmLpVariantMedia` を写す。
6. 各宛先に、自分の種類の手紙の型と LP の型を付け、本文を `expandLetterTags` で差し込んで作る。**差し込みの後の検査も今の `apply` と同じにする**(`hasUnresolvedTag` と `validateLetterBody`): 住所が読めない・物件種別が空などで差し込めない宛先は、**本文を空のまま下書きで作り**、作成の結果に「本文を差し込めなかった宛先 N件」を返して発送画面に出す(物件の情報を補ってから、今ある「差し込み」ボタンで入れ直す)。未解決のタグを含む本文は保存しない。住所なし・物件種別なしの両方をテストする。
- 50通の上限・物件を分けない切り詰め・共有者の扱い・冪等性キー・所有者の再確認は今のまま。
- ロックの順序は今の作成処理の順を守り、台帳行は最後に取る(既存の順序に新しい段を足すだけ)。

### 3.3.0 作成と「種類を変える」が共通で通る手順(片方だけ守りが漏れないように1か所にまとめる)
次の3つは関数として1つずつ作り、**作成(§3.3)と種類を変える(§3.4)の両方が必ずこれを呼ぶ**(走査型テストで呼び出しを固定する)。
1. **準備の検査** `checkScenarioReady(台帳の行)`: 手紙の文面が無い→止める(§4)/LPの文面が無い→LPなしで進む(注意を返す)/使わない→止める。
2. **写す** `copyScenarioIntoCampaign(発送, 台帳の行)`: その発送にその種類の写しがまだ無ければ、手紙の型1つ+(LPの文面があれば)LPの型1つと写真と図を作る。有ればそれを返す。**写す列は台帳の手紙・LPの列の全部**(対応表を1つの定数にして、列の足し忘れをテストで検出する):
   - 手紙: `design_template`→`designTemplate`(印刷の型=印刷処理が読む)・`tone`・`length`・`appeal`・`strength`・`extra_instruction`・`letter_prompt_text`→`promptText`・`letter_body_template`→`bodyTemplate`。`label`=種類名、`lpUrl`=NULL。
   - LP: `lp_tone`・`lp_length`・`lp_appeal`・`lp_strength`・`lp_prompt_text`・`lp_raw_template`・`lp_headline`・`lp_lead`・`lp_body_text`・`lp_faq_json`。`label`=種類名。
   - 写真と図: `dm_scenario_media` の全行(`slot`・`heading`・`sort_order`・`asset_id`/`figure_kind`)。
   - テスト: 台帳のすべての列に既定と違う値を入れて写し、写しの全列が一致すること(発送の既定値や空で埋まっていないこと)。
3. **宛先に付けて差し込む** `attachAndExpand(宛先, 写し)`: 手紙の型と、**その種類の期待されるLP**(下の組の決まり)を付け、`expandLetterTags` の後に `hasUnresolvedTag`/`validateLetterBody` で検査。差し込めない宛先は本文を空のまま下書きにし、件数を返す(作成でも種類を変えるでも同じ報告)。**この件数と注意(LPなしの種類など)は、作成の応答だけに頼らない**: ①作成の結果は冪等性の控え(`filterSnapshot.__result`)にも保存し、同じ冪等性キーでの再送(応答が失われた後のやり直し)でも同じ注意が返る(再送のテストを加える)②発送の画面は開くたびに DB から「本文が空の下書き N件」「LPの無い種類」を数えて表示する(応答を見逃しても画面で気づける)。

**組の決まり(正しい組の定義)**: 種類つきの発送の宛先は、手紙の型の `scenario_id`=S のとき、LP の型は「**その発送で S から写した LP の型**」でなければならない。**S に LP の写しが無ければ NULL** でなければならない(LPの文面が無い種類の正規の状態=§4)。単純な「両方の `scenario_id` が等しい」ではない(LP なしの正規の組を誤って拒否するため)。判定関数 `isValidScenarioPair(発送, 手紙の型, LPの型)` はこの定義で作り、組を書き換えうる全経路が使う。総当たりのテストに「LP なしの種類」を入れる。

**権限の再確認**: 現場担当(field_staff)は担当範囲の物件だけ。**物件をロックした後に、その物件がまだ担当範囲(`createdBy`/`assignedTo`)にあるかを読み直してから**書く(ロック前の確認のあとで担当が付け替えられた場合に書かない)。作成・種類を変える・物件の欄の保存の3経路すべて。同時の付け替えのテストを加える。

### 3.3.1 台帳の行ロック(写しが混ざらないための決まり)
- **台帳を書き換える経路はすべて、先に台帳の行を `FOR UPDATE` で押さえる**: 名前・設定の PATCH / 手紙の貼り戻し / LPの貼り戻し / 写真と図の割り付け(`dm_scenario_media` の置き換え) / 使わないにする / 削除。
- **台帳を写す・参照する経路はすべて、写す前に台帳の行を `FOR SHARE`(`ORDER BY id`)で押さえ、その中で手紙・LP・写真と図・有効性をまとめて読む**: 発送の作成(§3.3 の 2・全行)・「種類を変える」(移り先の行)・物件の欄の保存(選んだ行)。読む側どうしは待たず、書く側(`FOR UPDATE`)とだけ直列になる。
- これで「手紙は新しい版・写真は古い版」のような混ざった写しは作れない。
- **全体のロック順(既存の順を実測して、その間に新しい段を差し込む=2026-09-27 に sale-dm の全 route の FOR UPDATE を確認)**:
  **発送の行(`dm_campaigns`・新設の段・今は誰も取っていない)→ 手紙の型(`dm_variants`・id順)→ LPの型(`dm_lp_variants`・id順)→ 所有者(FOR SHARE・id順)→ 物件(id順)→ 宛先(`dm_recipient_drafts`・id順)→ 台帳(`dm_scenarios`)→ 写真(`dm_lp_assets`)**
  - 既存の confirm / mark-sent / assign / 型の PATCH は「型 → 物件 → 宛先」の順(**親が先・子が後**)。新しい経路もこれに従い、**宛先を物件より先に取らない**。
  - 台帳と写真は最後。台帳の書き手(§3.3.1)は台帳 → 写真だけを取り、発送・型・物件・宛先を取らないので、写し手と輪にならない。
  - 物件の編集で種類を選ぶときは「物件 → 台帳」(§3.6)。これも同じ向き。
  - 「種類を変える」の順: 発送の行 → 今の型と移り先の型(既にあれば・id順)→ 物件 → 宛先 → 台帳 → (無ければ写して作る)。
  - 既存のロック順テスト(経路をまたいだ順序の検査)に、新しい経路(作成の拡張・種類を変える・物件の種類の保存・台帳の書き手)を加える。

### 3.4 組がずれない守り
- **サーバーで拒否**: 種類つきの発送では、§3.3.0 の組の決まりに合わない保存を 409 で断る(作成・割り当て・種類の変更のすべての経路で同じ判定関数を使う)。
- **宛先1件の更新(既存の `PATCH /api/properties/sale-dm/drafts/[id]`)**: 今は `variantId` だけを差し替えられ、LP の型は残る=組がずれる抜け道。種類つきの発送では `variantId` の指定を 409 で断る(本文・差し込み値の手直しは今のまま許す)。種類の切り替えは「種類を変える」だけを通す。
- 組を書き換えうる経路の一覧(この一覧のすべてに判定を入れ、走査型テストで新しい経路の追加漏れも検知する): 作成 / `assign` / `drafts/[id]` PATCH / 種類を変える / 型の削除(配下の宛先の付け替えを伴う場合)。
- 種類つきの発送では `assign`(全組み合わせで均等・手での割り当て)を 409 で断り、画面にもボタンを出さない。
- 種類つきの発送で、型の追加・削除(手紙もLPも)は断る。**台帳から写した型(`scenario_id` あり)は、型の PATCH をまるごと断る**(手紙の型・LPの型の両方)。名前を変えると成績表の行名=種類名が崩れ、`lpUrl`(型ごとの外部LP)を入れると公開の `/t/<token>` が既定の転送先よりそれを優先して**種類と関係ない外部LPへ飛ぶ**、設定を変えると貼り戻した文面や写真の割り付けが消える=いずれも台帳との対応が崩れるため、1つずつ禁止項目を足すのでなく**写した型は PATCH 不可**と決める。写した型で許すのは、今の凍結の決まりの範囲での**文面の貼り直し**と**LPの写真と図の割り付け**だけ(この発送だけの手直し用)。
- 写すときも `lp_url` は NULL のまま(台帳に外部LPの欄は持たない)。LPの文面が無い種類の宛先は、既定の転送先(会社のホームページ)へ行く(§4)。型の文面の貼り直しは今の凍結の決まりのまま許す(この発送だけの手直し用)。
- 新しい操作「**種類を変える**」(`POST campaigns/[id]/properties/[propertyId]/scenario`): **物件単位**で行う(共有者が複数いても1物件=1種類の決まりを守るため、その発送のその物件の宛先を全員まとめて切り替える)。1人でも送付済みがいれば 409(一部だけ変えると同じ物件で種類が割れる)。確定済みは下書きに戻して切り替える。**下書きに戻す前に、移動元の手紙の型・LPの型を、ロックを持ったまま凍結の印を立てる**(`markVariantsFrozen`/`markLpVariantsFrozen`。今の `assign` と宛先1件の更新と同じ=最後の確定済みが抜けると「確定済みの宛先がある」という凍結の根拠が消え、承認済み・印刷済みかもしれない文面が貼り直せてしまうため)。**同じトランザクションで物件の `dm_scenario_id` にも選んだ種類を書く**(方針0-2=直す場所は物件=翌月以降の発送にも効かせる。発送の画面で直しても物件の欄で直しても結果が同じになる)。したがってこの操作には売却DMの権限に加えて**その物件を編集できる権限**が要る(無ければ 403)。操作の記録は物件の種類の変更としても残す(**AuditLog に加えて、物件の変更履歴 `ChangeLog` にも `dmScenarioId` の変更前→変更後を1行**=物件の編集画面から直したときと同じく、物件詳細の「履歴」に出る。値は種類の id、表示は種類名)。**物件を書く以上、物件の編集と同じ決まりに従う**(編集中の鍵=実績145・147): ①同じトランザクションで `Property.version` を1つ進める(開いたままの古い物件画面が保存したとき 409 になり、直した種類を黙って元に戻さない)②他の人が有効な編集中の鍵を持っていれば 423 `EDIT_LOCKED`(`PATCH /api/properties/[id]` と同じ判定関数)。既存の「版番号を進めない書き込み」の走査テスト(`docs/superpowers/plans/2026-09-18-edit-lock-version-inventory.md`)にこの経路を加える。古い画面からの保存が 409 になるテストを加える。写す・付ける・差し込む・検査は §3.3.0 の共通の手順で行う(準備の検査で止まる種類なら、宛先には何もせず 409)。**同時に2件来ても写しが1つになるよう、発送の行を先に `FOR UPDATE` で押さえてから「有るか確認→無ければ(台帳の行を §3.3.1 のとおり押さえて)写して作る」を行う**(DB の一意索引が最後の砦)。本文は差し込み直し、状態は下書きに戻す(今、手紙の型を変えたときと同じ扱い)。
- **種類つきの発送だけの操作は、種類なしの発送では断る**: 「種類を変える」は、発送の行をロックした後に `default_scenario_id` が NULL なら 409。種類なしの発送に `scenario_id` 付きの型ができると、上の守り(assign の封じ等)が効かないまま交差の割り当てができてしまうため。「種類つきかどうか」は発送の `default_scenario_id` だけで決め(作成時に一度だけ立ち、後から変わらない)、他の経路もこの1か所の判定関数を使う。
- **選んだ種類の有効性は、その台帳の行をロックした後に確かめる(共通の決まり)**: 作成の既定の種類・物件の欄の保存(§3.6)・種類を変える、のすべてで、台帳の行を押さえた後に「有る・使う」を読み直し、違えば 409(「選んだDMの種類は使えなくなりました」)。**作成での種類の判定(§3.2)は、ロック後に読んだ台帳の行だけを使う(ロック前の一覧で判定しない=§3.3 の 2・3)**。既定の種類がロック後に無効と分かった場合は、作らずに返す(黙って別の種類に振り直さない)。画面を開いたまま「使わない」にされたケースのテストを各経路に加える。
- 判定は純関数に出し、**総当たり**で試す(種類の数 1〜3 × 宛先の並び × 登録の有無)。

### 3.5 そのまま使う部分
公開ページ(`/t/<token>`)・QRの追跡・電話タップ・申込フォーム・メール通知・凍結の決まり・成績集計・社内プレビューは、どれも発送の中の型を見る作り。写す方式なので手を入れない。

### 3.6 台帳の画面とAPI
- 画面: `/admin/dm-scenarios`(一覧・並び替え・有効/使わない・追加)と `/admin/dm-scenarios/[id]`(手紙とLPの編集・写真と図・プレビュー)。管理者だけ。サイドバーは「LPの写真」の隣。
- 手紙とLPの編集部品は、今の `variant-manager` / `lp-variant-manager` / `lp-media-panel` / `lp-preview-panel` を、親が「発送の型」でも「台帳」でも使えるように、保存先だけ差し替えられる形にする(見た目と操作を揃える)。
- API: `/api/properties/sale-dm/scenarios`(GET 一覧・POST 追加)/`[id]`(GET・PATCH・DELETE)/`[id]/prompt`・`[id]/template`・`[id]/lp-prompt`・`[id]/lp-template`・`[id]/media`・`[id]/preview`・**`[id]/image-prompt`**(写真の「画像の指示文」ボタン用。発送版は宛先の物件種別の最多を `propertyKind` に使うが、台帳には宛先が無いので `propertyKind=null`=物件種別を入れない一般的な指示文にする。`buildImagePrompt` は null を受け付け済み)。
- **種類の選択肢だけを返す口(管理者以外も使う)**: `GET /api/properties/sale-dm/scenarios/options`=有効な種類の `id`・`name`・`sort_order`・`auto_key` だけを返す(手紙やLPの文面・指示文は返さない)。使える人=物件を編集できる人(物件の欄)と売却DMを使える人(発送の既定の種類)。台帳の中身を返す `GET /scenarios`・`[id]` と書き込みは管理者だけのまま。物件の詳細の表示(「自動: 相続」)も、この口と同じ項目だけを使う。管理者以外の役割(`office_staff`・`field_staff`)で選択肢が出ることと、中身の口が 403 になることをテストする。
- 共用する編集部品は、保存・読み込み・画像の指示文・プレビューの**呼び先をまとめて外から渡す**形にする(一部だけ差し替えると、台帳の画面で発送用の口を叩いて 404 になるボタンが残る)。部品の中に発送用の URL を直接書かないことを走査テストで固定する。指示文の組み立て・貼り戻しの検査・切り分けは今の関数をそのまま使う。
- 物件の欄: 物件の更新 API の検証(`validators.ts`)に `dmScenarioId` を足す(形式だけ・NULL 可)。**存在と有効性はトランザクションの中で確かめる**: 物件の行をロックした後、選んだ台帳の行を `FOR SHARE` で読み、無い・使わない なら 409(「選んだDMの種類は使えなくなりました。選び直してください」)。画面を開いたまま消された種類・同時に「使わない」にされた種類のテストを加える。
- **操作の記録(AuditLog)**: 台帳の追加・名前や設定の変更・手紙の貼り戻し・LPの貼り戻し・写真と図の置き換え・使わないにする/戻す・削除、物件の種類の変更、宛先(物件単位)の種類の変更を、今の売却DMの操作と同じく記録する。記録するのは**操作名・台帳の id・変わった項目の名前・件数・結果だけ**で、文面や指示文の中身は入れない(個人情報や長文を記録に残さない)。

## 4. 困るケース

| ケース | 扱い |
|---|---|
| 宛先の種類の台帳に**手紙の文面が無い** | 作らずに止める。「空き家の手紙の文面がまだ登録されていません」+登録画面へのリンク(管理者にだけリンク・他の人は文章のみ=実績144 の決まり) |
| 手紙はあり、**LPの文面が無い** | 手紙だけで作る。LP型は付けない(QR は今と同じく外部LPへ転送)。作成後の発送画面に「空き家のLPが未登録のため、QRは会社のホームページへ転送されます」と注意を出す |
| 既定の種類が「使わない」 | 選べない(選択肢に出さない)。API でも断る |
| 使ったことのある種類を消す | 断る(「使わない」にする)。使ったことが無ければ消せる |
| 台帳が使っている写真をライブラリから消す | 断る(今のLPと同じ) |
| 送付後に物件の種類を変えた | 送った分は変わらない。次の発送から効く |
| 同じ物件に共有者が複数 | 物件単位で1つ=全員同じ種類 |
| 50通の上限 | 今のまま(種類が混ざっても合計50) |
| 古い発送(種類なし) | 今の画面・割り当て・集計のまま。種類の列は出さない |

権限: 台帳の編集=管理者 / 物件の欄=物件を編集できる人 / 発送の作成・種類を変える=今の売却DMの権限(現場担当は担当範囲)。

## 5. 作らないもの
- 発送をまたいだ種類別の通算成績(当面は発送ごとの表)
- 同じ種類の中のA/B
- DMの写真枠(印刷の型の変更)
- 「相続の印」など導入ルート以外の自動判定

## 6. 分け方(PR 2本・直列)
1. **PR-S1 台帳と物件の欄**: migration(表2つ+列4つ+最初の2件)・台帳のAPIと画面(編集部品の共用化を含む)・物件の欄(編集・表示)。この段では発送の作り方は変わらない。
2. **PR-S2 発送での組み付け**: 種類の決め方(純関数)・作成処理の拡張・組がずれない守り(拒否・assign 封じ・種類を変える)・作成画面の既定の種類・宛先一覧の種類の列・登録不足の案内。

## 6.1 本番への反映と戻し方
- **順序**: 各PRとも「表を足す(`prisma migrate deploy`)→ コードを入れ替える」。表は足すだけなので、表を足した後・コードを入れ替える前の間も今のコードはそのまま動く(停止は今の反映と同じ再起動の数秒だけ)。
- **PR-S1 の後で戻すとき**: コードだけ前に戻す。表と列は残す(今のコードは新しい列を読まないので害がない)。表を消す必要は無い。
- **PR-S2 の後で戻すとき**: コードだけ前に戻す(表は残す)。⚠戻したコードは「種類つきの発送」を知らないので、**戻す前に作られた種類つきの発送では、戻したコードの `assign` などの守りが効かない**。戻す場合は、種類つきの発送を送付前に止める(発送の画面で使わない)ことを運用で守り、再反映後に続きを行う。表を消す・台帳を消すことは**しない**(RESTRICT のため消せない=意図どおり)。
- **表そのものを消す戻し**(migration の取り消し)は想定しない。どうしても要る場合は、先に種類つきの発送・写し・物件の欄を手で空に戻す SQL を用意してから行う(その時点で別途計画する)。

## 7. テスト
- 種類の決め方: 物件の欄/導入ルート8種/既定/使わない種類 の全組み合わせ。
- 組がずれない: 種類の数 1〜3 × 宛先の並び × LP の有無 を総当たり。作成・assign・種類を変える のすべての経路で不一致が保存されないこと。
- 古い発送: 既定の種類を送らない作成が、今とまったく同じ行を作ること(既存テストがそのまま通る)。
- 写しの独立: 発送を作った後に台帳を直しても、発送の型と公開ページが変わらないこと。
- 走査型: 組を保存する経路が判定関数を必ず通ること。
- 実機: 相続2件+空き家1件で発送を作り、それぞれのQRからそれぞれのページが出ること(ブラウザで開いて確認)。

## 8. @codex に見てほしい点
1. 写し取る方式で、台帳の書き換えと発送作成が同時に走ったとき、中身が混ざる隙間が無いか(§3.3.1 の `FOR UPDATE`/`FOR SHARE`)。
2. ロックの順序が既存の作成処理・割り当て・凍結と食い違わないか。
3. 組がずれない守りに抜け道(画面を通らない API・再送・既存の型の貼り直し)が無いか。
4. 物件の欄の種類を「使わない」にしたときの扱い(§3.2)で黙って誤った種類になる経路が無いか。
