# 貼り付けて物件化 — 設計書

作成日: 2026-08-26 / 発注者承認済み方針にもとづく設計 / 基点 `7eaeab50`

## 1. 何を解決するか

社外から届く物件情報を、いま人が読んで手で入力し直している。週5〜20件。

入力し直しには2つの実害がある。

1. **時間がかかる**。1件あたり10〜20項目の転記。
2. **地番を取り違える**。住居表示と地番は別物で、登記は地番でしか引けない
   (社内の恒久ルール「住居表示と地番は別物」)。元資料に地番が書かれていても、転記の過程で
   住所欄に混ぜてしまうと、あとで謄本が引けなくなる。

貼り付けるだけで、読み取れた項目が埋まった状態の確認画面を出し、人が見て確定する。

## 2. 適用範囲

### 対象とする入口

貼り付け欄1つ。次の3つを同じ受け皿で扱う。

- 業者・ポータルから届いた**メール本文**(コピーして貼る)
- **PDF**(ドラッグ&ドロップ、または選択)
- **ブラウザで見ているページ**(全選択してコピーして貼る)

### 対象としないもの(明示的に範囲外)

| やらないこと | 理由 |
|---|---|
| メールの自動受信(専用アドレスへの転送) | 週5〜20件に対して受信基盤・迷惑メール対策・なりすまし対策が重すぎる |
| ブラウザ拡張機能 | 全端末への導入と更新の手間が続く。Webメール以外では使えない |
| 外部AIへの送信による読み取り | 物件情報と個人情報の社外送信・費用・鍵管理。売却DMで一度廃止した方式(実績91) |
| 価格・面積などの推測補完 | 誤った値が入ったまま登録されるほうが、空欄より危険 |
| 画像しかないPDF(スキャン)のOCR | 別タスク(紙スキャンOCRは別タスクとして設計済・未実装)。本件はテキストを持つPDFのみ |

## 3. 実測した入力サンプル

発注者から提供された実物2件。**どちらも HOME4U だが書式が異なる**。
この「同一提供元でも複数書式」が設計の中心的な制約。

### サンプルA: 空き家相談シート(PDF)

```
空き家所有者との関係性 <TAB> 本人
物件所在地 <TAB> 世田谷区池尻4丁目26-8（地番552-2）
物件種別 <TAB> 一般住宅
築年数 <TAB> 平成8年建築
建物構造 <TAB> 木造スレート葺
私道負担の有無 <TAB> 私道（地番：552-11、210-10）持ち分あり
希望する利活用方法 <TAB> 売却
コメント <TAB> 売却を検討しているのでまずは査定をお願いしたい。
（値が "-" の項目が9つ）
```

- 区切りはタブ。ラベルに飾り文字なし
- **所在地の括弧内に地番がある**
- 築年は**和暦**
- **所有者の氏名・連絡先は含まれない**
- 一意の番号がない

```

■建物（専有）面積  ： 70 平米
```

- 区切りは全角コロン。ラベル頭に `■`
- **査定ナンバーという一意の番号がある**
- 築年は**西暦**
- **所有者の氏名・カナ・電話・メール・住所がある**
- **地番がない**(住居表示のみ)
- 全角数字が混ざる(`１年以内`)

第2節の方針と整合する。

## 4. 構造

### 4.1 全体の流れ

```
貼り付け / PDF投入
    ↓
[段1] テキスト化        … PDFは既存の extractTextFromPdf、貼り付けはそのまま
    ↓
[段2] ラベルと値に分解   … 純関数 parseLabeledLines
    ↓
[段3] アプリの欄へ対応   … 純関数 mapLabelsToDraft(辞書駆動)
    ↓
[段4] 送り元ごとの後処理 … 純関数 applySourceProfile
    ↓
下書き(PropertyDraft + OwnerDraft + 警告リスト)
    ↓
確認画面(人が見て直す)
    ↓
登録(物件 + 所有者 + 添付)
```

段2〜4はすべて**純関数**。DB・ネットワーク・ファイルに触らない。
理由: 実サンプルをそのままテストに固定でき、書式が増えても回帰を検出できるため
(社内の恒久ルール「見本は実物の並びを写す」)。

### 4.2 段2: ラベルと値に分解

`parseLabeledLines(text: string): LabeledLine[]`

1行を「ラベル」と「値」に割る。区切りとして次を等価に扱う。

- 全角コロン `：`
- 半角コロン `:`
- タブ

正規化:

- 行頭の飾り文字(`■` `●` `・` `【` など)を落とす
- ラベル・値の前後の空白(全角含む)を落とす
- 値が `-` `ー` `−` `空文字` のものは**「値なし」として扱う**(サンプルAに9件ある)
- 改行コードは LF に正規化(社内の恒久ルール「走査型テストは改行をLFに正規化」)

**割らない行**(区切りがない行)は捨てずに `unlabeled` として保持する。
確認画面で原文と突き合わせるときに必要になるため。

### 4.3 段3: アプリの欄へ対応づける

`mapLabelsToDraft(lines: LabeledLine[]): RawDraft`

ラベル名の**辞書**で振り分ける。1つの欄に複数の言い回しを登録する。

| アプリの欄 | 受け付けるラベル(初期辞書) |
|---|---|
| 物件.住所 | 物件所在地 / 所在地 / 物件住所 / 住所(物件) |
| 物件.種別 | 物件種別 / 種別 / 物件の種類 |
| 物件.建物名 | 物件名称 / 建物名 / マンション名 |
| 物件.専有面積 | 建物（専有）面積 / 専有面積 / 建物面積 |
| 物件.間取り | 間取り / 間取 |
| 物件.現況 | 現況 / 入居状況 |
| 所有者.氏名 | お名前 / 氏名 / ご氏名 |
| 所有者.カナ | フリガナ / ふりがな / カナ |
| 所有者.電話 | 電話番号 / TEL / 連絡先 |
| 所有者.メール | E-mail / メールアドレス / Email |
| 所有者.住所 | ご住所 / 住所 |

**他社が来たときは、この辞書に行を足すだけで対応できる。** これがA案を選んだ理由。

辞書に無いラベルは捨てず、`unmapped` として保持し、**備考へまとめて入れる**。
情報を落とさないため。

### 4.4 段4: 送り元ごとの後処理

`applySourceProfile(draft: RawDraft, profile: SourceProfile): PropertyDraft`

送り元の判定は**ラベルの組み合わせ**で行う(URLやファイル名に依存しない)。

| プロファイル | 判定条件 | 後処理 |
|---|---|---|
| `home4u_assessment` | `査定ナンバー` を含む | ①外部キー=査定ナンバー ②所在地から建物名と部屋番号を切り出す |
| `home4u_vacant_house` | `空き家所有者との関係性` を含む | 固有の処理はなし(共通処理だけで足りることを実サンプルで確認済み)。プロファイルとして名前を持たせるのは、確認画面に送り元を表示するためと、将来この書式だけ直したくなったときの受け皿のため |
| `generic` | 上記以外 | 共通処理のみ(括弧地番の分離・和暦変換は共通で試みる) |

**共通の後処理**(全プロファイルで走る。プロファイル固有処理は、これで足りないものだけを足す):

- `（地番XXX）` `（地番：XXX）` 形式を住所から切り離して地番欄へ
- 和暦(`平成8年` `令和3年` `昭和55年`)→西暦
- 全角英数字→半角
- `70 平米` `70㎡` → 数値 70
- 物件種別の言い換え→ enum(`分譲マンション（区分所有）`→`apartment_unit` /
  `一般住宅`→`house` / `土地`→`land` …)。**辞書に無い種別は `unknown` にして警告**

**建物名と部屋番号の切り出し**(サンプルBで必要):

所在地の末尾が「物件名称」と一致する場合、その後ろに残る文字列を部屋番号とする。
`東京都世田谷区等々力2丁目15番12号（建物名）303` − `（建物名）` → 部屋番号 `303`。
物件名称が無い、または一致しない場合は**切り出さない**(推測しない)。

### 4.5 出力する下書き

```
PropertyDraft {
  値: { 各欄: { value, sourceLabel, confidence } }
  warnings: Warning[]
  externalLinkKey: string | null
}
OwnerDraft | null
attachments: { PDF原本 }
```

各欄に**どのラベルから来たか**を持たせる。確認画面で「これは元資料のどこから来たか」
を示すために必要。

## 5. 確認画面

### 5.1 レイアウト

左に**貼った原文**、右に**読み取り結果のフォーム**。左右は画面が狭いときは縦に並ぶ
(スマホ対応は必須ではないが、崩れないこと)。

### 5.2 3つの状態を区別して見せる

| 状態 | 見せ方 |
|---|---|
| 拾えた | 値が入っている。どのラベルから来たかを小さく添える |
| 元資料に無い | 空欄 + 「元の資料に記載がありません」 |
| 拾えたが確信がない | 値 + 琥珀色の注意(例: 種別が辞書に無い) |

**「拾えなかったから推測で埋める」は行わない。** 発注者承認済みの方針。
誤った値が入ったまま登録されるほうが、空欄より業務被害が大きいため。

### 5.3 必ず出す警告

- **地番がありません** — 「このままでは謄本を取得できません。地番は地番検索サービスで
  調べて入力してください」(社内の恒久ルール「住居表示と地番は別物」)
- **すでに登録済みの可能性があります** — 第6節
- **物件種別を判別できませんでした** — enum に落とせなかった場合

### 5.4 操作

- どの欄も編集できる
- 「この内容で登録」で確定
- 所有者を作らない選択もできる(チェックを外す)

## 6. 二重登録の防止

3段階で見る。**外部キーが一致したときだけ登録を止める**。それ以外は警告を出すだけで
止めない(住所が似ていても別物件のことがあり、人が判断できるため)。

| 手がかり | 判定 | 既定の動作 |
|---|---|---|
| 外部キー(査定ナンバー) | `Property.externalLinkKey` 完全一致 | **登録を止める**。「この案件は登録済みです」+ 既存物件へのリンク |
| 住所 + 地番 | 正規化して一致 | 警告。既存物件を並べて「それでも新規作成する」を選べる |
| 所有者(氏名 + 住所) | `buildOwnerDedupKey` で一致 | 候補を並べ「既存に紐付ける / 別人として作る」を選ばせる |

所有者の重複判定は**既存の部品 `src/lib/owner-dedup.ts` の `buildOwnerDedupKey` をそのまま使う**。新設しない。

## 7. 登録時に書き込むもの

| 対象 | 内容 |
|---|---|
| 物件 | 下書きの各欄。`introductionRoute = web_inquiry`、`caseStatus = new_case` |
| 所有者 | 氏名・カナ・電話・メール・住所。`externalLinkKey` は物件側にのみ持たせる |
| 紐付け | `PropertyOwner` を1件 |
| 添付 | PDFを投入した場合、その原本を物件の添付として保存 |
| 備考 | 辞書に無かったラベルと値をまとめて記載(情報を落とさないため) |
| 監査ログ | 「貼り付けから物件作成」。**貼った原文・氏名・電話・メールは記録しない**(社内の恒久ルール「ログに外部由来の文字を出すときは許可リスト方式」) |

**トランザクション**: 物件・所有者・紐付け・添付を1つのトランザクションで作る。
添付作成は親の物件行を `FOR UPDATE` した同一tx内で行う(リポジトリ全体の規約。
走査テストで固定されている)。

## 8. 権限

- 画面と作成APIは `property:write` を要求(事務担当も使える)
- 所有者の作成を伴うため `owner:write` も要求
- サイドバーは「物件データ取り込み」グループ内、`office_staff` 以上に表示

## 9. 誤りへの備え

| 起きうること | 対応 |
|---|---|
| PDFがスキャン画像でテキストが取れない | 「文字が入っていないPDFです」と伝え、貼り付けを案内。**無言で空の下書きを出さない** |
| 貼り付けが巨大(ページ全体をコピー) | **200,000文字**を超えたら断る(サンプルAは334文字・Bは約900文字。3桁の余裕がある)。ラベル行が1つも見つからなければ「読み取れる項目がありませんでした」と伝える |
| 同じ内容を続けて2回登録 | 第6節 |
| 種別が辞書に無い | `unknown` + 警告。**登録は止めない**(人が直せる) |
| 全角・半角・空白のゆれ | 段2で正規化 |

## 10. テスト方針

### 10.1 実サンプルを見本として固定する

提供された2件を、**書式は1文字も変えずに**テストの見本として置く。

⚠ **実在の個人情報は入れない。** 氏名・カナ・電話番号・メールアドレス・査定ナンバーは
**架空の値に置き換える**。テストコードは残り続けるため。
置き換えるのは値だけで、桁数・区切り・全角半角の別は実物どおりにする
(社内の恒久ルール「見本は実物の並びを写す」)。

### 10.2 純関数の総当たり

- 段2: 区切り3種 × 飾り文字有無 × 値なし記号3種 × 空白ゆれ
- 段4: 和暦3元号 × 境界年、括弧地番の有無、建物名一致/不一致
- 種別の対応づけ: 既知の全ラベル + 未知(→`unknown`+警告)

### 10.3 やること

- `npx tsc --noEmit` = 0
- `npx vitest run` フル
- `npx eslint <変更ファイル>` = 新規0
- `npm run build`
