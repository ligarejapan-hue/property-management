# 宛名CSVの手紙に配信停止QR — 設計

- 日付: 2026-10-03
- 状態: 発注者の方針承認済み(案A「CSVに配信停止URLの列を足す」・2026-10-03)。本書は実装前のレビュー用
- 関連: 売却DMの配信停止QR(PR #416・`src/app/u/[token]/route.ts`)/ 宛名CSVの控えと確定(PR-A・`docs/superpowers/specs/2026-08-08-dm-sending-management-design.md` §2.1〜2.2)/ 反響(PR-B・`src/lib/dm-reaction/core.ts`)

## 1. 目的と前提

売却DM(アプリが印刷する手紙)には、受け手が自分で配信停止を申し出られる QR が付いている。宛名CSV(物件一覧の「DM差込CSV出力」)で作る手紙には付いていない。宛名CSVの手紙にも同じ停止の道を付ける。

発注者の運用(2026-10-03 回答): **Word の差し込み印刷**と**DM業者への引き渡し**の両方。アプリが印刷するわけではないので、アプリが渡すのは **手紙1通ごとの「配信停止URL」** まで。QR にするのは Word(差し込みフィールド `DISPLAYBARCODE`)か業者。

本番の実測(2026-10-03・読み取りのみ): 宛名CSVの控えは **0件**(作成・ダウンロード・確定とも0)、一括確定由来の送付記録も0件。=**移行の配慮(旧形式のCSV・旧控え)は実害ゼロ**。ただしコードは「旧控え」があっても正しく振る舞うように書く(§6)。

### 範囲外
- 物件住所宛のCSV(`/api/properties/property-dm-export`)。画面の入口が無く、控え・送付記録の仕組みも持たない。
- QR 画像の生成(案B・見送り)。
- 停止の取り消し画面(既存の「送付記録の訂正」で管理者が戻せる)。

## 2. 利用者から見た動き

1. 物件一覧「DM差込CSV出力」で落とした CSV の**最後の列**に「**配信停止URL**」が入る(1行=1通ごとに別のURL)。差し込みは列名で行うので、既存の Word の雛形は壊れない。
2. Word では差し込みフィールドで QR にする(手順は使い方ガイドに書く)。業者には「配信停止URL の列を QR にして刷ってほしい」と頼む。
3. 受け手が QR を読むと、売却DMと同じ「配信停止のお手続き」画面(氏名・住所は出さない)。「停止する」を押すと:
   - その手紙の**宛先全員**(共有者を含む)の送付記録に「**拒否**」が付く(メモ「QRコードからの配信停止申込」)。
   - 以後、宛名CSV・売却DMの対象から**自動で外れる**(既存の除外=`src/lib/dm-batch/terminal-exclusion.ts` がそのまま効く)。
4. **「送付の確定」(投函日の入力)より前**に停止が来た場合も、その場で拒否を記録する(売却DMの「送付済みにする前の停止」と同じ考え方=署名付きURLを持っている=手紙が手元にある証拠)。そのとき、その1通ぶんの送付記録を先に作る。後で控えを確定すると、その送付記録の投函日が確定時の投函日にそろう。
5. 同じQRをもう一度読んでも壊れない(同じ完了画面・記録は二重にならない)。
6. 画面(物件一覧の出力の案内)に「配信停止URLの列があります。QRの作り方は使い方ガイド」と一言出す。追跡URL(売却DM設定)が未設定なら「配信停止URLを出すには売却DM設定の追跡URLが必要です」と出し、列は空にする。

## 3. URL と署名

- 形: `<追跡URL>/u/<トークン>`(売却DMと同じ公開パス `/u/`・nginx の公開範囲・`proxy.ts` の PUBLIC_PATHS に既に含まれる)。
- トークン = `c<控えの行id(UUID)から '-' を除いた32桁の16進>.<署名22文字>`。
  - 先頭の `c` で「宛名CSVの1通」と判別する(売却DMの追跡トークンは `randomBytes(8)` の base64url=11文字なので、33文字の `c[0-9a-f]{32}` とは重ならない)。既存の形式門前払い(`^([A-Za-z0-9_-]{6,64})\.([A-Za-z0-9_-]{22})$`)の内側に収まる。
  - 署名 = 既存の停止専用鍵(`deriveUnsubscribeKey`・NEXTAUTH_SECRET から HKDF)で、**用途ラベルを分けた** HMAC: `dm-unsub-batch-item:<itemId>`(売却DMは `dm-unsub:<trackingToken>`)。片方の署名をもう片方へ流用できない。
  - 新しい関数 `buildBatchItemUnsubscribeToken(itemId, key)` / `verifyBatchItemUnsubscribeToken(raw, key) → itemId | null` を `src/lib/dm-batch/unsubscribe-token.ts` に置く(既存の `unsubscribe-token.ts` は変えない)。
- ⚠NEXTAUTH_SECRET をローテーションすると配布済みのURLが無効になる(売却DMと同じ・既知)。

## 4. CSV

- `DM_EXPORT_HEADERS` の**末尾**に「配信停止URL」を足す(この見出しを使うのは宛名CSVの控えだけ=`src/lib/dm-batch/csv.ts`)。
- 値は控えの行ごとに `buildBatchItemUnsubscribeToken(item.id)` から組む。Excel 用の無害化(`sanitizeCsvCellForExcel`)は他の列と同じく通す。
- **追跡URLは初回ダウンロードで控えに固定する**: `dm_export_batches.unsubscribe_base_url`(新しい列・TEXT NULL)に、初回 GET の凍結 tx の中で書く。再ダウンロードはこの値で組む。=設定画面で追跡URLを変えても、配った CSV と同じ内容が再生成され、csvDigest の一致検査(既存)に引っかからない。
  - 初回時点で追跡URLが未設定なら NULL のまま=列は空。再ダウンロードも空のまま(後から設定しても、配った CSV と変えない)。
- 署名鍵が取れない(NEXTAUTH_SECRET 不在)場合はアプリ自体が動かないので考えない(取れなければ列を空にする安全側)。

## 5. 停止の受付(`POST /u/<token>`)

既存の route の入口(per-IP 制限・Origin 検査・署名検証・トークン単位 5/時・全体 60/時・監査)はそのまま共通にし、署名検証の分岐だけ増やす:
- `c` 形式 → 宛名CSVの1通として処理(本節)。それ以外 → 既存の売却DMの処理(変更なし)。
- 回数制限のキーはトークン本体(`u-token:<itemId>` / 既存は `u-token:<trackingToken>`)。全体枠は両方で共有(=正規の停止の上限は合算60/時。現状の想定件数で十分)。

### 5.1 1通の処理(1つの取引)

ロック順は確定(`confirm/route.ts`)と同じ並び「所有者 → 物件親行 → 控え(バッチ)行 → 控えの行」。停止は拒否(terminal)を書くので所有者は **FOR UPDATE**(売却DMの停止と同じ)。

1. 先読み(無ロック): 控えの行(id・batchId・propertyId・ownerId・連関の所有者・`logId`)と控え(downloadedAt・confirmedAt・sentOn)。
   - 行が無い(控えの削除・初回ダウンロード前の物理削除)→ 在否を答えず完了画面(監査 `missing`)。
   - 控えが**未ダウンロード**(downloadedAt なし)→ 手紙はまだ存在しない=署名はあり得ないが、念のため「成功と言わない」画面(既存の `renderUnsubscribeInvalidPage`・監査 `unsent`)。
2. 所有者(代表+連関)を FOR UPDATE(id順)→ 物件親行(propertyId があれば)→ 控え行 FOR UPDATE → 控えの行 FOR UPDATE。
3. ロック下で読み直し、所有者の集合が先読みと違えば中止(`conflict`=「もう一度押してください」画面・既存の型)。
4. 送付記録(PropertyDmLog)を決める:
   - 控えの行に `logId` があり、その記録が残っている → それを使う。
   - `logId` が無く、控えが**未確定** → **この1通ぶんの送付記録を作る**: propertyId/ownerId(代表)/dmType=`owner_address`/batchId/method=`mail`/sentAt=**今日(JST暦日)**/sentBy=控えの作成者。連関の所有者を `property_dm_log_owners` へ。控えの行の `logId` に結び付ける(監査に `createdLog: true`)。
   - `logId` が無く、控えが**確定済み** → 本機能より前に確定した旧控え(本番には存在しない)。`(batchId, propertyId, ownerId)` で一意に引ければそれを使い、引けなければ `unsent` 扱い(成功と言わない)。
5. 各記録に、手動反響と同じ規則(`applyManualReaction`)で「拒否」を書く。守られた拒否(`isRefusalProtected`)はスキップ=冪等。メモ「QRコードからの配信停止申込」を付け足す(既存と同じ)。
6. 監査 `dm_batch_qr_unsubscribe`(detail は `result`・`batchId`・`itemId`・`createdLog`・`at` だけ。氏名・住所・URL は載せない)。

### 5.2 確定(`POST /dm-batches/[id]/confirm`)の変更

- 生成する送付記録のidを、各控えの行の `logId` に書く(以後の停止が §5.1-4 の1行目で引ける)。
- 控えの行に既に `logId` がある(=確定前に停止が来て記録を作った)なら、**新しい記録は作らず**、その記録の `sentAt` を確定の投函日に直す(反響=拒否はそのまま)。連関の所有者は作成時に入れてあるので触らない。
- ロック順・権限・既存の検査は変えない(控えの行は既に FOR UPDATE で読み直している)。

### 5.3 再ダウンロードとの関係(既存の動きのまま)

確定前に停止が来た控えを**もう一度ダウンロード**すると、既存の資格検査(2)「拒否・宛先不明」で止まり「出し直してください」と出る。拒否した相手へ刷り直さないための既存の守りで、正しい動き。確定(投函日の入力)は従来どおりできる。

## 6. データの変更(migration・追加のみ)

`20261003100000_add_dm_batch_unsubscribe`:
- `dm_export_batches.unsubscribe_base_url TEXT NULL`
- `dm_export_batch_items.log_id UUID NULL` + 外部キー → `property_dm_logs(id)` **ON DELETE SET NULL**(送付記録は物件削除時に所有者ゼロなら行ごと消えることがある=控えの行を道連れにしない)+ 索引 `(log_id)`。
  - 行数が0件の表への追加なので、索引は通常の CREATE INDEX でよい(本番実測0件・書き込みもまだ無い)。⚠念のため反映手順に「件数が0であること」を確かめる1行を書く。
- 既存行の書き換えなし(本番0件)。旧控えの扱いは §5.1-4 の3つ目。

## 7. 画面と資料

- 物件一覧の「DM差込CSV出力」の確認(既存のモーダル)に一言: 「CSVの最後の列に、1通ごとの配信停止URLが入ります。QRの作り方は使い方ガイド『宛名CSVの手紙に配信停止QRを付ける』」。追跡URL未設定のときは §2-6 の注意。
- 使い方ガイド・マニュアル(`public/docs/*.html`)に節を足す:
  - Word: 差し込み印刷の文書で Ctrl+F9 を2回入れ子にして `{ DISPLAYBARCODE "{ MERGEFIELD 配信停止URL }" QR \q 3 \s 50 }`(Word 2013 以降)。QR の下に一文「お手紙が不要な場合はQRから配信停止をお申し込みいただけます」を雛形に書く。
  - 業者: 「配信停止URL の列を QR コード(誤り訂正 M 以上・約15mm 角以上)にして、各通に刷ってください」。
  - 停止が来たらどう見えるか(物件の DM 送付履歴に「拒否」・以後は自動で外れる)。
- 監査ログの表示名に `dm_batch_qr_unsubscribe`=「宛名CSVの手紙 配信停止(QR)」。

## 8. 守り(売却DMと同じ水準を保つ)

- 署名の無いURL・形式違い・用途違いの署名 → DB に触らず同じ無効画面(在否を答えない)。
- GET は表示だけ(DB 無アクセス)。停止は POST のみ(プレビューbot の誤停止防止)。
- 回数制限は署名検証の後に全体枠を消費(でたらめな連投で正規の停止を止められない)。
- 監査・ログに氏名・住所・URL・トークンを出さない(許可リスト)。nginx は `/u/` のアクセスログを既に止めている。
- 公開経路にセッションは無い=送付記録の sentBy は控えの作成者。

## 9. テスト(TDD)

- トークン: 往復・用途ラベル違いの署名を拒否・`c` 形式の判別・売却DMトークンとの非衝突(長さ・形)。
- CSV: 末尾に「配信停止URL」・行ごとに別のURL・初回で base URL を固定し再ダウンロードで同じ内容(digest 一致)・未設定は空・既存の列は不変。
- 停止(route): 確定済み=拒否のみ/未確定=記録を作って拒否+logId/二度目=already/所有者集合が変わった=conflict/未ダウンロード=unsent/行なし=missing/旧控え(logIdなし・確定済み)の一意引き当てと不一致/監査の detail にPIIなし/売却DMの既存テストが全部そのまま通る。
- 確定: logId の書き込み/確定前の停止で作った記録は再作成せず sentAt だけ投函日に。
- ロック順: 停止と確定の取り合いを純関数に出して総当たり(既存の「順番が交差する処理は総当たり」の型)。
- 実機: ローカルDBで「控え作成→ダウンロード(列とURLを確認)→URLを開いて停止→DB の拒否と logId→確定で sentAt が投函日に→もう一度ダウンロードで 409」。
