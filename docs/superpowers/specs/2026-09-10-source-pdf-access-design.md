# 元資料PDF（受付帳・謄本）への導線と、所有者→物件リンク 設計書

作成日: 2026-09-10 / 状態: 発注者承認済（方針）・実装前

## 1. 背景と目的

名寄せ（重複所有者の突き合わせ）作業中に、判断の根拠となる**元資料**へ辿り着けない。

- **謄本PDF**（所有者事項・全部事項）は手元のPCにあるが、システムにはほぼ入っていない。
- **受付帳PDF**（その日その法務局に出た登記の一覧）はシステムに置き場所すら無い。
- **所有者から物件へ行く道が、システム上のどこにも無い**。所有者詳細は「紐づき物件数」の数字だけで、
  物件一覧に「この所有者で絞る」機能も無い。

本設計のゴールは次の3つ。

1. 所有者（特に補正候補の画面）から、その所有者の物件の基本情報へ1〜2クリックで行ける。
2. 物件の基本情報から、その物件の謄本PDFを開ける。
3. 物件の基本情報から、その物件が載っている受付帳PDFを開ける。

## 2. 実測（2026-09-10・本番と手元）

設計の前提はすべて実測で裏を取った。推測は使っていない。

### 2.1 手元のPDF

| 種類 | 本数 | 合計 | 1本の最大 |
|---|---|---|---|
| 受付帳PDF | 539 | 210MB | 41.3MB |
| 謄本PDF（取得済み） | 6,726 | 250MB | 0.2MB |

置き場所: `C:\Users\issin\Desktop\DM自動化\DM\不動産登記情報自動化システム（検証用）\{受付帳PDF, 取得済みPDF}`

VPS の空き容量は 76GB。合計 460MB は容量上まったく問題にならない。

### 2.2 謄本PDF一括取込は本番で一度も成功していない

```
job_type=registry_pdf_bulk : failed 68件 / success 0 / error 6,726 / 2026-07-06
行のエラー内容: 「サーバへの一時保存に失敗しました」 6,726件（全件）
現在システムにある謄本の添付: 7件のみ
```

**根本原因は特定済み**。2026-06-10 に保存先を `public/uploads` から
`/var/lib/property-management/uploads` へ移した際、systemd の `ReadWritePaths` を更新し忘れており、
**6/10〜7/16 の間はあらゆる新規アップロードが失敗していた**
（memory: systemd-readwritepaths-uploads-drift-fix）。7/6 の一括投入はまさにこの期間に当たる。
この不具合は 7/16 に修正済みで、現在の設定は正しい:

```
STORAGE_BACKEND=local
LOCAL_UPLOAD_ROOT=/var/lib/property-management/uploads
ReadWritePaths=/opt/property-management/.next /var/lib/property-management/uploads
```

→ **謄本側にプログラムの修正は不要。再投入すれば入る見込み**（ただし少量で試してから全量）。

### 2.3 受付帳PDF名と取込記録の名前は完全に一致する

本番の取込記録 752 件を全件取り出し、手元の 539 本のPDFと突き合わせた実測結果:

```
PDF本数=539  正準化キーの衝突=0
取込記録=752  受付帳系=747  一致=747  不一致=0  受付帳でない=5
```

例:

```
取込記録 (property_csv) : 01＋本局ー10月F_202501291026_0100_000021_受付帳_選別.xlsx
取込記録 (owner_csv)    : 10＋世田谷ー1月相続F_..._受付帳_選別.xlsx + 10＋世田谷ー1月相続F_..._所有者.xlsx
PDF                     : 01＋本局ー10月F_202501291026_0100_000021.pdf
```

### 2.4 物件と受付帳の紐付けはきれいに1対1

```
物件総数                    : 124,407
受付帳の取込行が紐づく物件  : 124,403（99.997%）
受付帳の取込行が無い物件    : 4（手動作成分）
2本以上の受付帳に紐づく物件 : 0
```

→ **1物件 = ちょうど1つの受付帳PDF + 1つの行番号**。曖昧さが無い。

### 2.5 サーバーが受け取れるファイルの上限

```
nginx: client_max_body_size 12m
       proxy_read_timeout 600s
```

- 謄本PDF: 100本/回 × 平均38KB ≒ 3.8MB → **現状のままで通る**。
- 受付帳PDF: **1本で最大41.3MB → 12MB上限に引っかかり必ず失敗する**。上限の引き上げが必須。

## 4. 段1: 所有者から物件へ飛べるようにする

### 4.1 やること

1. **物件一覧に「所有者で絞る」条件を追加する**（`ownerId`）。
   条件の組み立ては `src/lib/property-list-query.ts` の `buildPropertyListWhere` 一箇所に集約されており、
   一覧・CSV出力の両方がここを通る。**ここにだけ足す**（既存方針を崩さない）。
2. **所有者補正候補の「物件」列を押せるようにする**。
   - 0件 … いまのまま数字（リンクにしない）
   - 1件 … その物件の基本情報へ直行
   - 2件以上 … 物件一覧をその所有者で絞った画面へ
3. **所有者詳細ページに、紐づく物件の一覧を出す**（住所＋地番、それぞれリンク）。
   件数が多い場合に備えて上限20件＋「すべて見る」（＝2の物件一覧へ）。

### 4.2 判断は純関数へ

「件数からどのリンク先になるか」を `resolveOwnerPropertyLink(ownerId, count)` として切り出し、
0 / 1 / 複数の3分岐をテストで固定する。画面側は結果を表示するだけにする。

### 4.3 権限・PII

- 物件一覧の `ownerId` 絞り込みは、**既存の物件一覧と同じ担当者スコープ・権限**をそのまま通す。
  絞り込みを足したことで見えてはいけない物件が見えるようになってはならない。
- 所有者IDは既に画面に出ている値（opaque な UUID）なのでURLに載せてよい。
  **氏名・住所・法人番号・リンクキーはURLに載せない**（既存の明文ルール）。
- 所有者詳細の物件一覧は `owner:read` ではなく**物件の閲覧権限**で判定する（物件の情報だから）。

## 5. 段2: 謄本PDF 6,726本を入れる

### 5.1 手順（プログラム修正は想定していない）

1. **少量で試す**: 10本程度を既存の「取得済みPDFを一括で物件に添付」画面（登記DM取込の3ステップ目）から投入し、
   `success` になること・物件の添付タブから開けることを確認する。
2. 全滅した 68 ジョブ（2026-07-06・全行 error）は**そのまま残す**。過去の記録なので消さない。
   ただし取込一覧で紛らわしいので、**古い失敗ジョブと今回の投入を取り違えない**ようジョブは
   `job_type + 作成日` で必ず絞って見る（過去に取り違えて健全な投入を止めた実例がある）。
3. 全量 6,726 本を投入する。1回100本ずつに自動で分割され、途中で閉じても再開できる仕組みは既にある。
4. **当たらなかったPDFは「要確認」に残る**。所在の文字が物件と一致しなかったもの。
   後から手で物件に結びつけられる（既存機能）。何件残ったかを記録する。

### 5.2 物件の基本情報からの導線（新規）

物件の基本情報タブに1行足す:

```
謄本   所有者事項 2件 / 全部事項 1件      [添付を見る]
```

- 押すと同じ画面の「添付ファイル」タブへ切り替わる（別ページへ飛ばさない）。
- **件数だけを出し、ファイル名は出さない**。謄本のファイル名には所在が入るため、
  既存の伏せ字方針に合わせて基本情報には出さない。種別（所有者事項／全部事項）は非PIIなので出してよい。
- 謄本を見る権限が無い人には**この行自体を出さない**。

### 5.3 想定される失敗

- 少量テストが失敗した場合は、そこで止めて原因を突き止める（推測で全量を流さない）。
  ログの確認先は `journalctl -u property-management`（**時刻はUTC表記**）。
- 6,726本の投入中にサーバーが重くなる可能性がある。夜間に実施する。

## 6. 段3: 受付帳PDF 539本を入れて、物件から開けるようにする

### 6.1 保存の考え方

受付帳PDFは**1本に数千件の登記が載っている冊子**で、特定の物件のものではない。
よって**物件ごとにコピーを持たせない**。PDFは1本につき1回だけ保存し、物件からは名前で辿る。

新しいテーブルを1つ足す（既存テーブルへの破壊的変更なし・追加のみ）:

```prisma
model ReceptionBookPdf {
  id         String   @id @default(uuid()) @db.Uuid
  matchKey   String   @unique @map("match_key")  // 突き合わせ用の正準化キー
  baseName   String   @map("base_name")          // 表示用（例: 01＋本局ー10月F_202501291026_0100_000021）
  fileKey    String   @map("file_key")           // 保存場所のキー
  fileSize   Int      @map("file_size")
  uploadedBy String   @map("uploaded_by") @db.Uuid
  createdAt  DateTime @default(now()) @map("created_at")

  uploader User @relation(fields: [uploadedBy], references: [id])

  @@map("reception_book_pdfs")
}
```

- 保存キーは `reception-book/{id}.pdf`。**元のファイル名を保存キーに使わない**
  （規約外のファイル名がそのまま保存先の名前になるのを避ける既存方針に合わせる）。
- `baseName` は地区名と年月だけで個人情報を含まないため、画面に出してよい。

### 6.2 突き合わせ（純関数2本）

実データ 747 件で不一致ゼロを確認済みのロジックをそのまま部品にする。

```
receptionStemFromJobFileName(fileName)
  "A_受付帳_選別.xlsx + B_所有者.xlsx" → " + " の手前を取る
  拡張子(.xlsx/.xlsm/.xls/.csv)を落とす
  末尾の "_受付帳" または "_受付帳_選別" を落とす → A
  当てはまらなければ null（受付帳由来ではない取込）

canonicalReceptionKey(stem)
  NFKC正規化（＋→+ 、全角英数→半角）
  各種ダッシュ（ー－―‐−）を "-" に統一
  空白を除去
  小文字化
```

**検証方針**（この repo の既存ルールに従う）:

- 判定は画面やAPIに書かず、上の2つの純関数に隔離する。
- 本番の取込ファイル名 747 件と手元のPDF 539 本を**全件通す走査型テスト**を置き、
  一致747 / 不一致0 / キー衝突0 を固定する。
- 変異検証（正規化を1つ外すと落ちること）を、ダッシュ統一・NFKC・接尾辞除去のそれぞれで置く。
- 走査型テストは**改行をLFに正規化**してから比較する（手元CRLFとCIで判定が変わる既知の罠）。

### 6.3 アップロード画面

`/import/reception-pdf` を1つ足す。操作感は既存の「取得済みPDFを一括で上げる」画面と揃える
（フォルダごと選択・進捗表示・途中で閉じても再開）。

- 1ファイル上限 **50MB**（実測最大41.3MBに余裕を持たせる）。
- ただし**送信は1ファイル1リクエストに固定する**。謄本側は「100本 or 90MB でまとめる」割り振りを
  しているが、受付帳は1本で41MBあり、まとめた瞬間にサーバーの受け取り上限を超える。
  よって**まとめる仕組みは持ち込まない**（539本なので所要時間は問題にならない）。
- 同じキーのPDFを再度上げた場合は**上書きせず「既にあります」で飛ばす**（再開できるようにするため）。
- 取込記録に対応が無いPDFも**受け入れて保存する**（先にPDFを上げてから受付帳を取り込む順序を許す）。
  画面には「まだどの取込にも結びついていません」と出す。

**サーバー設定の変更が必須**:

```
nginx: client_max_body_size 12m → 64m
```

`/etc/nginx/sites-available/property-management` を退避を取ってから変更する。
**この変更を先に済ませないと段3は必ず失敗する。**

### 6.4 物件の基本情報からの導線

```
受付帳   01＋本局ー10月（12,345行目）      [PDFを開く]
```

解決の流れ（画面表示のたびに2クエリ）:

```
物件ID
  → 受付帳の取込行（jobType=property_csv・createdId=物件ID）から 取込ファイル名 と 行番号
  → receptionStemFromJobFileName → canonicalReceptionKey
  → ReceptionBookPdf を1件引く
```

- PDFがまだ入っていない場合は「**受付帳: 01＋本局ー10月（12,345行目・PDF未取込）**」と出し、
  リンクは出さない。どの受付帳から来た物件かは分かるので、それだけでも役に立つ。
- 取込行が無い物件（4件）はこの行自体を出さない。
- **行番号はExcelの行番号であって、PDFの何ページ目かではない**。画面にもその旨を短く添える
  （「PDF内の位置までは特定できません」）。誤解を招かないことを優先する。

### 6.5 権限・PII

- 閲覧は**謄本PDFと同じ扱い＝全員（現地スタッフ・事務スタッフ・管理者）**（発注者判断 2026-09-10）。
  既存の `registry_pdf` 権限を**流用しない**。受付帳は謄本とは別の資料なので、
  新しい資源名 `reception_pdf`（preview / download）を足し、3テンプレすべてに付与する。
  意味の違う権限を使い回すと、後で謄本だけ絞りたくなったときに受付帳まで巻き添えになる。
- 配信は謄本PDFと同じく**キャッシュさせない**（`no-store`）。
- アップロードは取込権限（`import:write`）を持つ人だけ。
- ログに元のファイル名を出す場合は、**安全なものだけを組み立てる許可リスト方式**にする
  （伏せ字方式は使わない・既存の明文ルール）。

## 7. やらないこと（YAGNI）

- **PDFの何ページ目かの特定**。受付帳PDFは全ページ画像で、文字を読むには文字起こしが要る。
  文字起こしは 2026-09-08 に発注者判断で止めている。行番号までで十分とする。
- **PDFのページ送り機能や画面内ビューア**。ブラウザ標準のPDF表示に任せる。
- **謄本PDFの中身の解析**。既存の仕組み（ファイル名の所在で突き合わせ）から変えない。
- **所有者から受付帳PDFへの直接リンク**。所有者は複数物件に紐づくため導線が曖昧になる。
  物件を経由すれば辿れるので作らない。
- **失敗した68ジョブの掃除**。過去の記録として残す。

## 8. 未確定・実施時に決めること

- 段2の少量テストで、当たらなかった謄本PDFが何割出るか。1割を大きく超えるようなら

- 受付帳PDFの `pageCount` を取れるか。取れなければ null のままにする（表示にも使わない）。
