# 反響の受付から資料を送る(資料請求への返信メール) 設計

日付: 2026-10-18 / 状態: 発注者の確認待ち

## 1. 目的

業者から「資料請求」の反響が来たとき、その反響の画面から、物件の資料一覧(添付)のファイルを付けたメールを
業者の問い合わせ者へ直接送れるようにする。送った記録を反響に残し、対応漏れを防ぐ。

### 発注者が決めたこと(2026-10-18 聞き取り)

| 項目 | 決定 |
|---|---|
| 送るもの | 物件の資料一覧(添付)にあるファイル。**システムで作る販売図面は使わない**(質が低い=発注者が作ってアップロードしたものを送る) |
| 送り方 | システムから直接送る(会社のメール設定=受付メールと同じ差出人) |
| 文面 | 管理画面にひな形を1つ登録。送る前にその場で直せる |
| 謄本 | 選べる。選ぶと黄色の注意(止めない)。謄本を扱える権限の人にだけ出す |
| 送れる人 | 反響の受付を書ける人なら誰でも(管理者・事務担当・現地担当) |
| 送ったあとの状態 | 自動で「対応済み」 |
| 控え(BCC) | 送らない。控えはシステムの記録だけ |

## 2. 画面

### 2.1 ボタン
- 種類が「資料請求」の反響にだけ「資料を送る」ボタンを出す。
- 出す場所: 受付の窓の反響の詳細(`inquiry-detail.tsx`)と、物件画面の「反響」タブ(`agent-inquiry-tab.tsx`)。
- 反響の受付の書き込み権限(`agent_inquiry:write`)と、その物件を開ける権限(`property:read`+`canAccessPropertyRecord`)が両方ある人にだけ出す。

### 2.2 小窓「資料を送る」
1. **宛先**: 反響の `contactEmail` を初期値に入れる。空・誤りはその場で直せる。送れたら、直した宛先を反響の `contactEmail` にも保存する。形式が正しくないと送信ボタンを押せない。宛先は1件だけ(カンマ区切り・CC は受けない)。
2. **件名・本文**: ひな形に差し込み済みの文面を出す(§4)。その場で直せる。件名 200 字・本文 10,000 字まで。
3. **付けるファイル**: その物件の添付をチェック欄つきで並べる(§3 の「出さないもの」を除く)。ファイル名・大きさ・登録日を出す。
   - 謄本を選ぶと黄色の注意「所有者の名前・住所が載っています。送ってよい相手か確かめてください」。
   - 合計の大きさを出し、20MB を超えたら赤字で知らせて送信ボタンを押せなくする。
   - 1つも選ばないと送信ボタンを押せない。
   - 添付が1つも無い物件では「資料一覧にファイルがありません」と物件の添付タブへのリンクを出す。
4. **送信**: 押すとその場で送る(待ち行列は作らない=月30件未満)。押している間はボタンを止める。
   - 成功: 小窓を閉じ、反響を「対応済み」にし、記録の行を出す。
   - 失敗: 小窓は開いたまま、入力も残す。「送れませんでした(理由)」を出す。状態は変えない。
- 小窓の × とキャンセルの扱いは既存の決まり(×は入力を残す・キャンセルは消す)に合わせる。

### 2.3 送った記録
- 反響の詳細に「資料送付」の一覧を出す: 送った日時・送った人・宛先・ファイル数・成功/失敗。
- 行を押すと、件名・本文・付けたファイル名と大きさが見られる。
- もう一度送るのは自由。毎回1行増える。

### 2.4 ひな形の登録
- 管理画面「メール設定」(受付メールの文面と同じ画面)に「資料送付メール」の件名・本文の欄を足す。
- 未入力(null)のときは既定の文面を使う(§4.2)。

## 3. 送ってよいファイルの判定(画面と送信処理の両方で同じ関数を使う)

純関数 `selectableForMaterialSend(attachment, perms)` にまとめ、画面の一覧 API と送信 API の両方から呼ぶ。

出さない(送れない)もの:
- 所有者の個人情報が載った書類=`isOwnerPiiDocumentType(type)` が真(反響資料 `referral`・査定報告書 `report`)。種類が今後足されても、この関数を見ていれば自動で外れる。
- 削除済み(`isDeleted=true`)。
- その物件の添付でないもの(`targetType="property"` かつ `targetId=物件ID`)。
- 謄本(`type="registry"`)は、`registry_pdf:download` の権限が無い人には出さない(送る=写しを渡す=ダウンロードと同じ扱い)。
- 種類が `general`・`registry` 以外のものは出さない(許可リスト)。

送信処理では、送る直前に DB から読み直して上の判定をもう一度通す。1つでも通らなければ、何も送らずに 400 で返す(画面の古い一覧や、手で作った要求を通さない)。

## 4. 文面

### 4.1 差し込み
差し込みは決まった4つだけ。値は画面の初期値作りでだけ差し込み、送信 API は利用者が確かめた最終の件名・本文をそのまま送る。
- `{物件名}` … 物件の名前(無ければ所在地)
- `{会社名}` … 反響の業者の会社名
- `{担当者名}` … 反響の問い合わせ者の名前(空なら「ご担当者」)
- `{自分の名前}` … 送る人の表示名

### 4.2 既定の文面(未登録のとき)
件名: `【資料送付】{物件名}`
本文:
```
{会社名}
{担当者名} 様

お世話になっております。
お問い合わせいただきました「{物件名}」の資料をお送りいたします。
ご確認のほど、よろしくお願いいたします。

{自分の名前}
```
(会社の署名は発注者がひな形に書く想定。既定文には入れない)

## 5. データ

### 5.1 新しい表 `agent_inquiry_material_sends`(追加のみ)
| 列 | 型 | 説明 |
|---|---|---|
| id | uuid | |
| inquiry_id | uuid → agent_inquiries | 削除は Restrict(反響は削除しない運用) |
| sent_by_id | uuid → users | 送った人 |
| to_address | text | 宛先 |
| subject | text | 送った件名 |
| body | text | 送った本文 |
| attachments | jsonb | `[{attachmentId, fileName, fileSize, type}]`(中身は複製しない) |
| total_size | int | 合計バイト |
| result | enum `sending` / `sent` / `failed` | `sending`=送信前に作る予約(§6.3) |
| error_code | text null | 失敗の理由の短いコード(`safeErrorCode` の許可リストだけ。SMTP の生メッセージは入れない) |
| client_token | uuid | 押し直しの鍵(§6.3) |
| created_at | timestamptz | |

一意制約: `(sent_by_id, client_token)`。索引: `(inquiry_id, created_at)`。

### 5.2 `mail_config` に2列(追加のみ・null 可)
- `material_send_subject` text null
- `material_send_body` text null

migration は1本(上の表+enum+2列)。すべて追加のみ=コードを戻しても DB は触らなくてよい。

## 6. 送信 API

`POST /api/agent-inquiries/[id]/material-sends`
入力: `{ to, subject, body, attachmentIds: uuid[] (1〜20件・重複不可), clientToken: uuid }`

1. `requireAgentInquiry("write")`。反響を読む(無ければ 404)。種類が `material_request` でなければ 400。
2. 物件の権限(`property:read`+`canAccessPropertyRecord`)。無ければ 403。
3. メール設定 `loadMailSendConfig()`。null なら 409 `mail_not_configured`(画面は「管理画面のメール設定が必要です」)。
4. 同じ `(送った人, clientToken)` の行があれば、その結果をそのまま返す(2通目を出さない。`sending` なら「送信中」)。
5. 添付を DB から読み直し、§3 の判定を全件に通す。合計 20MB 超は 400(添付は base64 で約4/3倍=メールで約27MB になり得る。@codex 5巡目で一度下げたが 2026-10-19 発注者が 20MB に決定)。
6. ストレージからファイルを読む(`storage.read(key)`)。読めないものが1つでもあれば送らずに 409 `file_unavailable`。
7. `sending` の行を作る(§6.3)→送る(§6.1)。
8. 行の結果を `sent`/`failed` に書き換える。成功なら同じトランザクションで反響を `status=done`(`version` を1つ進める)+宛先が変わっていれば `contactEmail` も更新。
   - 状態の更新は `version` を見ない(送信は済んでいる=他の人の更新とぶつかっても送信の記録は必ず残す)。既に `done` なら状態はそのまま。
9. 応答: 行の要約(id・result・error_code)と反響の新しい `version`。

### 6.1 メールの送り方
- `transport.ts` に添付つきの送信 `sendMailWithAttachments(config, { to, subject, text, attachments: [{filename, content: Buffer, contentType}] })` を足す。既存の `sendPlainMail` と同じ守り(件名の改行除去・失敗メッセージを出さない・`requireTLS`)を共有し、テスト用の差し替え口も同じ形にする。
- 宛先は1件の正しい形式のアドレスだけ(改行・カンマを含めば 400)。
- 添付のファイル名は、物件の添付に登録された名前をそのまま使う(nodemailer がヘッダ用に符号化する)。

### 6.2 失敗したとき
- SMTP の失敗は `failed` の行を残して 502 を返す。状態は変えない。
- 失敗の行も `clientToken` を使う=同じ押し直しは「失敗しました」を返すだけ。画面は送り直すとき新しい `clientToken` を作る。

### 6.3 二重送信
- 画面は小窓を開くたび(と失敗のあと)に新しい `clientToken` を作る。
- 同時に2回届いた場合: 送る前に `(sent_by_id, client_token)` で `sending` の行を先に作る(一意制約)→作れた方だけが送る。`sending` のまま10分を過ぎた行(プロセス停止など)は「結果不明(届いたか確かめてください)」と表示する。
- 判定は純関数にし、順番が交差する場合を総当たりでテストする。

## 7. 一覧 API

- `GET /api/agent-inquiries/[id]/material-sends` … 記録の一覧(新しい順)。権限は反響の読み取り+物件の権限。
- `GET /api/agent-inquiries/[id]/material-candidates` … 送ってよい添付の一覧(§3)+ひな形を差し込んだ件名・本文の初期値+メール設定の有無。

## 8. 権限・個人情報

- 本文と宛先は業者の担当者の情報=既存の反響と同じ扱い(所有者の個人情報ではない)。
- 謄本を送ったときは、既存の謄本の監査ログに「メールで送付」を1行残す(誰が・どの謄本を・どの反響へ)。宛先のアドレスは監査ログには入れない(記録の表で見る)。
- 応答・ログにメールのパスワードや SMTP の生メッセージを出さない。

## 9. テスト

- §3 の判定(純関数): 反響資料・査定報告書・削除済み・別の物件・謄本の権限あり/なし・知らない種類。
- 送信 API: 種類が資料請求でない/物件の権限なし/メール設定なし/20MB 超/他の物件の添付 ID を混ぜる/ファイルが読めない/SMTP 失敗で状態が変わらない/成功で `done`+記録+宛先の保存/同じ鍵の2回目は送らない/同時2回。
- 文面: 差し込み4つ・既定の文面・担当者名が空。
- 画面: 資料請求の反響にだけボタン/謄本の黄色の注意/20MB 超で送信不可/0件で送信不可/失敗で入力が残る。
- 守りの走査テスト: 送信 API が `selectableForMaterialSend` を通さずに添付を読まないこと。

## 10. 資料・確認

- 使い方ガイド・マニュアルの「反響の受付」に「資料を送る」の節を足す(`public/docs` も同期)。
- 確認リストに追加: 自分のアドレス宛てに1通送る(ファイルが開ける・件名と本文・対応済みになる・記録が出る)/謄本の注意/20MB の止め。

## 11. やらないこと

- システムで作る販売図面の添付(発注者判断)。
- BCC・CC・複数の宛先。
- 送ったメールへの返信の取り込み。
- 予約送信・待ち行列。
