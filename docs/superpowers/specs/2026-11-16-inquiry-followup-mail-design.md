# 一括査定・査定申込のお客様への追客メール(ステップメール) 設計

2026-11-16 初版 → 2026-11-17 発注者のイメージで改訂。状態: 設計(発注者の承認待ち)。PR1〜PR3 に分ける。

## 0. 決まっていること

### 0.1 発注者のイメージ(2026-11-17)

- 一括査定の物件の登録があった時点で、自動で挨拶メールを送る
- 3日経っても連絡がついていなければ、もう一度追客する
- 1週間後・1カ月後・3カ月後・半年後にフォローメールを送る
- 保留になったお客様にも送る

### 0.2 発注者の選択(2026-11-17)

- 送る相手は一括査定と査定申込の両方
  - 一括査定=貼り付け・Excel で登録し、導入ルートが「一括査定」の物件。その所有者のメールに送る
  - 査定申込=`DmInquiry`。手紙の QR・広告のページから来たもの
- 「連絡がついていない」は、案件の状態が「未着手」か「コンタクト中」かで判断する
- 1週間〜半年のフォローは「連絡がつかない人」と「保留」にだけ送る。やりとり中・査定中の人には担当が直接連絡するので送らない
- 保留のフォローは、保留になった日から数え直す。保留用に別の文面の流れを持つ

### 0.3 最初の依頼(2026-11-16)から変わらないこと

- 送信は今の SMTP を使う(`sendPlainMail`・`MailConfig`)。外部のサービスや依存は足さない
- 受付メールの考え方を踏襲する
  - 文面に申込者の入力を差し込まない
  - 取り合い(`updateMany`)で二重に送らない
  - 監査は定型コードだけを残す
- 初期状態は追客 OFF
- 法律対応(送信者の表示・配信停止)と安全策を入れる
- 新しい権限は作らない

### 0.4 最初の依頼から変えたこと

- 最初の依頼は「所有者(`Owner.email`)には送らない」だった。発注者のイメージで、一括査定の所有者に送ることになった
- 一括査定のお客様は、査定会社から連絡を受けるためにアドレスを出している。このため特定電子メール法の「自分のアドレスを通知した人」として扱える見込み
  - ⚠査定サイトの規約に「参加会社から連絡が来る」旨があるかは、発注者が確かめる
  - 末尾の表示と配信停止は、どちらの場合も必ず付ける

## 2. 送る流れ(2本)

### 2.1 「新規」の流れ(起点=登録日)

| 通 | 日数(例) | 送る相手 |
|---|---|---|
| 挨拶 | 0日=登録の直後(15分以内) | 一括査定の全員。査定申込は送らない(受付メールが挨拶を兼ねる) |
| 再追客 | 3日 | 連絡がついていない人だけ |
| フォロー | 7日・30日・90日・180日 | 連絡がついていない人だけ |

「連絡がついていない」の判定:
- 一括査定: 案件の状態が「未着手」か「コンタクト中」
- 査定申込: 対応状況が「未対応(open)」(査定申込には案件の状態が無いため)

### 2.2 「保留」の流れ(起点=保留になった日)

| 通 | 日数(例) | 送る相手 |
|---|---|---|
| 保留フォロー | 7日・30日・90日・180日 | 案件の状態が「保留」のままの人 |

- 一括査定の物件だけが対象(査定申込には保留が無い)
- 保留になると「新規」の流れは止まり、「保留」の流れが始まる
- 保留になった日は、定期実行が「保留」に変わったのを見つけた時刻にする(最大15分の遅れ)。状態を変える画面には手を入れない

### 2.3 状態ごとの扱い(送る直前に毎回確かめる)

| 状態 | 扱い |
|---|---|
| 未着手・コンタクト中 | 「新規」の通を送る |
| やりとり中・査定中 | その通は**飛ばす**(あとで状態が戻っても、過ぎた通は送らない)。次の通の日にまた確かめる |
| 保留 | 「保留」の流れに移る |
| 商談中・媒介取得〜決済・他社で決まった・見送り・除外申請中・除外 | **終わり**(止まった理由を記録) |
| 査定申込が対応中(in_progress) | その通は飛ばす |
| 査定申込が対応済み(done) | 終わり |

- 日数は「通ごとに登録」とする。文面と日数は発注者があとで決める
- 初期状態は追客 OFF・文面は空。上の日数(0・3・7・30・90・180/7・30・90・180)を枠として最初から入れておき、件名と本文は空にする。ON にするには、全部の通に件名と本文が入っている必要がある(枠は消したり足したりできる)

## 3. 安全策・止まる条件

### 3.1 始める条件

**一括査定**
- 導入ルートが「一括査定」
- 物件の登録日時が「追客を ON にした時刻」より後
- 所有者のメールがある
  - 所有者が複数のときは、物件の最初の所有者のうちメールがある1人
  - 同じ人(同じアドレス)の物件が複数あっても、追客は1本だけ

**査定申込**
- 受付メールが届いた申込(`autoReplyStatus='sent'`)
- ON にした時刻より後の申込
- 対応済みではない

**共通**
- 配信停止されたアドレスではない
- 同じアドレスで進行中の追客が無い(アドレス単位の advisory lock+部分 UNIQUE)

### 3.2 送るとき

- 1アドレスへは1日1通まで
- 送るのは 9:00〜20:00(日本時間)の実行だけ
- 1回の実行で送る上限は既定20通(env で変えられる)
- 1通ごとに `active → sending` の `updateMany` で取り合い、勝った1回だけが送る
- 成功したら次の通へ進む。失敗したら止める(送り直さない)
- `sending` のまま30分を過ぎた行は止める(途中で落ちた=届いたか分からないので送り直さない)

### 3.3 止まる条件(理由を記録する)

| 理由のコード | 意味 |
|---|---|
| `unsubscribed` | 配信停止 |
| `case_closed` | 状態が商談中以降・他社・見送り・除外 |
| `handled_done` | 査定申込が対応済み |
| `manual` | 担当が「追客を止める」を押した |
| `send_failed` | 送信の失敗 |
| `interrupted` | 送信の途中で落ちた |
| `disabled` | 追客を OFF にした。ON に戻しても再開しない |
| `no_address` | 所有者のメールが消された |
| `completed` | 全部送り終えた |

## 4. テーブル案(migration 1本・足すだけ)

migration 名は `20261117000000_lead_followup_mail`(PR1 で実装済み)。

1. `mail_config` に列を足す
   - `followup_enabled` boolean DEFAULT false
   - `followup_enabled_at` timestamptz
   - `followup_version` int DEFAULT 0(設定の版番号=同時に2人が直したら 409)
2. `lead_followup_steps`
   - 列: `id`・`series`(`new`|`hold`)・`position`・`delay_days`(0〜365。0 は new の1通目だけ)・`subject`(120字)・`body`(4000字)・`updated_at`/`updated_by_id`
   - 決まり: UNIQUE(series, position)。各流れ最大10通。日数は後の通ほど大きい
   - 保存は全部を置き換える。版番号の 409 で、同時に2人が直したことを知らせる
3. `lead_followups`(追客の対象1件に1行)
   - 列:
     - `id`
     - 対象: `target_type`(`property`|`inquiry`)・`property_id`/`inquiry_id`(CHECK でどちらか1つ。それぞれ UNIQUE)
     - 宛先・状態: `email_normalized`・`status`(active/sending/completed/stopped)・`stop_reason`
     - 新規の流れ: `new_started_at`・`new_next_position`
     - 保留の流れ: `hold_started_at`・`hold_next_position`
     - 時刻: `last_sent_at`・`claimed_at`・`stopped_at`/`stopped_by_id`・`created_at`/`updated_at`
   - index:
     - 部分 UNIQUE(email_normalized) WHERE status IN (active, sending)
     - (status)
     - (email_normalized)
4. `lead_followup_sends`
   - 列: `id`・`followup_id`・`series`・`position`・`result`(sent/failed/skipped)・`subject`(件名の控え)・`at`
   - UNIQUE(followup_id, series, position)
   - 「飛ばした」も記録する。何通目を飛ばしたかが画面で分かるように
5. `mail_unsubscribes`
   - 列: `email_normalized` UNIQUE・`source`・`followup_id`(SET NULL)・`created_at`

保留を出たり入ったりしたとき: 「保留」の流れは1件につき1回だけ。もう一度保留になったら、前の続きの通から、その日を新しい起点にして数える。

## 5. 法律対応(特定電子メール法)

外向きの URL は売却DM設定の「追跡の土台 URL」(`trackingBaseUrl`)だけを使う(社内向けの `appBaseUrl` はお客様が開けないので使わない)。物件・申込を消したら追客の行も消える(CASCADE)が、配信停止の記録は残る(SET NULL)。

末尾には次の文を自動で付ける。本文の欄からは消せない。

```
──────────────
送信者: {会社名}
住所: {住所}
お問い合わせ: {電話} / {メール}
このメールは査定のお申し込みをいただいた方にお送りしています。
今後のご案内が不要な場合は、こちらから配信を停止できます:
{配信停止の URL}
```

- 1通目(挨拶、査定申込では最初のフォロー)だけ、その前に「お心当たりのない場合は、お手数ですが下の配信停止を押してください。」を足す
- 会社の名前・住所・問い合わせ先・外向きの URL が欠けていたら、送らない。ON の保存も断る
- 配信停止のリンクは `/u/f<32桁16進>.<署名22字>` の形
  - HMAC の作り方は今の配信停止の鍵と同じで、ラベルだけ別にする
  - GET は確認の画面だけを出す。POST で、アドレス単位の停止を記録し、そのアドレスの追客を全部止める
  - レート制限と Origin の確認は今の `/u/` と同じにする

### 8.1 PR3 の実装で決めたこと(2026-11-17)

- 実行口 `POST /api/lead-followup/run`(合言葉 `LEAD_FOLLOWUP_RUN_SECRET`・ヘッダー `x-lead-followup-run-secret`・未設定は 503 で休眠)。timer=`deploy/systemd/pm-lead-followup.*.example`(前回の終わりから15分)。nginx で外からは 404。手順=`docs/deploy.md`「追客メールの送信」
- 判断は純関数 `src/lib/lead-followup/decide.ts`、DB の読み書きは `run.ts`
  - 古い案件の状態(今は使わない値)・知らない値は「飛ばす」。`done` は終わり
  - 新規の流れを終えたとき保留でなければ完了。保留になったら新規の流れは終わり(`new_next_position=999` の印)、保留の流れの起点=見つけた時刻
  - 保留を出たら起点を外して待つ(新規の流れには戻らない)。もう一度保留になったら続きの通から、その時刻を起点に
  - 次の通の日も過ぎていたら、古い通は飛ばす(止まっていた間の分をまとめて送らない)
- 始めるとき: 配信停止のアドレスは `unsubscribed`、同じアドレスで進行中の追客があれば `duplicate_address`(新しい理由)、アドレスの形がおかしければ `no_address` の止めた行として作る(毎回見直さないため)。物件はメールのある所有者(終わっていない所有者・主たる所有者→登録順)がいるものだけを探す
- 見回りで止める: 物件・申込が消えた=`target_deleted`(新しい理由)/アドレスが無くなった・変わった=`no_address`/配信停止=`unsubscribed`
- 送る: アドレス単位の鍵の下で配信停止と「直近20時間に同じアドレスへ送ったか」を見て、`active→sending`(進み具合も条件)。送ったら記録を必ず残し、行の書き戻しは `sending` のときだけ
- 1通目(その追客で最初に送る通)だけ「お心当たりのない場合は…」を付ける。配信停止のヘッダー(List-Unsubscribe と One-Click)を付ける。`/u/` の POST は Origin なしを受けるので、Gmail などのボタンからそのまま止まる
- 画面で ON→OFF にしたら、進行中(送っている途中も)を `disabled` で止める(ON に戻しても再開しない)。実行でも OFF なら止める
- 監査 `lead_followup_send`(result・series・position・失敗のときは定型の code だけ)
- 持ち時間: 新しい送信・新しい行の判断は呼ばれてから150秒まで(curl は240秒・1通は最大およそ45秒)
- 内部レビューで足した守り:
  - 送信に失敗したら、その回はもう送らない(メールサーバーの不調で大勢を一度に止めない)。接続・認証の段階の失敗(確実に送っていない)は止めずに進行中へ戻し、次の回にもう一度
  - 送る直前(鍵の下)に ON を確かめ直す(実行の途中で OFF にされた場合)
  - 保留の流れを全部終えていれば、今の状態に関わらず完了(進行中のまま残ってアドレスを塞がない)
  - 見る順は長く見ていない行から。上限(2000)に当たっているときは、待つ行の時刻を進めて後ろへ回す
  - 1行の判断で例外が出ても残りは続ける(件数だけ数える)
- @codex の指摘で足した守り:
  - 行を作る・送る直前に、設定の行を `FOR UPDATE` で押さえて「今も ON で、この実行が見た ON の期間のままか」を確かめる。画面の OFF の保存も同じ行を書き換えるので順番がそろい、探している最中に OFF にされても進行中の行が残らない
  - 送った時刻(`last_sent_at`)は行の状態に関わらず残す(送信中に止められた行でも、同じアドレスへの「20時間に1通」が効く)
