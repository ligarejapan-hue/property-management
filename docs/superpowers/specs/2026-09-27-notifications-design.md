## 0. ひとことで

通知を2つの仕組みに分ける。

- **A. 画面から出す通知**: 開いている画面自身が、ブラウザの通知機能（Notification API）で PC／スマホの通知欄に出す。編集権限が外れる・自動ログオフされる、の予告に使う。サーバー・DB は変えない。
- **B. サーバーから送る通知（Web プッシュ）**: サーバーが期限を見張り、登録された PC／スマホへ送る。画面を閉じていても届く。次回対応・査定申込・その他の期限に使う。DB・依存・VPS の定期実行が要る。

通知の本文には**種類と件数だけ**を載せ、物件名・所有者名・住所などは載せない。詳しくは通知を押して開いた画面で、今の権限どおりに見る。

## 4. 段階1: 画面から出す通知（A）と画面内の土台

### 4.1 通知の許可

- 通知には利用者ごとの**ブラウザの許可**が要る。ページを開いた瞬間には求めない（多くのブラウザが嫌う・拒否されやすい）。
- 右上のベルを開いたときの「PC・スマホにも通知する」ボタン（利用者の操作）から許可を求める。
- 許可が無い・拒否された・対応していないブラウザでは、**画面内のポップアップだけ**で知らせる（機能は失わない）。
- OS の通知は `new Notification()` ではなく、**Service Worker の `registration.showNotification()` で出す**（§4.5）。Android の Chrome は前者を使えず、iPhone のホーム画面アプリも後者が前提のため。

### 4.2 N1・N2（編集権限）

- 予告の時刻・外れた判定は、今の編集ロックの仕組み（`EDIT_LOCK_IDLE_WARN_MS`=55分・`ui-state.ts` の状態）をそのまま使う。**鍵の規則は変えない**。
- 画面内の帯（今ある予告）は残し、**そのタブが見えていないとき（`document.hidden`）だけ** OS の通知も出す。見えているときは帯だけ（二重に出さない）。
- 同じ通知が何度も出ないよう、通知に `tag`（例 `edit-lock:<資源の種類>:<資源ID>`）を付ける。⚠資源IDは UUID のみ（PII ではない）。

### 4.3 N3（自動ログオフ）

- 今の `idle-session-guard` は**予告なしで**ログアウトする。55分の時点で「まもなくログオフします」を出す処理を足す。
  - 画面内: 「あと5分で自動ログオフします [続ける]」のダイアログ（押すと操作とみなして延長）。
  - タブが見えていないとき: OS の通知も出す。
- 60分でログアウトする規則・延長の仕組みは**変えない**。
- 複数タブ: 最終操作時刻は今も `localStorage` でタブ間共有している。通知は `tag: "idle-logout"` で1つにまとめる。

### 4.4 画面内の土台

- 右下のポップアップ（トースト）と、右上ヘッダーのベル（未確認の件数）を共通部品として作る（`src/components/ui` に追加）。
- 見た目は `/ui-design` の手順で、実装前に HTML イメージで承認を取る。
- 動き: 表示時に軽く出てくる程度。`motion-reduce` で止める。

### 4.5 iPhone の制約

- iPhone（Safari）の通知は、社内システムを**ホーム画面に追加して開いた場合のみ**使える（iOS 16.4 以降）。ブラウザのタブで開いた場合は、画面内のポップアップだけになる。
- ホーム画面に追加できるようにする設定（Web アプリの名前・アイコンの定義 = manifest）は、D13 を受けて**段階1で入れる**（依存追加なし・ファイルの追加のみ）。
- あわせて、通知を表示する受け取り役 **Service Worker（`public/sw.js`）も段階1で入れて登録する**。manifest だけでは iPhone で通知を出せないため（Codex #451 指摘）。段階1の Service Worker は「通知の表示（`showNotification` の呼び出し元は画面）」と「通知を押したときに該当画面を開く（`notificationclick`）」だけを持つ。サーバーからの受信（`push`）は段階4で足す。
- ⚠Service Worker はページの読み込みを横取りしない（`fetch` を扱わない・キャッシュしない）。オフライン対応は対象外。
- ⚠**共用 PC での後片付けも段階1で入れる**（Codex #451 指摘・P1）。段階1から N1〜N3 を OS の通知として出すので、段階4を待つと、前の人の通知が通知欄に残って次の人に見える。
  - ログアウトのとき（自動ログオフを含む）とログイン画面を開いたときに、Service Worker の `registration.getNotifications()` で本システムが出した通知を取り出し、すべて `close()` する。
  - ⚠**表示の依頼と後片付けを段階1から同じ順番待ちに並べる**（Codex #451 指摘・P1）。画面は `registration.showNotification()` を直接呼ばず、N1〜N3 の表示も後片付けも `postMessage` で Service Worker に頼む。Service Worker はどちらも**1本の Promise の列で1件ずつ**処理する（`event.waitUntil` は各処理を最後まで動かすだけで、処理どうしを直列にはしないため）。失敗しても列が止まらない作り（§7.5 と同じ `queue.then(task).catch(記録して続行)`）にする。
  - ⚠**切り替えの世代**: Service Worker は「切り替えの世代」（整数。IndexedDB に保存）を持ち、後片付けのたびに1つ増やす。各タブは開いたときに今の世代を受け取り、表示の依頼に付けて送る。Service Worker は**世代が今と違う依頼は表示しない**（前の人のまま開いていた古いタブが、切り替えの後に N1〜N3 を出さないようにするため）。後片付けの後、Service Worker は開いている全タブに「切り替わった」と知らせ、古いタブは通知の処理を止める。
  - 画面は後片付けの返事を最大3秒待つ。返事が失敗・時間切れのときは、画面から直接、**先に IndexedDB の世代を1つ上げてから** `getNotifications()` → `close()` を行う。世代を上げられなかったら後片付けは失敗として扱う（下のとおりログインに進まない）。
  - ⚠**表示のたびに、表示のあとで世代を読み直す**（Codex #451 指摘・P1）。返事が3秒を超えるのは、前に並んだ表示（`showNotification()`）がまだ終わっていないときがあり、画面からの直接の後片付けがそれを追い越すと、通知欄が空に見えてログインに進んだあとで前の人の通知が出てしまう。そこで Service Worker は各表示の `showNotification()` が終わったあと IndexedDB の世代を読み直し、**表示に使った世代と違えば、その通知をすぐ `close()` する**。直接の後片付けは先に世代を上げているので、追い越された表示も出た直後に自分で閉じる。
  - ⚠**通知を閉じられたことを確認できなかったら、ログインに進まない**（Codex #451 指摘・P1）。Service Worker の返事も、画面からの直接の `getNotifications()` も失敗した場合は、すでに出ている前の人の通知が残っている可能性があるため、「通知を消せませんでした。ブラウザを閉じて開き直してからログインしてください」と出して止める（まれな場合。PII は出さない）。段階4の `binding_id` の確認（§7.5）とは別の条件で、両方を満たしたときだけ進む。
  - 段階4では、この順番待ちに `push` の処理と `binding_id` の消去などを足す（§7.5）。

### 4.6 段階1の予告通知が届かない場面（Codex #451 指摘）

段階1の N1〜N3 は**画面の中の処理が動いている間だけ**出せる。次の場面では画面の処理が止められ、予告の時刻になっても OS の通知は出ない。

- iPhone・Android でアプリ（ホーム画面アプリ・ブラウザ）を裏に回した、または画面をロックした
- PC でブラウザを閉じた・PC がスリープした

これを補うため、次の2つを入れる。

1. **戻ったときの知らせ（段階1）**: 画面に戻った（`visibilitychange` で見える状態になった）ときに、今の状態を確かめ直し、編集権限が外れていた・ログオフされていた場合は画面内で理由をはっきり出す（「無操作が60分続いたため、編集権限が外れました」など）。保存前の入力がある場合はその旨も出す。
2. **外れたことをサーバーから送る（段階4）**: 画面が止まると合図（heartbeat）が止まり、編集の鍵は**既存の規則どおり5分で外れる**（D4・`expiryCause` は合図の期限を先に判定する）。そのため、画面が止まった端末に「55分で外れます」という予告は成り立たない（Codex #451 指摘）。代わりに、**鍵が外れたこと（N2）をサーバーから Web プッシュで送る**。
   - ⚠鍵の行は、別の人が取り直すと `acquireEditLock` の UPSERT で ID・持ち主・時刻がまるごと書き換わる（`src/lib/edit-lock/service.ts`）。定期実行が鍵の表を後から見るだけでは、前の持ち主が分からず知らせ漏れる（Codex #451 指摘）。そこで、**外れた事実を別の表 `edit_lock_loss_events` に残し**、定期実行はこの表だけを見て送る（§7.2）。
   - 記録する場面は3つ。いずれも鍵の行の ID（取るたびに新しくなる）を一意キーにして、同じ「1回の持ち時間」を二重に記録しない。
     1. 取り直し（`acquireEditLock`）で、別の画面の期限切れの鍵、または管理者に外された鍵を上書きするとき。**上書きと同じトランザクションで**、上書き前の持ち主を記録する。
     2. 管理者が外したとき（`force-release`）。外すのと同じトランザクションで記録する。
     3. 期限を過ぎたまま誰にも取り直されていない鍵。定期実行が見つけて記録する。
   - 定期実行は、まだ知らせていない記録について、持っていた利用者に「編集権限が外れました」を送り、送った時刻を記録に残す。
   - 鍵の規則（5分・60分・55分の予告）は**変えない**。
   - 自動ログオフの予告（N3）は、最後の操作時刻をサーバーが持っていない（ログインの有効期限は cookie 側で延長している）ため、サーバーから正確に送れない。**N3 は画面が動いている間のみ**とし、戻ったときの知らせで補う。

| 通知 | PC（ブラウザ起動中） | スマホ（アプリを開いている） | スマホ（裏に回した・ロック中） |
|---|---|---|---|
| N1 編集権限の予告 | 段階1から出る | 段階1から出る | 出ない（画面が止まると5分で鍵が外れる既存の規則のため、予告の場面が無い） |
| N2 編集権限が外れた | 段階1から出る | 段階1から出る | 段階4からサーバー送信。戻ったときにも画面内で出す |
| N3 自動ログオフの予告 | 段階1から出る | 段階1から出る | 出ない。戻ったときに画面内で出す |

## 5. 段階2: 画面内で N4・N6・N7 を出す（DB 変更なし）

### 5.1 窓口（API）

`GET /api/notifications/summary?inquiryCursor=<時刻,ID>&registryCursor=<時刻,ID>`（新設・読み取りのみ）。応答は**件数と ID・時刻だけ**。

```json
{
  "nextActionToday": 3, "nextActionOverdue": 1,
  "nextActionReminders": [{ "key": "不透明な値（actionId・deadline・rev・slot から作る）", "slot": 4 }],
  "openInquiries": 2, "newInquiryIds": ["不透明な値"], "inquiryCursor": "不透明な文字列（中身は (submittedAt, id)）",
  "registryJobsCompleted": [{ "jobKey": "不透明な値", "done": 12, "failed": 1, "skipped": 2, "chargedButFailed": 1 }], "registryCursor": "不透明な文字列"
}
```

- 次回対応:
  - `nextActionToday` / `nextActionOverdue`: どちらも `assignedTo = 自分` かつ `isCompleted = false`。`nextActionToday` は **`scheduledAt = 今日`**、`nextActionOverdue` は **`scheduledAt < 今日`**（どちらも**日本時間の今日**。`scheduledAt` は日付型）。同じ件を両方に数えない（Codex #451 指摘）。ベル・ホームの件数に使う。
  - `nextActionReminders`: 自分の未完了の次回対応のうち、**今が §7.4 の送信予定のどれかの回に当たっているもの**と、その回の番号（`slot`）。回の計算は §7.4 の純関数（`nextActionReminderSlot(期限T, 今)`）を段階2と段階4で**共用**する。段階2では時刻の欄が無いので T＝予定日の9:00。1週間を過ぎたものは含めない。
  - 権限は今の次回対応 API（`GET /api/properties/[id]/next-actions`）と**同じ2段**で確認する（Codex #451 指摘・P1）: ① `property:read`、② 物件の担当範囲（`assertPropertyRecordAccess` と同じ規則。field_staff は親の物件の `createdBy` か `assignedTo` が自分のものだけ）。一覧の問い合わせでは `propertyRecordScopeFilter(session)` を `property` 条件に畳み込む。次回対応の担当が自分でも、親の物件の担当から外れていれば数えない・送らない。
- 査定申込（Codex #451 指摘: 件数の増減では「1件完了＋1件新着」を見逃す）:
  - `openInquiries`: `handleStatus = "open"` の件数（ベル用）。
  - `newInquiryIds`: カーソルより後に届いた申込の ID。カーソルは**時刻と ID の組** `(submittedAt, id)` で、辞書順で比べる。時刻だけだと同じミリ秒の2件目を取りこぼすため（Codex #451 指摘）。
    - ⚠既存の `inquiryCursorWhere`（`inquiry-list.ts`）は一覧を**古い方へ**めくるための条件（`submittedAt < t`、同時刻なら `id < i`）なので、**そのまま使わない**（Codex #451 指摘）。新着は**逆向き**に取る: 「カーソルより後」は `submittedAt > t OR (submittedAt = t AND id > i)`。実際の問い合わせは下の読み直しのため `submittedAt >= t − 5分` で取り、`(submittedAt, id)` の**昇順**に並べる。次のカーソルは **「受け取ったカーソル」と「返した中の最大の `(submittedAt, id)`」の大きい方**にし、決して戻さない（Codex #451 指摘）。読み直し範囲（5分前〜カーソル）の古い行だけが返ったときにカーソルを後ろへ戻すと、同じ行を読み直し続け、見た ID を捨てたあとで新着として出してしまうため。カーソルの読み書き（`encode`／`decode`）だけは既存と同じ形式を使う。
  - 遅れて保存された行（時刻はカーソルより前だが、前回の問い合わせの後に確定した行）を取りこぼさないよう、**カーソルの5分前から**読み直し、画面側で見た ID と照らして重複を除く。見た ID は1日分だけ残す。
  - 範囲は申込一覧 API と同じ `requireSaleDmAccess` と担当範囲。`newInquiryIds`（ポップアップ・プッシュの元）は、さらに `inquiryNotifyEnabled = true` の人にだけ返す（`isActive` も確認）。
- 謄本の一括取得: `requestedById = 自分` かつ `status = "completed"` で、カーソル `(completedAt, id)` より後のもの（`completedAt > t OR (completedAt = t AND id > i)` の向き。読み直しと重複除去、次のカーソルを戻さない決め方も申込と同じ）。
  - ⚠件数（`done`・`failed`）は、ジョブの集計列をそのまま返さない。既存の `getBulkJobProgress` と同じく、**項目ごとに `canAccessPropertyRecord` で今見られる物件だけに絞って数え直す**（Codex #451 指摘・P1。field_staff の担当から外れた物件の結果を出さない）。見られる項目が1件も無いジョブは通知しない。段階4の送信も同じ関数を使う。
  - 件数は `done`・`failed` だけでなく、既存の `BulkJobCounts`（`recomputeCounts`）と同じく **`skipped`（要手動）と `chargedButFailed`（要確認：課金されたが取得に失敗）も別に返す**（Codex #451 指摘）。「成功1件・失敗0件」のように見えて実は要確認がある、という誤解を防ぐ。`chargedButFailed` が1件以上あれば、通知の文言でも「要確認」を必ず出す。
- **物件名・住所・申込者名など PII は返さない**（ID は UUID のみ）。

### 5.2 取りに行く間隔

- 画面を開いている間、**60秒ごと**と、タブが見える状態に戻ったときに取りに行く。見えていないタブでは間隔を延ばす（ブラウザも自動で遅くする）。
- ポップアップを出す条件（件数の増減では判定しない）:
  - 次回対応: `nextActionReminders` に**まだ見ていない `(actionId, deadline, rev, slot)` の組**が現れたとき。同時に複数あれば1つのポップアップにまとめる。
  - 査定申込: `newInquiryIds` に、まだ見ていない ID があるとき。表示後、`inquiryCursor` と見た ID を保存して次回に使う。
  - 謄本: `registryJobsCompleted` に、まだ見ていないジョブがあるとき。同様に `registryCursor` を保存する。
- ⚠`rev`（担当と期限の版）を組に含めるのは、担当者が A→B→A と戻ったとき、期限が同じでも A さんへの繰り返しを数え直すため（Codex #451 指摘）。`rev` は担当者または期限を変えた時刻。段階3の migration で `next_actions` に `reminder_rev_at` を追加し、それを使う（埋め方と更新方法は §6。段階2の値と一致させ、DB 側で更新する）。段階2（まだ列が無い）では `updated_at` で代用する（担当以外の編集でも今の回が1回出直すことがあるが、実害は小さい）。
  - ⚠`rev` は担当者だけでなく**期限（予定日・時刻）を変えたときにも進める**（Codex #451 指摘）。期限を T→T2→T と戻すと、`deadline` が同じ値に戻り、担当も同じなら組が最初の予定と完全に一致して、やり直した予定の通知が抑えられるため。段階3の列は、担当と期限の両方の変更で進むことが分かるよう `reminder_rev_at` という名前にする。段階2の `updated_at` は期限の変更でも進むので、そのままでよい。
  - ⚠`rev` は**秒に丸めず、DB の時刻をミリ秒まで含めた ISO 文字列**で返す（Codex #451 指摘）。秒単位だと、同じ秒の中で A→B→A と担当が変わったとき同じ `rev` になり、出直すはずの回が抑えられるため。段階3のトリガー（§6）は `reminder_rev_at` を**必ず前の値より大きく**する（`GREATEST(clock_timestamp(), 前の値 + 1ミリ秒)`）ので、同じ行で `rev` が重なることはない。段階4の `ref_key` も同じ値（エポックミリ秒）を使う。
- ⚠`deadline`（期限 T）を組に含めるのは、予定日・時刻を変えても次回対応の ID は変わらず、回の番号も新しい期限から数え直しになるため（Codex #451 指摘）。期限を含めないと、変更前に見た組が変更後の通知を抑えてしまう。
- 見た `(actionId, deadline, rev, slot)` の組とカーソルは端末の `localStorage` に置く（利用者IDごと。段階2では DB に既読を持たない）。初めて開いた端末（カーソルを持っていない）は、カーソルを付けずに問い合わせ、サーバーは初期カーソルと一緒に**読み直し範囲（初期カーソルの5分前から）にすでにある出来事の ID（`initialSeenIds`）**も返す。端末はこれを「見た ID」として最初から持っておく。こうしないと、次の問い合わせで5分前から読み直したときに、初期化より前の出来事を新着として出してしまう（Codex #451 指摘）。初期化の時点でまだ確定していなかった行は `initialSeenIds` に入らないので、遅れて確定した新着は正しく出る。**サーバーが返す初期カーソル（サーバーの時計での「今」と、ID には正しい形式の境界値 `00000000-0000-0000-0000-000000000000`）**をそのまま保存する。ID を空にすると、既存の `decodeInquiryCursor`（ID が UUID の形でないと受け付けない）で読めず、DB の UUID 列とも比べられないため（Codex #451 指摘）。カーソルの読み書きは既存の `encode`／`decode` と同じ形式（base64url の JSON）にし、読めないカーソルが来たときは**初期化とみなさず 400 を返す**（黙って初期化すると、その間の新着を取りこぼすため）。過去の分はまとめて出さない。端末の時計はカーソルに使わない（端末の時計がずれていると、新着を取りこぼしたり古い分を出したりするため。Codex #451 指摘）。見た組は1週間を過ぎたものから捨てる。
- ⚠共用 PC では、利用者IDごとに分けて置くだけでは、次の人が同じブラウザから前の人の次回対応の ID・期限・申込 ID・謄本ジョブ ID を読めてしまう（担当範囲外のものを含む。Codex #451 指摘）。そこで**ログアウトのとき（自動ログオフを含む）、ログイン画面を開いたとき、ログインの送信前に、本システムの通知用の `localStorage` の値を（どの利用者の分も）すべて消す**。§7.5 の `binding_id` を消すのと同じ箇所で行う。
  - ⚠**古いタブが消したあとに書き戻さないようにする**（Codex #451 指摘・P1）。前の人のタブが開いたままだと、消す前に出した問い合わせの結果が消した後に返り、前の人の情報を `localStorage` に書き戻してしまう。そこで2つの守りを入れる。
    - **切り替えの世代**（§4.5 と同じ考え方）を `localStorage` にも置き、消すときに1つ増やして `BroadcastChannel` で全タブに知らせる。各タブは開いたときの世代を覚えておき、**書く直前に（同じ処理の中で）今の世代と比べ、違えば書かずに問い合わせを止める**。
    - **そもそも生の ID を置かない**。サーバーは、次回対応・申込・謄本ジョブの「見たかどうか」の判定用に、生の ID ではなく**利用者ごとの鍵で作った不透明な値**（HMAC-SHA256。鍵は既存の配信停止トークンと同じく `NEXTAUTH_SECRET` から HKDF で用途別に導出し、新しい env は足さない）を返す。カーソルもサーバーが暗号化・改ざん防止をかけた不透明な文字列で返す（中身の時刻と ID は画面から読めない）。画面はこの不透明な値だけを保存する。これで、書き戻しが起きても次の人には前の人の ID・期限が読めない。
    - これに合わせ、§5.1 の応答の `actionId`・`newInquiryIds`・`jobId`・`initialSeenIds` とカーソルは、判定用には不透明な値を使う（画面の遷移に ID が要る場面は、ポップアップを押したときにサーバーから取り直す）。
  - 消したあとの最初の問い合わせは「初めて開いた端末」と同じ扱いになり、`initialSeenIds` で過去の出来事は出さない。次回対応の今の回だけは、ログインし直したあとに1回出直すことがある（見落とし防止の側に倒す）。

## 6. 段階3: 次回対応に時刻の欄（DB 変更あり）

- `next_actions` に `scheduled_time`（時刻・NULL 可）と `reminder_rev_at`（担当者または期限（予定日・時刻）を変えた時刻。§5.2 の `rev`）を**追加のみ**。既存の行は NULL のまま＝今までどおり日付だけ。
- 次回対応タブの入力に「時刻（任意）」を追加。
- 通知: 時刻がある行は**その時刻の5分前**（D8）に N5 を出す。時刻が無い行は N4 のまま**当日9:00**に送る（D16）。
- rollback: **アプリだけを前の版に戻し、列は残す**（追加の列なので前の版は無視して動く）。列を消すと、利用者が入力した時刻が失われるため（Codex #451 指摘）。どうしても消す場合は、事前に `id` と `scheduled_time` を書き出して保存し、戻し方の手順を用意してから消す。
- ⚠`reminder_rev_at` は、段階2から段階3へ移るときと、アプリを戻したときに `rev` がずれないようにする（Codex #451 指摘）。
  - **既存行は `updated_at` で埋める**（`created_at` ではない）。段階2は `rev` に `updated_at` を使っているので、反映の前後で同じ件の `rev` が変わらず、今の回が二重に出たり、古い組と重なって抑えられたりしない。
  - **更新は DB のトリガーで行う**（`BEFORE INSERT` で `now()`、`BEFORE UPDATE` で `assigned_to`・`scheduled_at`・`scheduled_time` のどれかが変わったときだけ `GREATEST(clock_timestamp(), 前の値 + 1ミリ秒)`。同じ行の `rev` が重ならないよう必ず増やす）。アプリのコードに頼らないので、アプリだけを前の版に戻しても（前の版は `reminder_rev_at` を知らない）担当替えのたびに正しく更新される。トリガーは同じ migration で作り、rollback でも残す（列と同じ扱い）。
  - ⚠**migration の中の順番を「表を書き込み止めにする → 列を足す → トリガーを作る → 既存行を埋める」にし、1つのトランザクションで行う**（Codex #451 指摘）。反映中も前の版のアプリは動いているので、トリガーより先に埋めると、その間に担当が変わった行は `updated_at` だけ進み `reminder_rev_at` が古いまま残る。最初に `LOCK TABLE next_actions IN SHARE ROW EXCLUSIVE MODE` で書き込みを待たせ（読み取りは止めない。件数は少なく数秒で終わる見込み）、トリガーを先に有効にしてから埋める。埋める `UPDATE` は `assigned_to` を変えないのでトリガーは動かず、`updated_at` も変えない。Prisma の migration は1ファイルを1トランザクションで流すが、実装時に確認し、そうでなければ SQL に明示する。
  - migration の適用からアプリの再起動までの短い間に担当・期限以外の編集があると、その件だけ `rev` が1回変わり今の回が1回出直すことがある（段階2で割り切ったものと同じ程度）。
- ⚠列の型（時刻だけの列にするか、日付と時刻を合わせた列にするか）は、既存の `scheduledAt`（日付型）との整合と並び替えへの影響を見て、実装前の計画で確定する。

## 7. 段階4: Web プッシュ（DB・依存・VPS の変更あり）

### 7.1 仕組み

1. 利用者が「PC・スマホにも通知する」を押す → ブラウザが通知の登録情報（宛先 URL と鍵）を作る → サーバーに保存。
2. サーバーの**定期実行**が数分ごとに期限を確認し、送るべき通知があれば登録先へ送る。
3. ブラウザ側の受け取り役（段階1で入れた Service Worker・`public/sw.js` に `push` の受信を足す）が通知を表示する。押すと該当画面を開く。

- ⚠**`push` を受けられる Service Worker が動いてから登録する**（Codex #451 指摘）。段階4を反映しても、開いたままのタブやホーム画面アプリでは段階1の Service Worker（`push` の受信が無い）が動き続けることがある。その状態で登録すると、届いた通知が黙って捨てられる。
  - Service Worker は画面からの問い合わせ（`postMessage`）に**版と対応機能**（例 `{ version: 4, push: true }`）を返す。画面は、動いている Service Worker が `push: true` を返したときだけ「PC・スマホにも通知する」を押せるようにし、登録（`pushManager.subscribe()`）とサーバーへの保存を行う。
  - 古い版が動いているときは `registration.update()` で新しい版を取りに行く。段階4の Service Worker は `install` で `skipWaiting()`、`activate` で `clients.claim()` を呼び、開いているタブを待たずに入れ替わる（`fetch` を扱わない作りなので、途中で入れ替わってもページの表示には影響しない）。入れ替わった後に版を確かめ直してから登録する。
  - 入れ替わりを確認できない間はボタンを押せなくし、「画面を再読み込みしてください」と出す。

- 送信先は、ブラウザ各社のプッシュ中継サービス（Google・Mozilla・Apple）。**本文は規格上暗号化されて**中継される。利用料はかからない見込み。接続は D14 で承認済み。
- ⚠外部サービスへの接続にあたるため、CLAUDE.md §17・§18.2 の事前承認の対象として扱った（D14 で承認済み。`web-push` の依存追加は実装時に改めて確認）。

### 7.2 データ（すべて追加のみ）

- `push_subscriptions`: `id` / `user_id` / `endpoint`（一意）/ `p256dh` / `auth` / `device_scope`（`shared` か `personal`・§7.5）/ `bound_at`（今の利用者に結び付いた時刻。付け替えのたびに更新）/ `binding_id`（結び付けごとの乱数。付け替えのたびに作り直す・§7.5）/ `expires_at` / `created_at` / `last_success_at` / `failure_count` / `revoked_at` / `revoked_reason`（`gone`（中継サービスが 404/410 を返した）・`logout`・`admin` など定型値）
  - `endpoint` と鍵は**秘密情報として扱う**。API の応答・ログ・AuditLog に出さない。
  - ⚠**保存する前に `endpoint` を確かめる**（Codex #451 指摘）。登録 API は画面から送られた値をそのまま信じない。細工した URL を登録されると、定期実行がサーバーから任意の宛先へ接続させられ（SSRF）、D14 で承認した接続先の範囲も超えてしまう。
    - `https:` のみ、ポートは既定（443）のみ、利用者名・パスワード付きの URL は拒否。
    - 接続先は**ブラウザのプッシュ中継サービスの許可リスト**に限る（例: `fcm.googleapis.com`、`updates.push.services.mozilla.com`、`*.push.apple.com`。**D14 で承認した Google・Mozilla・Apple に限る**。正確な一覧は実装時に各社の仕様で確認して定数にする）。IP アドレスを直接書いたもの、`localhost`、社内・リンクローカルの宛先は拒否する。
    - 送信時も同じ確認をもう一度行い、合わない登録には送らず無効にする（許可リストを後から狭めた場合や、確認の導入前の行に備える）。送信ではリダイレクトを追わない。
    - 拒否したときの応答・ログに URL 本体を出さない（定型のエラーコードのみ）。
    - ⚠Microsoft（`*.notify.windows.com`。Windows の Edge が使う）は D14 の承認に含まれていないため、許可リストに入れない（Codex #451 指摘）。その端末では登録を断り、画面に「このブラウザでは PC・スマホ通知を使えません（Chrome・Firefox を使ってください）」と出す。Edge に対応する場合は、Microsoft への接続を別途承認してから D14 を更新して追加する（§12）。
- `notification_deliveries`（端末に送る1通。まとめ方は §7.4）: `id` / `user_id` / `subscription_id` / `binding_id`（作ったときの端末の結び付け・§7.5）/ `kind`（N4 など）/ `scheduled_for` / `attempts` / `sent_at` / `status`（`pending`・`sent`・`failed`・`gone`）/ `last_error_code`（定型コードのみ）
- `notification_delivery_refs`（1通に含めた件）: `delivery_id` / `subscription_id` / `binding_id`（送ったときの結び付け・§7.5）/ `kind` / `ref_key`（例 `next_action:<ID>:<期限Tのエポック秒>:<rev（エポックミリ秒）>:<回>`（期限を変えたら別のキー）や `inquiry:<申込ID>`）。
  - **端末（登録）ごとに記録する**（Codex #451 指摘）。一意制約は端末ではなく**結び付け（`binding_id`）ごと**にする。共用 PC で A さんから B さんに付け替えたあと、A さんの時代の記録が B さんへの同じ件の通知を止めないようにするため（Codex #451 指摘）。`notification_delivery_refs` の一意制約 `(binding_id, kind, ref_key)` で、同じ端末に同じ件を2回含めないようにする。
  - ⚠一意制約だけでは、定期実行が2つ重なったとき両方が同じ `pending` の行を見て送ってしまう（Codex #451 指摘）。そこで**送る前に行を取り合う**。既存の査定申込メール通知（`notifyStatus` = `sending`・`notifyClaimedAt`・15分で残骸扱い）と同じ方式にする。
    - 列 `claimed_at` を足し、状態に `sending` と `cancelled` を加える。
    - 1文の `UPDATE ... SET status = 'sending', claimed_at = now() WHERE id = ? AND (status IN ('pending','failed') OR (status = 'sending' AND claimed_at < now() - 15分)) RETURNING id` で取れた処理だけが送る。取れなかった処理は送らない。送り直し（`failed` の行）も同じく取り合う。
    - 送信後に `sent`・`failed`・`gone` へ更新する。この更新は **`WHERE id = ? AND status = 'sending' AND claimed_at = <自分が取ったときの値>`** の条件付きにし、15分を過ぎて別の処理に取り直されたあとで元の処理が結果を上書きしないようにする（既存の査定申込メール通知と同じ。Codex #451 指摘）。送信の直後に処理が落ちた場合は、15分後に取り直されて1回多く届くことがある（本文は種類と件数だけなので実害は小さい。メール通知と同じ割り切り）。
  - あわせて、定期実行そのものも重ならないようにする（systemd の oneshot サービスは実行中に次を起動しない。cron を使う場合は `flock` で1本に絞る）。
  - PC は届いてスマホは一時的に失敗した、という場合も、**失敗した端末だけ**を次の実行で送り直せる（届いた端末には送り直さない）。送り直しはその回の次の予定時刻まで、最大3回。404/410 は `gone` にして登録を無効にする。
- `notification_source_cursors`（§7.3）: `source`（主キー。`inquiry`・`registry_job`）/ `cursor_t` / `cursor_id` / `updated_at`。段階4の migration で、反映時点のサーバー時刻と境界値 UUID の行を入れる。
- `edit_lock_loss_events`（§4.6）: `id` / `lock_id`（一意。外れた鍵の行の ID）/ `user_id`（外れた持ち主）/ `resource_type` / `resource_id` / `cause`（`heartbeat`・`idle`・`force_released`）/ `occurred_at` / `notified_at` / `status`（`pending`・`queued`・`expired`）
  - 鍵の規則（5分・60分）は変えない。記録を足すだけ。資源の中身（物件名・所有者名など）は入れない。
  - ⚠**端末ごとに分けてから締める**（Codex #451 指摘）。記録1件に `notified_at`・`status` が1組しかないため、PC とスマホの両方を持つ人では「1台目で送って締めると2台目に届かない」「1台が失敗して残すと成功した方にも送り直す」ことになる。そこで定期実行は、**1つのトランザクションの中で**、その人の送ってよい端末（§7.3 の `bound_at` の基準を満たすもの）ごとに `notification_deliveries` と `notification_delivery_refs`（`ref_key` = `edit_lock_loss:<記録ID>`）を作り、同じトランザクションで記録を `queued` にする。以降の送信・送り直しは端末ごとの送信記録が独立して行う（§7.2 の取り合い・送り直しと同じ）。送ってよい端末が無いときも `queued` にして締める。
  - 知らせ終わった記録は30日で消す。
- 通知の種類ごとの ON/OFF は**作らない**（D12）。設定用の列・表は不要。

### 7.3 定期実行

- VPS の **systemd timer**（または cron）で、数分ごとに送信スクリプトを `www-data` で実行する。HTTP の窓口を増やさないため、スクリプト方式を第一案とする。
- 既存の方針（謄本の一括取得は画面駆動で、サーバーに常駐のタイマーを置かない）と矛盾しないよう、**アプリのプロセス内に setInterval を置かない**。
- 送信に失敗して「もう存在しない」（HTTP 404/410）と返された登録は無効にする。
- 繰り返し送る通知（D9・D17）は §7.4 の送信予定に従い、`ref_key` に「何回目の送信か」を含めて各回1度だけ送る。完了（`isCompleted = true`）・削除・担当者の変更で止まる（担当者が変わったら新しい担当者の予定として数え直す）。
- 夜間・休日も止めない（D10）。
- **切り替え時点の基準（Codex #451 指摘）**: 段階4を初めて動かしたとき、過去の申込・完了済みの謄本ジョブには送信記録が無いため、そのままでは過去分を全部送ってしまう。逆に「直前の実行以降だけ」を見ると、定期実行が止まっていた間の分を落とす。そこで次の2つの基準を持つ。
  - **発生源ごとのサーバー側カーソル**: 表 `notification_source_cursors`（`source`＝`inquiry`・`registry_job` / `cursor_t` / `cursor_id`）。段階4の反映時に「反映した時点のサーバー時刻」と境界値 UUID で初期化する。定期実行はカーソルより後の出来事（時刻と ID の組・§5.1 と同じ比べ方）だけから送信記録を作り、作り終えたところまでカーソルを進める（今のカーソルより戻さない。§5.1 と同じ）。
    - ⚠**カーソルを進めるのは、対応する送信記録（`notification_deliveries`・`notification_delivery_refs`）を作るのと同じトランザクションの中だけ**（Codex #451 指摘）。先にカーソルを進めてから落ちると、次の実行が5分より後なら、その出来事は読み直しの範囲からも外れて永久に送られない。送信記録の作成のどれかが失敗したら、カーソルも含めて巻き戻す（次の実行で同じ範囲をやり直す）。実際の送信はこのトランザクションの外（§7.5 の端末ごとの処理）で行う。止まっていた間の出来事はカーソルより後なので落ちない。
    - ⚠時刻を先に決めてから確定が遅れる行（申込の `submittedAt` は物件の鍵を待つ前に決まる・謄本ジョブの `completedAt` も確定前に入る）を取りこぼさないよう、**毎回カーソルの5分前から読み直す**（§5.1 の画面側と同じ考え方。Codex #451 指摘）。読み直した分の重複は、送信記録の一意制約 `(binding_id, kind, ref_key)`（`ref_key` に出来事の ID を含む）で弾く。
  - **登録ごとの基準**: **今の利用者に結び付いた時刻（`push_subscriptions.bound_at`）**より前の出来事は、その端末には送らない。行を作った時刻（`created_at`）ではなく、付け替えのたびに更新する `bound_at` を使う（共用 PC で付け替えたあと、前の人の時代の出来事を次の人に送らないため。Codex #451 指摘）。次回対応の繰り返し（§7.4）も、登録時刻より前の回は送らない。
  - 編集権限が外れた記録（`edit_lock_loss_events`）にも**登録ごとの基準を当てる**。`occurred_at` がその端末の `bound_at` より前の記録は、その端末には送らない（端末を持っていない間に起きた古い記録が、後から登録した端末に届かないようにするため。Codex #451 指摘）。さらに、起きてから1時間を過ぎた記録は、送らずに「送らなかった」として締める（`notified_at` に締めた時刻、`status` に `expired` を入れる）。外れたことは画面に戻ったときにも知らせるので、古い通知を後から送る意味は薄い。

### 7.4 次回対応の送信予定（D8・D16・D17）

**期限 T** を次のとおり決める。

- 時刻あり: T = 予定日＋時刻。
- 時刻なし: T = 予定日の **9:00**（日本時間）。

| 経過 | 送る時刻 | 回数 |
|---|---|---|
| 期限の前 | 時刻ありのみ **T − 5分**（時刻なしは T＝9:00 に送る） | 1回 |
| 期限から24時間まで | T＋2h, ＋4h, …, ＋24h（**2時間ごと**） | 12回 |
| 24時間〜72時間 | T＋30h, ＋36h, …, ＋72h（**6時間ごと**） | 8回 |
| 72時間〜1週間 | T＋84h, ＋96h, …, ＋156h（**12時間ごと**） | 7回 |
| 1週間（T＋168h）以降 | **送らない**（停止） | — |

- 完了したらその時点で以降の予定は取り消す。1週間で停止したあとも、画面内の件数（ベル・ホームの一覧）には「期限切れ」として残る（通知だけ止める）。
- 定期実行が止まっていた・遅れた場合、**取りこぼした回をまとめて送らない**。その時点で最も新しい1回だけ送る（例: 6時間止まっていたら、3回分ではなく1回）。
- 同じ実行で同じ利用者に複数件が該当したら、**端末ごとに1通にまとめる**（「今日の次回対応が3件、期限切れが2件あります」）。
  - ⚠1件ずつ行を取り合う方式だと、定期実行が重なったときに別々の処理が別々の件を取り、1通のはずが複数通届く（Codex #451 指摘）。そこで**まとめた1通を1行にする**。
    - `notification_deliveries` は「端末に送る1通」を表す（`ref_key` は持たない）。含めた件は子の表 `notification_delivery_refs`（`delivery_id` / `subscription_id` / `kind` / `ref_key`、一意制約 `(binding_id, kind, ref_key)`）に記録する。
    - 送信処理は §7.5 の端末の行の押さえ（`FOR UPDATE`）の中で、その端末のまだ記録されていない件をまとめて `notification_delivery_refs` に入れ（一意制約に当たった件は他の処理が済ませた分として除く）、残った件で1通を作って送る。端末の行を押さえているので、同じ端末に対して2つの処理が同時にまとめることはない。
    - 送り直し（`failed`）は、その1通（1行）と含めた件をまとめて送り直す。
    - ⚠**送る直前（初回・送り直しとも）に、含めた件を1件ずつ確かめ直す**（Codex #451 指摘）。§7.5 の端末の行の押さえの中で、各件について「未完了か」「担当者が今もこの利用者か」「期限 T と `rev` が `ref_key` と一致するか」「§9 の見える範囲に入っているか」を今の DB で調べる。合わなくなった件は外し、残った件で件数と文言を作り直して送る。残りが0件なら送らずに `cancelled` にする。外した件の `notification_delivery_refs` は消し、新しい期限・担当で改めて送れるようにする。
      - これで、失敗して送り直す間に完了・担当替えされた件の古い件数が、前の担当者に届くことはない（上の「完了したら以降の予定は取り消す」もこの確認で守る）。
- 夜間・休日も止めない（D10）。
- 画面を開いている間のポップアップ（段階2）も同じ予定に従う。

### 7.5 共用 PC への配慮

前に使った人宛ての通知が次の人の画面に出ないようにする。ログアウト時の解除だけに頼らない（ブラウザを閉じるとログアウトの処理は走らないため。Codex #451 指摘・P1）。

1. **サーバー側の有効期限**: 送信処理は `expires_at > 今` の登録にしか送らない。
   - `shared`（既定）: `expires_at` ＝ ログイン中の最後の操作＋65分（自動ログオフと同じ）。ログイン中は、今の延長処理（`idle-session-guard` の5分ごとの延長）に合わせて `expires_at` を延ばす。ブラウザを閉じてから65分で、その端末には送られなくなる。
   - `personal`: 登録時に利用者が「この端末は自分専用（自分のスマホ・自分の PC）」を選んだ場合。`expires_at` ＝ 最後のログイン＋30日。画面を閉じていても届く（D2・D3 の本来の使い方）。30日ログインしなければ止まり、ログインし直すと再開する。
2. **ログインのたびに付け替え**: ログイン後、画面がその端末の登録情報をサーバーへ送り直す。同じ `endpoint` が別の利用者に結び付いていたら、**今ログインした利用者に付け替える**（前の利用者の分は消える）。
   - ⚠**別の利用者への付け替えでは `device_scope` を `shared` に戻し、`expires_at` を「今＋65分」にする**（Codex #451 指摘・P1）。前の人が `personal`（30日）を選んでいても、次の人がその設定を引き継ぐと、ブラウザを閉じたあとも次の人の通知（種類と件数）が届き続けるため。`personal` にするには、付け替えのあとで**今の利用者が自分で改めて選ぶ**必要がある（D18 の既定どおり）。画面は前の利用者の選択を表示・流用しない。
   - ⚠**同じ利用者でも、登録が期限切れ（`expires_at <= 今`）または無効化（`revoked_at` あり）だった場合は、新しい結び付けとして扱う**（Codex #451 指摘）。`binding_id` を作り直し、`bound_at` を今にし、`revoked_at` を消してから `expires_at` を延ばす。止まっていた間の出来事は `bound_at` より前になるので、定期実行が遅れて処理しても、その端末には送られない。有効なままの再登録（同じ利用者・期限内）は結び付けを変えない。
   - ⚠ただし **`revoked_reason = gone` の登録は、同じ `endpoint` での再有効化を受け付けない**（Codex #451 指摘）。中継サービスがその宛先を無効と返しているので、有効に戻しても送信のたびに失敗し、通知が止まったままになる。登録 API は定型のエラー（例 `endpoint_gone`）を返し、画面は `pushManager.unsubscribe()` で古い登録を捨ててから `subscribe()` で新しい `endpoint` を作り直して登録し直す。再有効化できるのは、ログアウト・期限切れ・管理者の操作など**こちら側で止めた登録だけ**。
   - ⚠付け替えと**同じトランザクションで**、その端末（`subscription_id`）に残っている**前の結び付けの**未送信の送信記録（`pending`・`failed`・`sending`）を `cancelled` にする（Codex #451 指摘・P1）。そうしないと、送り直しで前の利用者宛ての通知が次の人の端末に届く。**利用者が変わった付け替えだけでなく、同じ利用者の期限切れ・無効化からの再有効化（上記）でも同じく取り消す**（Codex #451 指摘。再有効化前に作られた記録が、止まっていた間の出来事を新しい結び付けで送ってしまうため）。
   - さらに、送信前の取り合い（§7.2）の条件に**「送信記録の `user_id` と `binding_id` がその端末の今の `user_id`・`binding_id` と一致し、端末が無効化・期限切れでない」**ことを含める（`binding_id` の一致で、再有効化の前に作られた記録も送らない）。付け替えと送信が同時に起きても、前の利用者宛ては送らない（二重の守り）。
   - ⚠ただし、送信処理が行を取ったあと実際に送るまでの間に付け替えが起きる窓が残る（Codex #451 指摘・P1）。そこで**端末ごとに送信と付け替えを直列にする**。
     - 送信処理は、トランザクションの中で `push_subscriptions` のその端末の行を `SELECT ... FOR UPDATE` で押さえ、**その場で** `user_id` の一致と、無効化・期限切れでないことを確かめてから送り、送信記録を `sent` 等に更新してからトランザクションを閉じる。
     - 付け替え（と解除）は同じ行を更新するので、送信中は待たされる。送信が終わってから付け替わるため、付け替えの後に前の利用者宛てが送られることはない。
     - 行を押さえている間に外部へ送るので、送信には**短い時間制限（10秒）**を付け、長く押さえ続けないようにする。
     - ⚠このトランザクションの時間制限は、送信の時間制限より**長く明示する**（Codex #451 指摘）。Prisma 7 の対話型トランザクションは既定で5秒で打ち切られ、本リポジトリの `src/lib/prisma.ts` は既定を変えていない。そのままだと、送信に5〜10秒かかったときに、相手には届いたのに `sent` への更新が巻き戻り、15分後にもう一度送られる。
       - 送信処理の `prisma.$transaction(fn, { timeout: 20_000, maxWait: 5_000 })` のように、この処理だけで指定する（送信10秒＋前後の DB 処理の余裕。全体の既定は変えない）。
       - 送信の時間制限（10秒）は必ずトランザクションの時間制限より短くする。この関係はテストで固定する。
       - ⚠**端末の行の押さえで待たない**（Codex #451 指摘）。同じ端末に2つの処理が重なると、後の処理が `FOR UPDATE` で前の処理の送信（最大10秒）を待ち、そのあと自分も10秒送るので、20秒の枠を使い切ってしまう。そこで押さえは **`SELECT ... FOR UPDATE SKIP LOCKED`** にし、押さえられなかった端末は**その回は飛ばす**（送信記録は残り、次の実行で送る）。送信記録の取り合い（§7.2 の `UPDATE ... SET status = 'sending'`）も、端末の行を押さえた**後に同じトランザクションの中で**行うので、飛ばした端末の記録は取られないまま残る。これでトランザクションの時間は「送信10秒＋前後の DB 処理」に収まる。
   - ⚠それでも、画面側のログインの切り替えは DB の付け替えより先に起きる。そのため、DB の直列化だけでは「前の人宛ての通知が、中継済みのまま次の人の画面に表示される」ことを防げない（Codex #451 指摘・P1）。そこで**表示する側（Service Worker）でも確かめる**。
     - 付け替えのたびに、端末の登録に新しい `binding_id`（乱数）を作る。送信時は、その時点の `binding_id` を本文（暗号化される）に入れる。
     - 画面は、**付け替えが成功した時点でだけ**、新しい `binding_id` を Service Worker の保存領域（IndexedDB）に書き込む。**ログイン画面を開いたとき、およびログインの送信前に、保存済みの `binding_id` を先に消す**（前の人が明示的にログアウトせずに次の人がログインした場合でも、前の人の値が残らないようにするため。Codex #451 指摘・P1）。ログイン後、付け替えが終わるまでの間は保存値が無いので、届いた通知は中身なしで表示される。ログアウトのとき（自動ログオフを含む）は、まずこれを消し、そのあと端末の登録解除（`pushManager.unsubscribe()`）を行う。
     - あわせて、**すでに通知欄に出ている通知も消す**（Codex #451 指摘・P1）。ログアウトのとき、ログイン画面を開いたとき、付け替えの前に、Service Worker の `registration.getNotifications()` で本システムが出した通知を取り出し、すべて `close()` する。`binding_id` を消すだけでは、すでに表示されている前の人の通知（種類と件数）が残るため。
     - Service Worker は通知を受け取ったら、本文の `binding_id` と保存している値を比べる。**一致しないとき、または保存値が無いときは、中身を出さない**。ブラウザは受信のたびに何か表示することを求めるため、その場合は内容の無い「新しいお知らせがあります（ログインして確認してください）」だけを出す。
     - ⚠**表示と切り替えの処理を Service Worker の中で1本の順番待ちにする**（Codex #451 指摘・P1）。`getNotifications()` は、まだ表示していない処理中の通知を閉じられない。Service Worker が A さんの `binding_id` を読んで一致と判断したあと、B さんのログイン処理が保存値を消して通知欄を確認し（まだ何も無い）、そのあとで A さんの種類・件数が表示される、という隙間があるため。
       - 画面は `binding_id` の消去・書き込みと通知の `close()` を自分で行わず、`postMessage` で Service Worker に頼み、完了の返事を待ってからログインの送信・付け替えに進む。
       - Service Worker は `push` の処理（保存値の読み取り→比較→`showNotification()`）と、画面からの消去・書き込み・`close()` の依頼を、**同じ Promise の列に並べて1件ずつ**処理する（`event.waitUntil` で最後まで動かす）。消去の依頼は、それより前に並んだ表示が終わってから動くので、表示済みの通知として確実に閉じられる。
       - ⚠**1件の失敗で列が止まらないようにする**（Codex #451 指摘）。IndexedDB・`showNotification()`・`close()` のどれかが失敗すると、つなげた Promise が失敗のままになり、後ろの表示や消去の依頼がすべて飛ばされる。そこで各処理を「失敗を受け止めて必ず成功で終える」形で列につなぎ（`queue = queue.then(task).catch(記録だけして続行)` のように、次をつなぐ前に失敗を片付ける）、各依頼の成否は依頼ごとに返す。失敗の記録は定型のコードのみで、通知の中身は残さない。
          - 画面は Service Worker の返事を**最大3秒**待つ。返事が失敗・時間切れのときは、画面から直接 IndexedDB の `binding_id` を消し、`getNotifications()` で本システムの通知を `close()` する。**通知を閉じられたことが確認できなければ、下の `binding_id` の条件を満たしていてもログインに進まない**（§4.5。`unsubscribe()` は今後の受信を止めるだけで、すでに出ている通知は消せないため。Codex #451 指摘・P1）。
       - ⚠**消せたことを確かめてからでないと、利用者の切り替え（ログインの送信）に進まない**（Codex #451 指摘・P1）。保存値が A さんのまま残ると、そのあと届いた A さん宛ての通知が一致してしまい、B さんに種類と件数が見えるため。
         - 消去が確認できなかったときは、`pushManager.unsubscribe()` でその端末のプッシュ登録そのものを捨てる（宛先が無効になり、A さん宛てはもう届かない）。捨てられたら、サーバーにも登録の解除を伝えて（届かなくても 404/410 で無効になる）ログインに進む。
         - 消去も登録の破棄もできなかったときは、**ログインに進まず**「通知の設定を消せませんでした。ブラウザを閉じて開き直してからログインしてください」と出す（まれな場合。PII は出さない）。
       - さらに二重の守りとして、`showNotification()` のあとで保存値を読み直し、表示に使った `binding_id` と違っていれば（または消えていれば）、その通知をすぐ `close()` する。
     - これで、切り替えの前後どちらで届いた通知も、次の人には件数や種類を見せない。
3. **ログアウト時の解除**: 明示のログアウト・自動ログオフの処理が走った場合は、その場で登録を解除する（1・2 の補助）。

⚠`shared` の端末では、画面を閉じてから65分を過ぎると届かない。スマホで常に受けたい人は、登録時に「自分専用」を選ぶ運用にする（D18）。

### 7.6 必要な準備（VPS）

- 鍵の作成と env への追加: `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT`（連絡先の mailto）。`/etc/property-management/app.env` に置く。値はログに出さない。
- `prisma migrate deploy`（段階4の migration）。
- systemd timer の設置。手順は `docs/deploy.md` に追記する。

**反映の順番（Codex #451 指摘）**: 定期実行（timer）は**最後に**有効にし、元に戻すときは**最初に**止める。

1. env に VAPID の鍵を追加する（まだ timer は置かない）。
2. `git pull` → `npm ci` → `prisma migrate deploy` → `prisma generate` → `npm run build` → サービス再起動（CLAUDE.md §13 の通常手順）。migration は表と列の追加だけで、古いコードとも両立する（停止時間は通常の再起動のみ）。
3. 送信スクリプトを手で1回だけ実行し、エラーなく終わることを確かめる（鍵や表が無い場合は送らずに終了コード非0で終わる作りにする）。
4. systemd の timer を有効にする（`systemctl enable --now`）。

**元に戻す順番**:

1. **timer を止める**（`systemctl disable --now`）。止めないまま戻すと、定期実行が失敗し続ける。
2. アプリのコードを前の版に戻して再起動する。
3. 追加した表・列は古いコードに影響しないので、原則そのまま残す。消す必要がある場合だけ、timer を止めたあとに消す（消すと送信記録・外れた鍵の記録・基準カーソルが失われ、再び反映したときは基準カーソルの初期化からやり直しになる）。

## 9. 権限

- 件数の窓口・送信処理とも、**今の各一覧の権限判定をそのまま再利用**する（次回対応=`property:read`＋物件の担当範囲（`propertyRecordScopeFilter`・field_staff は作成か担当の物件のみ）、査定申込=`requireSaleDmAccess`＋担当範囲、謄本ジョブ=作成者本人）。新しい権限は作らない。
