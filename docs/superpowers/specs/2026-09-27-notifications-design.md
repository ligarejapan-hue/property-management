## 0. ひとことで

通知を2つの仕組みに分ける。

- **A. 画面から出す通知**: 開いている画面自身が、ブラウザの通知機能（Notification API）で PC／スマホの通知欄に出す。編集権限が外れる・自動ログオフされる、の予告に使う。サーバー・DB は変えない。
- **B. サーバーから送る通知（Web プッシュ）**: サーバーが期限を見張り、登録された PC／スマホへ送る。画面を閉じていても届く。次回対応・査定申込・その他の期限に使う。DB・依存・VPS の定期実行が要る。

通知の本文には**種類と件数だけ**を載せ、物件名・所有者名・住所などは載せない。詳しくは通知を押して開いた画面で、今の権限どおりに見る。

## 4. 段階1: 画面から出す通知（A）と画面内の土台

### 4.1 通知の許可

- 通知には利用者ごとの**ブラウザの許可**が要る。ページを開いた瞬間には求めない（多くのブラウザが嫌う・拒否されやすい）。
- 右上のベルを開いたときの「PC・スマホにも通知する」ボタン（利用者の操作）から許可を求める。
- 許可が無い・拒否された・対応していないブラウザでは、**画面内のポップアップだけ**で知らせる（機能は失わない）。
- OS の通知は `new Notification()` ではなく、**Service Worker の `registration.showNotification()` で出す**（§4.5）。Android の Chrome は前者を使えず、iPhone のホーム画面アプリも後者が前提のため。

### 4.2 N1・N2（編集権限）

- 予告の時刻・外れた判定は、今の編集ロックの仕組み（`EDIT_LOCK_IDLE_WARN_MS`=55分・`ui-state.ts` の状態）をそのまま使う。**鍵の規則は変えない**。
- 画面内の帯（今ある予告）は残し、**そのタブが見えていないとき（`document.hidden`）だけ** OS の通知も出す。見えているときは帯だけ（二重に出さない）。
- 同じ通知が何度も出ないよう、通知に `tag`（例 `edit-lock:<資源の種類>:<資源ID>`）を付ける。⚠資源IDは UUID のみ（PII ではない）。

### 4.3 N3（自動ログオフ）

- 今の `idle-session-guard` は**予告なしで**ログアウトする。55分の時点で「まもなくログオフします」を出す処理を足す。
  - 画面内: 「あと5分で自動ログオフします [続ける]」のダイアログ（押すと操作とみなして延長）。
  - タブが見えていないとき: OS の通知も出す。
- 60分でログアウトする規則・延長の仕組みは**変えない**。
- 複数タブ: 最終操作時刻は今も `localStorage` でタブ間共有している。通知は `tag: "idle-logout"` で1つにまとめる。

### 4.4 画面内の土台

- 右下のポップアップ（トースト）と、右上ヘッダーのベル（未確認の件数）を共通部品として作る（`src/components/ui` に追加）。
- 見た目は `/ui-design` の手順で、実装前に HTML イメージで承認を取る。
- 動き: 表示時に軽く出てくる程度。`motion-reduce` で止める。

### 4.5 iPhone の制約

- iPhone（Safari）の通知は、社内システムを**ホーム画面に追加して開いた場合のみ**使える（iOS 16.4 以降）。ブラウザのタブで開いた場合は、画面内のポップアップだけになる。
- ホーム画面に追加できるようにする設定（Web アプリの名前・アイコンの定義 = manifest）は、D13 を受けて**段階1で入れる**（依存追加なし・ファイルの追加のみ）。
- あわせて、通知を表示する受け取り役 **Service Worker（`public/sw.js`）も段階1で入れて登録する**。manifest だけでは iPhone で通知を出せないため（Codex #451 指摘）。段階1の Service Worker は「通知の表示（`showNotification` の呼び出し元は画面）」と「通知を押したときに該当画面を開く（`notificationclick`）」だけを持つ。サーバーからの受信（`push`）は段階4で足す。
- ⚠Service Worker はページの読み込みを横取りしない（`fetch` を扱わない・キャッシュしない）。オフライン対応は対象外。

### 4.6 段階1の予告通知が届かない場面（Codex #451 指摘）

段階1の N1〜N3 は**画面の中の処理が動いている間だけ**出せる。次の場面では画面の処理が止められ、予告の時刻になっても OS の通知は出ない。

- iPhone・Android でアプリ（ホーム画面アプリ・ブラウザ）を裏に回した、または画面をロックした
- PC でブラウザを閉じた・PC がスリープした

これを補うため、次の2つを入れる。

1. **戻ったときの知らせ（段階1）**: 画面に戻った（`visibilitychange` で見える状態になった）ときに、今の状態を確かめ直し、編集権限が外れていた・ログオフされていた場合は画面内で理由をはっきり出す（「無操作が60分続いたため、編集権限が外れました」など）。保存前の入力がある場合はその旨も出す。
2. **外れたことをサーバーから送る（段階4）**: 画面が止まると合図（heartbeat）が止まり、編集の鍵は**既存の規則どおり5分で外れる**（D4・`expiryCause` は合図の期限を先に判定する）。そのため、画面が止まった端末に「55分で外れます」という予告は成り立たない（Codex #451 指摘）。代わりに、**鍵が外れたこと（N2）をサーバーから Web プッシュで送る**。
   - ⚠鍵の行は、別の人が取り直すと `acquireEditLock` の UPSERT で ID・持ち主・時刻がまるごと書き換わる（`src/lib/edit-lock/service.ts`）。定期実行が鍵の表を後から見るだけでは、前の持ち主が分からず知らせ漏れる（Codex #451 指摘）。そこで、**外れた事実を別の表 `edit_lock_loss_events` に残し**、定期実行はこの表だけを見て送る（§7.2）。
   - 記録する場面は3つ。いずれも鍵の行の ID（取るたびに新しくなる）を一意キーにして、同じ「1回の持ち時間」を二重に記録しない。
     1. 取り直し（`acquireEditLock`）で、別の画面の期限切れの鍵、または管理者に外された鍵を上書きするとき。**上書きと同じトランザクションで**、上書き前の持ち主を記録する。
     2. 管理者が外したとき（`force-release`）。外すのと同じトランザクションで記録する。
     3. 期限を過ぎたまま誰にも取り直されていない鍵。定期実行が見つけて記録する。
   - 定期実行は、まだ知らせていない記録について、持っていた利用者に「編集権限が外れました」を送り、送った時刻を記録に残す。
   - 鍵の規則（5分・60分・55分の予告）は**変えない**。
   - 自動ログオフの予告（N3）は、最後の操作時刻をサーバーが持っていない（ログインの有効期限は cookie 側で延長している）ため、サーバーから正確に送れない。**N3 は画面が動いている間のみ**とし、戻ったときの知らせで補う。

| 通知 | PC（ブラウザ起動中） | スマホ（アプリを開いている） | スマホ（裏に回した・ロック中） |
|---|---|---|---|
| N1 編集権限の予告 | 段階1から出る | 段階1から出る | 出ない（画面が止まると5分で鍵が外れる既存の規則のため、予告の場面が無い） |
| N2 編集権限が外れた | 段階1から出る | 段階1から出る | 段階4からサーバー送信。戻ったときにも画面内で出す |
| N3 自動ログオフの予告 | 段階1から出る | 段階1から出る | 出ない。戻ったときに画面内で出す |

## 5. 段階2: 画面内で N4・N6・N7 を出す（DB 変更なし）

### 5.1 窓口（API）

`GET /api/notifications/summary?inquiryCursor=<時刻,ID>&registryCursor=<時刻,ID>`（新設・読み取りのみ）。応答は**件数と ID・時刻だけ**。

```json
{
  "nextActionToday": 3, "nextActionOverdue": 1,
  "nextActionReminders": [{ "actionId": "uuid", "slot": 4 }],
  "openInquiries": 2, "newInquiryIds": ["uuid"], "inquiryCursor": { "t": "2026-09-28T01:23:45.123Z", "i": "uuid" },
  "registryJobsCompleted": [{ "jobId": "uuid", "done": 12, "failed": 1, "skipped": 2, "chargedButFailed": 1 }], "registryCursor": { "t": "2026-09-28T01:20:00Z", "i": "uuid" }
}
```

- 次回対応:
  - `nextActionToday` / `nextActionOverdue`: `assignedTo = 自分` かつ `isCompleted = false` かつ `scheduledAt ≦ 今日`（**日本時間の今日**。`scheduledAt` は日付型）。ベル・ホームの件数に使う。
  - `nextActionReminders`: 自分の未完了の次回対応のうち、**今が §7.4 の送信予定のどれかの回に当たっているもの**と、その回の番号（`slot`）。回の計算は §7.4 の純関数（`nextActionReminderSlot(期限T, 今)`）を段階2と段階4で**共用**する。段階2では時刻の欄が無いので T＝予定日の9:00。1週間を過ぎたものは含めない。
  - 権限は今の次回対応 API（`GET /api/properties/[id]/next-actions`）と**同じ2段**で確認する（Codex #451 指摘・P1）: ① `property:read`、② 物件の担当範囲（`assertPropertyRecordAccess` と同じ規則。field_staff は親の物件の `createdBy` か `assignedTo` が自分のものだけ）。一覧の問い合わせでは `propertyRecordScopeFilter(session)` を `property` 条件に畳み込む。次回対応の担当が自分でも、親の物件の担当から外れていれば数えない・送らない。
- 査定申込（Codex #451 指摘: 件数の増減では「1件完了＋1件新着」を見逃す）:
  - `openInquiries`: `handleStatus = "open"` の件数（ベル用）。
  - `newInquiryIds`: カーソルより後に届いた申込の ID。カーソルは**時刻と ID の組** `(submittedAt, id)` で、申込一覧の既存カーソル（`inquiryCursorWhere`）と同じ辞書順で比べる。時刻だけだと同じミリ秒の2件目を取りこぼすため（Codex #451 指摘）。
  - 遅れて保存された行（時刻はカーソルより前だが、前回の問い合わせの後に確定した行）を取りこぼさないよう、**カーソルの5分前から**読み直し、画面側で見た ID と照らして重複を除く。見た ID は1日分だけ残す。
  - 範囲は申込一覧 API と同じ `requireSaleDmAccess` と担当範囲。
- 謄本の一括取得: `requestedById = 自分` かつ `status = "completed"` で、カーソル `(completedAt, id)` より後のもの（読み直しと重複除去も申込と同じ）。
  - ⚠件数（`done`・`failed`）は、ジョブの集計列をそのまま返さない。既存の `getBulkJobProgress` と同じく、**項目ごとに `canAccessPropertyRecord` で今見られる物件だけに絞って数え直す**（Codex #451 指摘・P1。field_staff の担当から外れた物件の結果を出さない）。見られる項目が1件も無いジョブは通知しない。段階4の送信も同じ関数を使う。
  - 件数は `done`・`failed` だけでなく、既存の `BulkJobCounts`（`recomputeCounts`）と同じく **`skipped`（要手動）と `chargedButFailed`（要確認：課金されたが取得に失敗）も別に返す**（Codex #451 指摘）。「成功1件・失敗0件」のように見えて実は要確認がある、という誤解を防ぐ。`chargedButFailed` が1件以上あれば、通知の文言でも「要確認」を必ず出す。
- **物件名・住所・申込者名など PII は返さない**（ID は UUID のみ）。

### 5.2 取りに行く間隔

- 画面を開いている間、**60秒ごと**と、タブが見える状態に戻ったときに取りに行く。見えていないタブでは間隔を延ばす（ブラウザも自動で遅くする）。
- ポップアップを出す条件（件数の増減では判定しない）:
  - 次回対応: `nextActionReminders` に**まだ見ていない `(actionId, slot)` の組**が現れたとき。同時に複数あれば1つのポップアップにまとめる。
  - 査定申込: `newInquiryIds` に、まだ見ていない ID があるとき。表示後、`inquiryCursor` と見た ID を保存して次回に使う。
  - 謄本: `registryJobsCompleted` に、まだ見ていないジョブがあるとき。同様に `registryCursor` を保存する。
- 見た `(actionId, slot)` の組とカーソルは端末の `localStorage` に置く（利用者IDごと。段階2では DB に既読を持たない）。初めて開いた端末（カーソルを持っていない）は、カーソルを付けずに問い合わせ、サーバーは初期カーソルと一緒に**読み直し範囲（初期カーソルの5分前から）にすでにある出来事の ID（`initialSeenIds`）**も返す。端末はこれを「見た ID」として最初から持っておく。こうしないと、次の問い合わせで5分前から読み直したときに、初期化より前の出来事を新着として出してしまう（Codex #451 指摘）。初期化の時点でまだ確定していなかった行は `initialSeenIds` に入らないので、遅れて確定した新着は正しく出る。**サーバーが返す初期カーソル（サーバーの時計での「今」と、ID には正しい形式の境界値 `00000000-0000-0000-0000-000000000000`）**をそのまま保存する。ID を空にすると、既存の `decodeInquiryCursor`（ID が UUID の形でないと受け付けない）で読めず、DB の UUID 列とも比べられないため（Codex #451 指摘）。カーソルの読み書きは既存の `encode`／`decode` と同じ形式（base64url の JSON）にし、読めないカーソルが来たときは**初期化とみなさず 400 を返す**（黙って初期化すると、その間の新着を取りこぼすため）。過去の分はまとめて出さない。端末の時計はカーソルに使わない（端末の時計がずれていると、新着を取りこぼしたり古い分を出したりするため。Codex #451 指摘）。見た組は1週間を過ぎたものから捨てる。

## 6. 段階3: 次回対応に時刻の欄（DB 変更あり）

- `next_actions` に `scheduled_time`（時刻・NULL 可）を**追加のみ**。既存の行は NULL のまま＝今までどおり日付だけ。
- 次回対応タブの入力に「時刻（任意）」を追加。
- 通知: 時刻がある行は**その時刻の5分前**（D8）に N5 を出す。時刻が無い行は N4 のまま**当日9:00**に送る（D16）。
- rollback: 列の DROP で戻せる。
- ⚠列の型（時刻だけの列にするか、日付と時刻を合わせた列にするか）は、既存の `scheduledAt`（日付型）との整合と並び替えへの影響を見て、実装前の計画で確定する。

## 7. 段階4: Web プッシュ（DB・依存・VPS の変更あり）

### 7.1 仕組み

1. 利用者が「PC・スマホにも通知する」を押す → ブラウザが通知の登録情報（宛先 URL と鍵）を作る → サーバーに保存。
2. サーバーの**定期実行**が数分ごとに期限を確認し、送るべき通知があれば登録先へ送る。
3. ブラウザ側の受け取り役（段階1で入れた Service Worker・`public/sw.js` に `push` の受信を足す）が通知を表示する。押すと該当画面を開く。

- 送信先は、ブラウザ各社のプッシュ中継サービス（Google・Mozilla・Apple）。**本文は規格上暗号化されて**中継される。利用料はかからない見込み。接続は D14 で承認済み。
- ⚠外部サービスへの接続にあたるため、CLAUDE.md §17・§18.2 の事前承認の対象として扱った（D14 で承認済み。`web-push` の依存追加は実装時に改めて確認）。

### 7.2 データ（すべて追加のみ）

- `push_subscriptions`: `id` / `user_id` / `endpoint`（一意）/ `p256dh` / `auth` / `device_scope`（`shared` か `personal`・§7.5）/ `expires_at` / `created_at` / `last_success_at` / `failure_count` / `revoked_at`
  - `endpoint` と鍵は**秘密情報として扱う**。API の応答・ログ・AuditLog に出さない。
- `notification_deliveries`: `id` / `user_id` / `subscription_id` / `kind`（N4 など）/ `ref_key`（重複防止のキー。例 `next_action:<ID>:<回>` や `inquiry:<申込ID>`）/ `scheduled_for` / `attempts` / `sent_at` / `status`（`pending`・`sent`・`failed`・`gone`）/ `last_error_code`（定型コードのみ）
  - **端末（登録）ごとに1行**（Codex #451 指摘）。一意制約 `(subscription_id, kind, ref_key)` で、同じ端末・同じ回の行が2つできないようにする。
  - ⚠一意制約だけでは、定期実行が2つ重なったとき両方が同じ `pending` の行を見て送ってしまう（Codex #451 指摘）。そこで**送る前に行を取り合う**。既存の査定申込メール通知（`notifyStatus` = `sending`・`notifyClaimedAt`・15分で残骸扱い）と同じ方式にする。
    - 列 `claimed_at` を足し、状態に `sending` と `cancelled` を加える。
    - 1文の `UPDATE ... SET status = 'sending', claimed_at = now() WHERE id = ? AND (status IN ('pending','failed') OR (status = 'sending' AND claimed_at < now() - 15分)) RETURNING id` で取れた処理だけが送る。取れなかった処理は送らない。送り直し（`failed` の行）も同じく取り合う。
    - 送信後に `sent`・`failed`・`gone` へ更新する。送信の直後に処理が落ちた場合は、15分後に取り直されて1回多く届くことがある（本文は種類と件数だけなので実害は小さい。メール通知と同じ割り切り）。
  - あわせて、定期実行そのものも重ならないようにする（systemd の oneshot サービスは実行中に次を起動しない。cron を使う場合は `flock` で1本に絞る）。
  - PC は届いてスマホは一時的に失敗した、という場合も、**失敗した端末だけ**を次の実行で送り直せる（届いた端末には送り直さない）。送り直しはその回の次の予定時刻まで、最大3回。404/410 は `gone` にして登録を無効にする。
- `notification_source_cursors`（§7.3）: `source`（主キー。`inquiry`・`registry_job`）/ `cursor_t` / `cursor_id` / `updated_at`。段階4の migration で、反映時点のサーバー時刻と境界値 UUID の行を入れる。
- `edit_lock_loss_events`（§4.6）: `id` / `lock_id`（一意。外れた鍵の行の ID）/ `user_id`（外れた持ち主）/ `resource_type` / `resource_id` / `cause`（`heartbeat`・`idle`・`force_released`）/ `occurred_at` / `notified_at`
  - 鍵の規則（5分・60分）は変えない。記録を足すだけ。資源の中身（物件名・所有者名など）は入れない。
  - 知らせ終わった記録は30日で消す。
- 通知の種類ごとの ON/OFF は**作らない**（D12）。設定用の列・表は不要。

### 7.3 定期実行

- VPS の **systemd timer**（または cron）で、数分ごとに送信スクリプトを `www-data` で実行する。HTTP の窓口を増やさないため、スクリプト方式を第一案とする。
- 既存の方針（謄本の一括取得は画面駆動で、サーバーに常駐のタイマーを置かない）と矛盾しないよう、**アプリのプロセス内に setInterval を置かない**。
- 送信に失敗して「もう存在しない」（HTTP 404/410）と返された登録は無効にする。
- 繰り返し送る通知（D9・D17）は §7.4 の送信予定に従い、`ref_key` に「何回目の送信か」を含めて各回1度だけ送る。完了（`isCompleted = true`）・削除・担当者の変更で止まる（担当者が変わったら新しい担当者の予定として数え直す）。
- 夜間・休日も止めない（D10）。
- **切り替え時点の基準（Codex #451 指摘）**: 段階4を初めて動かしたとき、過去の申込・完了済みの謄本ジョブには送信記録が無いため、そのままでは過去分を全部送ってしまう。逆に「直前の実行以降だけ」を見ると、定期実行が止まっていた間の分を落とす。そこで次の2つの基準を持つ。
  - **発生源ごとのサーバー側カーソル**: 表 `notification_source_cursors`（`source`＝`inquiry`・`registry_job` / `cursor_t` / `cursor_id`）。段階4の反映時に「反映した時点のサーバー時刻」と境界値 UUID で初期化する。定期実行はカーソルより後の出来事（時刻と ID の組・§5.1 と同じ比べ方）だけから送信記録を作り、作り終えたところまでカーソルを進める。止まっていた間の出来事はカーソルより後なので落ちない。
    - ⚠時刻を先に決めてから確定が遅れる行（申込の `submittedAt` は物件の鍵を待つ前に決まる・謄本ジョブの `completedAt` も確定前に入る）を取りこぼさないよう、**毎回カーソルの5分前から読み直す**（§5.1 の画面側と同じ考え方。Codex #451 指摘）。読み直した分の重複は、送信記録の一意制約 `(subscription_id, kind, ref_key)`（`ref_key` に出来事の ID を含む）で弾く。
  - **登録ごとの基準**: 端末を登録した時刻（`push_subscriptions.created_at`）より前の出来事は、その端末には送らない。次回対応の繰り返し（§7.4）も、登録時刻より前の回は送らない。
  - 編集権限が外れた記録（`edit_lock_loss_events`）は1件ずつ `notified_at` を持つので、この基準は不要（段階4の反映前の記録は作られない）。

### 7.4 次回対応の送信予定（D8・D16・D17）

**期限 T** を次のとおり決める。

- 時刻あり: T = 予定日＋時刻。
- 時刻なし: T = 予定日の **9:00**（日本時間）。

| 経過 | 送る時刻 | 回数 |
|---|---|---|
| 期限の前 | 時刻ありのみ **T − 5分**（時刻なしは T＝9:00 に送る） | 1回 |
| 期限から24時間まで | T＋2h, ＋4h, …, ＋24h（**2時間ごと**） | 12回 |
| 24時間〜72時間 | T＋30h, ＋36h, …, ＋72h（**6時間ごと**） | 8回 |
| 72時間〜1週間 | T＋84h, ＋96h, …, ＋156h（**12時間ごと**） | 7回 |
| 1週間（T＋168h）以降 | **送らない**（停止） | — |

- 完了したらその時点で以降の予定は取り消す。1週間で停止したあとも、画面内の件数（ベル・ホームの一覧）には「期限切れ」として残る（通知だけ止める）。
- 定期実行が止まっていた・遅れた場合、**取りこぼした回をまとめて送らない**。その時点で最も新しい1回だけ送る（例: 6時間止まっていたら、3回分ではなく1回）。
- 同じ実行で同じ利用者に複数件が該当したら、**端末ごとに1通にまとめる**（「今日の次回対応が3件、期限切れが2件あります」）。まとめた通知に含めた `ref_key` ごとに、端末ごとの記録を残す。
- 夜間・休日も止めない（D10）。
- 画面を開いている間のポップアップ（段階2）も同じ予定に従う。

### 7.5 共用 PC への配慮

前に使った人宛ての通知が次の人の画面に出ないようにする。ログアウト時の解除だけに頼らない（ブラウザを閉じるとログアウトの処理は走らないため。Codex #451 指摘・P1）。

1. **サーバー側の有効期限**: 送信処理は `expires_at > 今` の登録にしか送らない。
   - `shared`（既定）: `expires_at` ＝ ログイン中の最後の操作＋65分（自動ログオフと同じ）。ログイン中は、今の延長処理（`idle-session-guard` の5分ごとの延長）に合わせて `expires_at` を延ばす。ブラウザを閉じてから65分で、その端末には送られなくなる。
   - `personal`: 登録時に利用者が「この端末は自分専用（自分のスマホ・自分の PC）」を選んだ場合。`expires_at` ＝ 最後のログイン＋30日。画面を閉じていても届く（D2・D3 の本来の使い方）。30日ログインしなければ止まり、ログインし直すと再開する。
2. **ログインのたびに付け替え**: ログイン後、画面がその端末の登録情報をサーバーへ送り直す。同じ `endpoint` が別の利用者に結び付いていたら、**今ログインした利用者に付け替える**（前の利用者の分は消える）。
   - ⚠付け替えと**同じトランザクションで**、その端末（`subscription_id`）に残っている前の利用者宛ての未送信の送信記録（`pending`・`failed`・`sending`）を `cancelled` にする（Codex #451 指摘・P1）。そうしないと、送り直しで前の利用者宛ての通知が次の人の端末に届く。
   - さらに、送信前の取り合い（§7.2）の条件に**「送信記録の `user_id` がその端末の今の `user_id` と一致し、端末が無効化・期限切れでない」**ことを含める。付け替えと送信が同時に起きても、前の利用者宛ては送らない（二重の守り）。
   - ⚠ただし、送信処理が行を取ったあと実際に送るまでの間に付け替えが起きる窓が残る（Codex #451 指摘・P1）。そこで**端末ごとに送信と付け替えを直列にする**。
     - 送信処理は、トランザクションの中で `push_subscriptions` のその端末の行を `SELECT ... FOR UPDATE` で押さえ、**その場で** `user_id` の一致と、無効化・期限切れでないことを確かめてから送り、送信記録を `sent` 等に更新してからトランザクションを閉じる。
     - 付け替え（と解除）は同じ行を更新するので、送信中は待たされる。送信が終わってから付け替わるため、付け替えの後に前の利用者宛てが送られることはない。
     - 行を押さえている間に外部へ送るので、送信には**短い時間制限（10秒）**を付け、長く押さえ続けないようにする。
3. **ログアウト時の解除**: 明示のログアウト・自動ログオフの処理が走った場合は、その場で登録を解除する（1・2 の補助）。

⚠`shared` の端末では、画面を閉じてから65分を過ぎると届かない。スマホで常に受けたい人は、登録時に「自分専用」を選ぶ運用にする（D18）。

### 7.6 必要な準備（VPS）

- 鍵の作成と env への追加: `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT`（連絡先の mailto）。`/etc/property-management/app.env` に置く。値はログに出さない。
- `prisma migrate deploy`（段階4の migration）。
- systemd timer の設置。手順は `docs/deploy.md` に追記する。

**反映の順番（Codex #451 指摘）**: 定期実行（timer）は**最後に**有効にし、元に戻すときは**最初に**止める。

1. env に VAPID の鍵を追加する（まだ timer は置かない）。
2. `git pull` → `npm ci` → `prisma migrate deploy` → `prisma generate` → `npm run build` → サービス再起動（CLAUDE.md §13 の通常手順）。migration は表と列の追加だけで、古いコードとも両立する（停止時間は通常の再起動のみ）。
3. 送信スクリプトを手で1回だけ実行し、エラーなく終わることを確かめる（鍵や表が無い場合は送らずに終了コード非0で終わる作りにする）。
4. systemd の timer を有効にする（`systemctl enable --now`）。

**元に戻す順番**:

1. **timer を止める**（`systemctl disable --now`）。止めないまま戻すと、定期実行が失敗し続ける。
2. アプリのコードを前の版に戻して再起動する。
3. 追加した表・列は古いコードに影響しないので、原則そのまま残す。消す必要がある場合だけ、timer を止めたあとに消す（消すと送信記録・外れた鍵の記録・基準カーソルが失われ、再び反映したときは基準カーソルの初期化からやり直しになる）。

## 8. 個人情報（CLAUDE.md §7・§8）

- 通知の本文・タイトルには**種類と件数・時刻だけ**。物件名・所有者名・住所・申込者名・電話番号・座標は載せない。
- 通知を押して開く URL には ID（UUID）だけを入れ、PII を入れない。
- AuditLog: 通知の登録・解除は「操作と件数」だけ記録し、`endpoint`・鍵は記録しない。個々の送信は AuditLog に記録しない（量が多いため。`notification_deliveries` が記録を兼ねる）。
- console・エラー文に登録情報や通知の中身を出さない。

## 9. 権限

- 件数の窓口・送信処理とも、**今の各一覧の権限判定をそのまま再利用**する（次回対応=`property:read`＋物件の担当範囲（`propertyRecordScopeFilter`・field_staff は作成か担当の物件のみ）、査定申込=`requireSaleDmAccess`＋担当範囲、謄本ジョブ=作成者本人）。新しい権限は作らない。
- 権限が外れた利用者・無効化された利用者（`isActive = false`）には送らない。送信の直前にも確認する（今のメール通知と同じ考え方）。

## 10. 変えないもの

- 自動ログアウトの時間（60分）と延長の仕組み。
- 編集ロックの規則（55分の予告・60分で解除・画面停止5分）。
- 査定申込のメール通知（そのまま残す。プッシュは追加の経路）。
- 謄本の一括取得の進め方（画面駆動）。

## 11. テスト

- 段階1: 予告の時刻判定（純関数）、タブが見えている／いないでの出し分け、許可が無いときに画面内だけになること、`tag` による重複防止。
- 段階2: 件数 API の権限（field_staff の担当範囲・権限なしで 403）、PII を返さないこと、日本時間の「今日」の境界。
- 段階3: migration 後も既存の次回対応が今までどおり動くこと、時刻の入力・表示。
- 段階1（追加2）: 画面を裏に回して戻ったとき、外れた・ログオフされた理由が画面内に出ること。
