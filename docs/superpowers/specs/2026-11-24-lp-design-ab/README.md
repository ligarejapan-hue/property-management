# 売却の代表LP 5つの見た目の比較テスト(設計メモ・見本)

2026-11-24 発注者と Claude のやりとりで決まった内容。**この PR は docs のみ**(実装は別 PR)。

## 1. 何をしたいか

理由を問わず売却を考えている人向けの「代表LP」を新しく作り、**入り方の違う5つの見た目**のどれが査定の申込につながるかを比べる。

今の LP(相続・空き家など)は「AI が作ったサイトに見える」という発注者の評価。高級感のある見た目と動きを入れた見本を作り、発注者が 5 案まで絞った。

## 2. 5つの案(見本はこのフォルダの HTML)

| 記号 | ファイル | 最初の画面 | そのあとの並び |
|---|---|---|---|
| base | `design-0-base.html` | 見出しと「無料査定を申し込む」 | 査定方針 → 4つの選択肢 → 仲介と買取 → 5つの段階 → 事例 → 質問 → 申込 |
| form | `design-1-form.html` | 見出しのすぐ下に、お名前と電話番号の入力欄 | base と同じ |
| question | `design-2-question.html` | 3つの質問(種類 → 都県 → お届け先)を1つずつ | base と同じ |
| compare | `design-5-compare.html` | 「売り方は二つあります」と2つの札・金額を並べる表 | 4つの選択肢 → 査定方針 → 5つの段階 → 事例 → 質問 → 申込 |
| editorial | `design-8-editorial.html` | 縦書きの見出しと、3つの短い文章 | 4つの選択肢 → 仲介と買取 → 5つの段階 → 事例 → 質問 → 申込 |

- 色・書体・ロゴ・動きは 5 案で同じ。違うのは最初の画面と並び順だけ(申込の差を「入り方の違い」として読めるようにするため)。
- 見本はブラウザでそのまま開ける。申込は送信されない(入力の点検と完了表示だけ動く)。
- 見本の文言は発注者が確認済みのものだけで組んである。**実装で文言を足さない・変えない**。
  - 代表の実績(業界歴・査定件数・取引件数)は載せない(2026-11-23 発注者)。
  - 対応地域は一都三県(東京都・神奈川県・埼玉県・千葉県)。
  - 「住宅ローンが残っていても売れる」「住みながら売れる」の 2 問は発注者の確認待ち(§6)。
  - 事例 3 件は今の相続LPに載っている文をそのまま使っている。

## 3. 見本と本番の違い(実装で直すところ)

既存コードを読んで分かった制約。

1. **外部の書体は使えない**。公開ページの CSP は `default-src 'none'`(`lp-page.ts` の `LP_PAGE_HEADERS`)で、Google Fonts を読めない。見本は Google Fonts(Shippori Mincho B1 / Zen Kaku Gothic New / Cormorant Garamond)を読んでいるので、本番は今の LP と同じ「端末の明朝体」の並び(`lp-page.ts` の `SERIF`)とゴシック体に置き換える。CSP は広げない。
2. **画像は自サイトのものだけ**(`img-src 'self'`)。ロゴは `public/lp-assets/brand/` に置く。濃い地の上に載せるため、文字を生成り色にした版(`assets/logo-light.png`・赤い丸はそのまま)が要る。
3. **申込フォームは今の受け口をそのまま使う**(`POST /lp/<公開名>/inquiry`)。
   - 欄の名前は `inquiry-input.ts` に合わせる(`name` / `phone` / `consent` / ボット除け `hp_extra_note`)。見本はこの名前にしてある。
   - 同意のチェック(`consent`)は必須。「個人情報の取り扱い」の文面は今の LP と同じもの(設定の文面)を出す。見本は仮の一文。
   - 広告の印(utm_* / gclid)の隠し欄、送信中・完了・エラーの表示、Google のタグへの成果の送信は、今の LP のフォームと同じ動きにする。
   - question 案の「種類・都県・市区町村」は新しい列を作らず、`propertyAddress`(都県+市区町村)と `message`(種類)に入れる。
4. **スクロールで順に現れる部分は、スクリプトが動かなくても読めること**。見本は IntersectionObserver が無いと全部表示するが、スクリプト自体が止まった場合の備え(`<noscript>` で表示に戻す等)を入れる。
5. `noindex`、OG、応答ヘッダ、回数制限は今の公開ページと同じ。

## 4. 比べ方(提案)

**案ごとに別の公開名(URL)を持たせ、広告側で振り分ける。**

- 例: `/lp/baikyaku`(base)・`/lp/baikyaku-form`・`/lp/baikyaku-question`・`/lp/baikyaku-compare`・`/lp/baikyaku-editorial`。
- 申込は今でも公開名つきで保存される(`dm_inquiries.public_slug`)。閲覧数は Google アナリティクスでページごとに出る。**振り分けと記録のための新しい仕組みは要らない**。
- 広告(SmartNews など)は、同じ広告グループに 5 本の広告を作り、遷移先だけ変える。

採らなかった案: 1 つの URL でサーバーが訪問者を振り分ける方式。申込にどの案かを残す列が要り(migration)、閲覧数も案ごとに数える仕組みが要る。最初のテストには重い。

## 5. 実装の方針(提案・schema 変更なし)

- 新しい描画モジュールを足す(例: `src/lib/sale-dm-letter/lp-design-pages.ts`)。5 つの見本を、今の `renderLpPage` と同じ入力(フォームの設定・広告の印・Google のタグ・公開名)から HTML を返す関数にする。共通部分(色・動き・下半分の節)は 1 か所にまとめる。
- どの公開名でどの案を出すかは、**コードの対応表**で決める(例: `LP_DESIGN_BY_SLUG`)。DM の種類の行は今までどおり要る(公開の条件・申込の紐づけ・Google のタグ)。
  - ⚠対応表は比較テストのための仮の形。続けて使うと決まったら、種類ごとに見た目を選ぶ列を足す(その時に migration を相談する)。
- `loadPublicLpPage` は、公開の条件(公開ゲート・「使う」・文章あり)を今までどおり確かめたうえで、対応表にある公開名なら新しい描画を使う。対応表に無い公開名は今までどおり。
- DM 用のご案内ページ(`/t/<token>`)は変えない。

### 触らないもの

- schema / migration、申込の受け口の検証・回数制限・監査、CSP、既存 LP(相続・空き家など)の見た目。
- AuditLog に入力値を増やさない(CLAUDE.md §8・§19)。

### テスト

- 対応表にある公開名は新しい描画、無い公開名は今までの描画になること。
- 公開の条件を満たさないときは今までどおり 404 になること(新しい描画でも中身の有無を漏らさない)。
- 5 案それぞれ: フォームの欄の名前・同意・ボット除け・広告の印の隠し欄が出ること、外部の URL(書体・画像・スクリプト)を含まないこと、`</script>` などを含む値を入れても壊れないこと。
- question 案: 種類・都県・市区町村が `message` / `propertyAddress` に入ること。

## 6. 発注者の判断待ち

1. 今の相続LPも比較に入れるか(入れると 6 案)。
2. 「住宅ローンが残っていても、代金などで完済できれば売れる」「住みながら売れる」の 2 問が実態と合っているか。
3. 公開名(§4 の例でよいか)。
4. 冒頭の線画(街並み)のままでよいか、絵を用意するか。

## 7. 期間の見込み

申込率 1%・1 日 30 クリックと仮定すると、「2% に上がった」程度の差を見分けるのに 1 案あたり約 2,300 人、5 案で約 11,500 人。今の広告の予算(SmartNews 1 日 800 円)では 1 年前後かかる。申込率とクリック数は仮の数字。
