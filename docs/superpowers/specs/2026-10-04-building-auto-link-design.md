# 区分マンションの棟を自動で作ってつなぐ・物件名の候補 — 設計

- 日付: 2026-10-04
- 発注者判断: 本書の「決定」D1〜D12 はすべて 2026-10-04 に発注者が承認済み(再提案しない)
- 関連: 物件写真タブの案内から棟写真へのリンク(実績162・`48ad923a`)

## 1. 背景と目的

物件写真タブに「共用部・外観は棟写真を」と案内し、該当の棟へのリンクを付けた(実績162)。ところが本番では次の状態で、リンクの飛び先がどこにも無い。

| 本番の実測(2026-10-04) | 値 |
|---|---|
| 棟(buildings)の件数 | 1(名前「仮」) |
| 区分マンション(`apartment_unit`)の件数 | 42,340 |
| そのうち棟につながっている件数(`building_id` あり) | 0 |
| そのうち物件名(`building_name`)が入っている件数 | 1 |
| 全物件のうち棟につながっている件数 | 0 / 130,487 |

物件名(マンション名)を入れた区分マンションは、保存時に自動で棟につながり、棟が無ければ棟を作る。入力時には既存の棟を候補に出し、表記の揺れ(第一/第１/第1 など)で棟が分かれないようにする。

**成功の基準**
- 物件名を入れて保存した区分マンションは、必ずどれか1つの棟につながる。
- 同じ町丁目で同じ建物を表記違いで登録しても、棟は1つにまとまる。
- 写真タブの案内が全物件で常に出て、棟につながった区分マンションでは棟写真へ飛べる。

**範囲外(別の機会)**
- 既存 42,340 件を家屋番号からまとめて棟にする一括処理(試算=約1万9千棟・2部屋以上 7,885棟)。
- 現地調査からの物件化への物件名の欄の追加。

## 2. 決定(発注者承認済み)

- **D1** 方式=候補を出し、選ばなければ自動で判断する(候補のみ・自動作成のみ、は採らない)。
- **D2** 同じ棟とみなす範囲=**同じ町丁目**。丁目の無い住所は町名(番地の数字の手前)まで。丁目違いの同名棟は自動ではつながず、候補に住所つきで出す。
- **D3** つないだら、物件名を**棟の正式な表記**に書きそろえる。棟の名前を直したら、つながっている全部屋の物件名も直す。
- **D4** つながっている部屋の物件名を編集で変える=**別の棟への付け替え**(保存前に確認)。物件名を空にしたら棟から外す。建物名そのものの誤りは棟の画面で直す。
- **D5** 対象=**区分マンション(`apartment_unit`)だけ**。一棟アパート・一棟マンションは物件名を持つだけで棟は作らない。
- **D6** 正式名称は書き換えない。漢数字・ローマ数字・全角半角のそろえは**比べるときだけ**使う。棟の名前は最初に登録した表記のまま残す。
- **D7** 自動で棟を作ったら「正式な表記か確認してください」と知らせ、棟の画面へのリンクを付ける。
- **D8** 候補の一番下に「新しい棟として登録する」を置く(比べる形では同じでも、別の建物のとき)。
- **D9** 同じ町丁目・同じ比べる形の棟が2件以上あるときは、部屋数が一番多い棟(同数なら古い方)につなぎ、「同じ名前の棟が複数あります」と知らせる。
- **D10** 同じ町丁目に同じ名前の棟を作ることを DB で禁止しない(D8 の道を残すため)。同時に保存されたときだけ順番待ちにして、棟が2つできないようにする。
- **D11** 棟の名前を全部屋に反映するとき、誰かがその中の部屋を編集中(編集中の鍵)なら、反映せず止める。
- **D12** DB 変更=buildings に `name_key`(比べる形)と `area_key`(町丁目)の2列を足す(nullable・ADD のみ)。

## 3. 比べる形と町丁目(純関数)

置き場所: `src/lib/building-identity.ts`(新規)。DB にも React にも依存しない。

### 3.1 `buildingNameKey(name: string): string | null`

空・空白だけなら null。それ以外は次の順でそろえる。

1. ローマ数字の記号(`Ⅰ`〜`Ⅻ`/`ⅰ`〜`ⅻ`)を数字にする。NFKC は `Ⅱ`→`ii` にしてしまうため、**NFKC より前**に行う。英字の `II` は変えない(英単語の誤変換を避ける)。
2. 既存の `normalizeBuildingName`(`src/lib/normalize.ts`)= NFKC・空白の除去・小文字化。
3. 漢数字=**数として使われる位置だけ**数字にする。
   - `第` の直後の漢数字の並び(`第一`→`第1`、`第十二`→`第12`)
   - `番館`・`号館`・`号棟`・`番街`・`期` の直前の漢数字の並び(`二番館`→`2番館`)
   - 漢数字の並びは `〇一二三四五六七八九十百` を位取りで読む(`十`→10、`二十一`→21、`百`→100)。
   - それ以外の位置(地名の `一番町`、固有名の `一` など)は変えない。
4. 表記の揺れ: `ヶ`/`ケ`/`が`→`ケ`、`ノ`/`の`/`之`→`ノ`、長音とハイフン類(`ー`・`－`・`‐`・`―`・`-`)→`-`。
5. 末尾の `マンション`・`レジデンス` などの語は**外さない**。

### 3.2 `areaKey(address: string): string | null`

物件・棟の住所から町丁目を取り出す。

1. NFKC・空白除去。
2. `(\d+|[一二三四五六七八九十]+)丁目` が見つかれば、そこまで(丁目の数字は算用数字に)。例 `東京都大田区南雪谷１丁目１６４－２－４５` → `東京都大田区南雪谷1丁目`。
3. 丁目が無ければ、最初の算用数字(番地)の手前まで。例 `○○市大字△△１２３` → `○○市大字△△`。
4. 都道府県が無い住所も、そのまま(比べるのは同じ書き方どうしで足りる)。ただし市区町村の手前で切れて短すぎる(市区町村を含まない)ものは null。
5. 取り出せなければ null。

### 3.3 テスト

例を表にして全件を回す(漢数字・ローマ数字が正式名称の例、地名の `一` を変えない例、丁目なし、全角数字、崩れた住所)。

## 4. 保存時の判断(1か所に集約)

置き場所: `src/lib/building-link/resolve.ts`(判断=純関数)+ `src/lib/building-link/apply.ts`(DB=トランザクション内で使う)。

### 4.1 入力

```
{ propertyType, buildingName, address,
  choice: { kind: "auto" } | { kind: "existing", buildingId } | { kind: "new" },
  currentBuildingId }   // 編集時のみ
```

### 4.2 判断(純関数 `decideBuildingLink`)

候補(同じ `area_key` かつ同じ `name_key` の棟の一覧・部屋数・作成日時)を受け取り、次を返す。

| 条件 | 結果 |
|---|---|
| 区分マンション以外 | `unlink`(つながっていれば外す・物件名は今までどおり) |
| 物件名が空 | `unlink` |
| choice=existing | その棟へ `link`(棟が無い・消えていたら 409) |
| choice=new | `create` |
| auto・候補1件 | その棟へ `link` |
| auto・候補0件 | `create` |
| auto・候補2件以上 | 部屋数最多(同数なら作成が古い)へ `link` + 注意 `duplicate_names` |
| auto・`area_key` が null | `create` + 注意 `area_unknown` |

`link`/`create` の結果に、物件名を棟の正式な表記へそろえたか(`renamedFrom`)を添える。

### 4.3 DB への適用(`applyBuildingLink(tx, …)`)

1. `pg_advisory_xact_lock(hashtext('building-link:' || area_key || ':' || name_key))` で順番待ち(area_key が null のときは name_key だけ)。
2. 順番待ちのあとに候補を読み直して判断する(同時に来た2人目は、1人目が作った棟を見つけてつながる)。
3. `create`: buildings に name=入力の物件名(そのまま)・address=物件の住所から部屋の部分を除いたもの。受付帳由来の区分は住所の末尾が家屋番号(`building_number`)と一致するので、そのときだけ家屋番号の最後の `－` 以降を住所から除く(例 `…南雪谷1丁目164－2－45`→`…南雪谷1丁目164－2`)。一致しない(手入力の住居表示など)ときは住所そのまま・name_key・area_key・createdBy を入れる。監査ログ `building.auto_create`。
4. 物件の `building_id` と `building_name`(=棟の正式な表記)を更新。変更があれば監査ログ `property.building_link` / `property.building_relink` / `property.building_unlink`。
5. 結果(棟の id・名前・作ったか・そろえたか・注意)を返し、各 API がレスポンスに載せる。

ロック順: 物件の保存は既存どおり物件行を先に扱い、そのあと本関数でアドバイザリロック → 棟。棟の名前の反映(§6.3)は棟の行 → 部屋の行の順。⚠段3の実装で順番を 部屋 → 棟 に変えた(販売図面の書き戻しと同じ向き・待ちの輪を防ぐ)。両者が逆順で同じ行を待つことはない(本関数は棟の行をロックしない・読むだけ)。

### 4.4 入口ごとの組み込み

| 入口 | 変更 |
|---|---|
| 新規登録 `POST /api/properties` | schema に `buildingChoice` を追加。作成と同じトランザクションで `applyBuildingLink` |
| 編集 `PATCH /api/properties/[id]` | 物件名・種別・住所が変わったとき、または `buildingChoice` があるときだけ適用。付け替えは画面で確認済みの前提(API は確認の有無を見ない) |
| 貼り付けて物件化 `POST /api/import/paste/commit` | 確認画面に「つなぐ先の棟」を出す(候補 API を使う)。commit で適用 |
| Excel 取込 | 貼り付けて物件化の commit を1行ずつ通すので自動で同じになる(choice=auto) |
| CSV 取込 `api/import/csv` | `resolveBuildingId` を本関数に置き換える(既存の部分一致・needs_review の候補提示は残す)。**不具合修正**: 要確認で選んだ `__resolved_building_id` を、行の確定(`rows/[rowId]`・`retry`)で choice=existing として使う |
| 棟の画面「部屋を追加」 | **不具合修正**: 種別を `apartment_unit`、物件名を棟の名前、棟へ link で作る |
| 現地調査からの物件化 | 変更なし(物件名の欄が無い) |

## 5. 候補の API

`GET /api/buildings/suggest?name=…&address=…`(`property:read`)

- name が比べる形で2文字未満なら空。
- 返すのは最大10件: 同じ `name_key` の棟(同じ `area_key` を先頭)+ 名前の部分一致(`name ILIKE`)の棟。
- 各行: id・name・address の町丁目まで・部屋数・`sameName`(name_key 一致)・`sameArea`(area_key 一致)。
- 棟の住所は町丁目までに丸めて返す(候補一覧で番地まで並べない)。

## 6. 画面

### 6.1 物件名の入力欄(新規登録・編集)

区分マンションのときだけ候補つき。部品 `src/components/buildings/building-name-combobox.tsx`(新規)。

- 2文字目から 300ms おいて候補 API を呼ぶ。古い応答は捨てる(`owner-link-modal` の連番方式)。
- 行: 棟の名前・町丁目・部屋数。`sameName` に「同じ名前」、`sameName && !sameArea` に「丁目が違います」。
- 一番下に「新しい棟として登録する」。
- 選ぶと欄の下に「棟『…』(…・N部屋)につなぎます」。もう一度打ち直すと選択は外れて auto に戻る。
- 上下キー・Enter・Esc。スマホは行の高さ 44px 以上。

### 6.2 保存後の知らせ

API の結果から:
- link: 「棟『…』につなぎました」(そろえたときは「(入力: …)」を添える)
- create: 「棟『…』を新しく作りました。正式な表記か確認してください」+ 棟の画面へのリンク
- 注意 `duplicate_names`: 「同じ名前の棟が複数あります。棟の一覧で確かめてください」
- 注意 `area_unknown`: 「住所から町丁目を読み取れなかったため、新しい棟として作りました」

### 6.3 付け替えの確認と、棟の名前の反映

- 編集で物件名を変えて保存するとき、つながっている棟の名前と比べる形が違えば「棟『A』から付け替えます」と確認する。
- 棟の画面で名前を保存するとき、つながっている部屋が1件以上あれば「部屋N件の物件名も直します」と確認する。
- サーバー(`PATCH /api/buildings/[id]`): ⚠段3の実装で順番を 部屋 → 棟 に変えた(販売図面の書き戻しと同じ向き・待ちの輪を防ぐ)。棟の行をロック → name・name_key を更新 → つながっている部屋に編集中の鍵があれば 409(件数だけ返す・誰が編集中かは返さない)→ 無ければ部屋の `building_name` を新しい名前にし、版番号を進める。監査ログ `building.rename_propagate`(件数)。

### 6.4 写真タブの案内(常に出す)

`PhotoTabBuildingHint` を種別と棟の有無で3通りに:
- 区分マンション・棟あり: 棟写真へのリンク(実績162のまま)
- 区分マンション・棟なし: 「物件名(マンション名)を入れると棟につながり、共用部・外観の写真を部屋どうしで共有できます」+ 編集を開くボタン
- それ以外: 「この物件の写真です。」

## 7. データベース

migration `…_add_building_identity_keys`:

```sql
ALTER TABLE "buildings" ADD COLUMN "name_key" TEXT;
ALTER TABLE "buildings" ADD COLUMN "area_key" TEXT;
CREATE INDEX "buildings_area_key_name_key_idx" ON "buildings"("area_key", "name_key");
```

- 2列は棟を作る・名前を変えるたびにアプリが計算して入れる(比べる形の計算は JS のため、SQL の migration では埋めない)。
- 既存の棟(本番1件)は key が null のまま残る。候補 API と判断は、key が null の棟も名前と住所からその場で計算して比べ、見つけたら key を埋める。
- ADD のみ。戻すときはコードだけ戻せばよい(列は残っても無害)。

## 8. 記録・権限・個人情報

- 棟の作成・名前の変更は既存どおり `property:write`。候補 API は `property:read`。
- 監査ログの detail には件数・id・種別だけを入れ、物件の住所は入れない(棟の名前は物件名と同じ扱いで可)。
- 物件の変更履歴に `buildingId` の日本語名「棟」を追加。

## 9. テスト

- `building-identity`: 例の表(正式名称が漢数字/ローマ数字・地名の一・丁目なし・崩れた住所)。
- `decideBuildingLink`: §4.2 の表を全行。
- 同時保存: 2人が同じ新しい建物を登録する順番の組み合わせを総当たり(判断を純関数に出し、ロック後の読み直しを含めた手順を列挙して確かめる)。
- 入口ごと: 新規・編集・貼り付け・CSV(要確認の選択が効く)・部屋を追加 で、同じ入力が同じ棟につながる。
- 棟の名前の反映: 編集中の鍵があると 409・無いと全部屋がそろう・版番号が進む。
- 画面: 候補部品・案内3通りを SSR で文言と href を確かめる。
