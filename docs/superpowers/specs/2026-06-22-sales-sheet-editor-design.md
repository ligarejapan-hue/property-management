# 販売図面エディタ 設計書（仕様）

- 作成日: 2026-06-22
- 対象: property-management
- ステータス: 設計（実装前・ユーザーレビュー待ち）

## 1. 目的
物件1枚もの（マイソク＝販売図面）を、システムの物件データ・写真・間取り図を土台に、
**アプリ内のデザインエディタ**で組み上げ、デザイン性の高い **PDF／画像** として出力する。
毎回の手作業（Excel/PowerPointでのレイアウト）をなくし、見た目の品質と作成スピードを両立する。

参考とする到達イメージ：フルカラーの designed マイソク（大きな価格表示、特徴バッジ、間取り中央、
複数写真、ACCESS、会社帯、QR）。＝ デザインツールの出力相当。Excel流し込みでは到達できないため、
**HTML/CSS で構築し、ヘッドレスブラウザでPDF/画像化**する方式を採る（既存 playwright を流用）。

## 2. スコープ
### 含む（全部入り・ユーザー合意 2026-06-22）
1. テンプレ・ギャラリー（複数フォーマットから選択）
2. データ自動取り込み（物件/建物/所有者/写真→図面の初期内容）
3. キャンバス・エディタ（**自由配置**：ドラッグ／拡大縮小／重ね順）
4. スマート自動レイアウト（要素の相互自動調整。自動が土台→手動で上書き）
5. バッジ・デザイナー（設備・特徴の**オリジナルバッジ**作成）
6. 写真管理（**枚数自由**・アップロード/既存選択・トリミング・パノラマ対応）
7. QR生成（**中身は設定式**。既定は実装時に確定）
8. 出力エンジン（高品質 **PDF/画像**）
9. 保存・複製（図面デザインを物件ごとに保存・再編集）
10. 画面導線＋権限（既存の認証/権限に準拠）

### 含まない（将来・別テーマ）
- 間取り図の**自動作図**（寸法から図を描く）。本仕様は「間取り画像のアップロード配置」まで。
- 外部サービス（REINS/SUUMO等）からの**情報自動収集**。
- Excel(.xlsx) を主出力にすること（この見た目はExcel不可）。将来「簡易データ版Excel」を別途出すのは可。

## 3. 利用者と基本フロー
対象ユーザー：社内スタッフ（admin / office_staff / field_staff、権限に応じる）。
1. 物件詳細ページで「販売図面を作成」を押す。
2. **テンプレ・ギャラリー**から1つ選ぶ（種別に合うものを自動提案）。
3. 選んだテンプレに**物件データ・写真が自動配置**された状態でエディタが開く。
4. エディタで調整：写真の追加/配置/拡縮、文字のフォント/サイズ/装飾/色、間取り画像の配置、
   バッジ追加、テーマ色、表示項目の切替、QR配置。スマート自動レイアウトが土台配置を支援。
5. **保存**（物件に紐づくデザインとして保存・再編集可）。
6. **PDF／画像で出力**（ダウンロード）。

## 4. アーキテクチャ全体
- **1つの「ドキュメントモデル（構造化JSON）」**を中心に据える。
  - ページ（サイズ/向き）＋ 要素配列 elements[]（種類・位置・サイズ・重ね順・スタイル・内容）。
- **同じドキュメントモデルを、同じレンダラ（HTML/CSS）で描画**する：
  - 画面プレビュー＝ブラウザでレンダラを描画＋編集操作を重ねる。
  - 出力＝サーバーで**同じレンダラのHTMLをヘッドレスブラウザに読ませて PDF/画像化**。
  - → 「**見たまま出力（WYSIWYG）**」を構造的に保証する（プレビューと出力が同一定義・同一描画）。
- 編集UIはレンダラの上に「選択・移動・拡縮・整列」のオーバーレイを載せる（自由配置）。

## 5. コンポーネント（独立した部品）
各部品は「役割／入力／出力／依存」を明確にし、単体で理解・テストできる単位にする。

1. **ドキュメントモデル & スキーマ**（`sales-sheet/document` 型）
   - 役割：図面の構造化定義（page, elements, theme）。型＋バリデーション（zod）。
   - 依存：なし（純データ）。他の全部品がこれを介して連携。
2. **レンダラ**（`SalesSheetRenderer`）
   - 役割：ドキュメントモデル→HTML/CSS描画（要素種別ごとの描画）。**ブラウザ/サーバー共通**。
   - 入力：document（＋画像URL/バイト）。出力：DOM（プレビュー）／HTML文字列（サーバー出力用）。
3. **エディタUI**（`SalesSheetEditor`）
   - 役割：レンダラ＋編集オーバーレイ（選択/ドラッグ/拡縮/重ね順/整列/スナップ）。右パネル（写真/文字/間取り/バッジ/テーマ/表示項目/QR）。
   - 依存：レンダラ、ドキュメントモデル、自動レイアウト、写真管理、バッジ、QR。
4. **データ自動取り込み**（`build-initial-document`）
   - 役割：Property/Building/Owner/写真 → 選択テンプレに差し込んだ初期 document を生成。権限/マスキング準拠。
   - 依存：Prisma、既存 permissions/property-access、storage。
5. **テンプレ・ギャラリー**（`SalesSheetTemplate`）
   - 役割：複数フォーマット（=初期document＋プレースホルダ）の定義・一覧・プレビュー・選択。
   - 内容：シード提供の標準テンプレ数種＋将来ユーザー保存テンプレ。
6. **スマート自動レイアウト**（`auto-layout`）（最難所・§8）
   - 役割：要素サイズ変更時の相互調整（間取り拡大→写真縮小、パノラマ追加→外観/間取り縮小）。
   - 方式：ゾーン＋制約ベース。自動が土台、ユーザー手動で上書き可。
7. **バッジ・デザイナー**（`BadgeDesigner` / `BadgePreset`）
   - 役割：設備/特徴バッジの作成（形/色/アイコン/文言）。プリセット保存・再利用。
   - 出力：document の badge 要素＋保存プリセット。
8. **写真管理**（`photo-manager`）
   - 役割：枚数自由のアップロード/既存写真選択/トリミング/パノラマ判定（縦横比でレイアウト連携）。
   - 依存：既存の storage（upload/read）＋写真検証ルール流用。
9. **QR生成**（`qr`）
   - 役割：設定された中身（物件URL/自社ページ/連絡先/外部掲載）からQR画像を生成し配置。
10. **出力エンジン**（`render-to-output`）
    - 役割：document → レンダラHTML → ヘッドレスブラウザで **PDF/画像**（A4横/縦、解像度指定）。
    - 依存：playwright（既存）＋レンダラ。
11. **保存・API・導線**
    - `SalesSheetDesign`（物件ごとの保存デザイン）。API群（後述）。物件詳細のボタン＋エディタ画面ルート。

## 6. データモデル（新規・Prisma）
> 反映時の `prisma migrate deploy` は**ユーザー承認後**（既存運用と同じ）。

- **SalesSheetDesign**：保存された図面デザイン。
  - id, propertyId(FK), title, document(JSON: ページ/要素/テーマ), templateId(任意),
    createdBy, updatedBy, createdAt, updatedAt, （任意 thumbnailUrl）。
- **SalesSheetTemplate**：テンプレ定義。
  - id, name, category（種別: 売マンション/売戸建/売土地/…）, document(JSON: 初期レイアウト＋プレースホルダ),
    isBuiltin(シード), createdBy(ユーザー保存時), createdAt。
- **BadgePreset**：オリジナルバッジのプリセット。
  - id, label, shape, colors(JSON), icon, createdBy, createdAt。
- 画像（写真・間取り・出力サムネ）は既存 storage を使用（`/uploads/...`・read(key)）。

## 7. データフロー
1. ボタン → テンプレ選択 → `build-initial-document`（DBデータ＋テンプレ＝初期document）。
2. エディタで編集（documentを更新）。プレビューはレンダラで即時反映。
3. 保存：`POST /api/properties/[id]/sales-sheets`（document永続化）／更新 `PUT .../[sheetId]`。
4. 出力：`POST .../[sheetId]/export?format=pdf|png` → 出力エンジン → ファイル返却。
   - 画像/写真はサーバー側 `storage.read(key)` でバイト取得し埋め込み（PII/認可は既存準拠）。

## 8. スマート自動レイアウト（最難所・設計方針）
**ゴール**：要素の大きさを変えると他要素が自動で気持ちよく再配置される（間取り拡大→写真縮小、
パノラマ写真追加→外観/間取りが自動で小さくなる 等）。かつ**自由配置と両立**。

**方式（ゾーン＋制約）**：
- ページを論理「ゾーン」（例：写真ゾーン/間取りゾーン/データゾーン/帯）に分け、ゾーン内は
  フレックス的な相対サイズ（重み）で自動配分。1要素を拡大→同ゾーン/関連ゾーンの重みを再計算して縮小。
- パノラマ（横長比率）を検知したら専用ルール（横幅優先・他を縮小）を適用。
- **モード**：①自動（土台レイアウトを提案・相互調整ON）／②手動（自由配置＝特定要素を「固定」して
  自動調整から除外し、絶対座標で配置）。要素ごとに「自動/固定」フラグ。
- 既定は自動。ユーザーが動かした要素は「固定」に切替（手動が勝つ）。

**リスクと対策**：ここが最も難しく不確実。**実装初期に独立した試作（プロトタイプ）**を作り、
代表ケース（写真2/3/5枚、パノラマ有無、間取り大小）で挙動を確認してから本実装に進む。
（このプロトタイプの結果次第で、自動の賢さの範囲を調整する＝過剰な自動化はしない）

## 9. バッジ・デザイナー
- バッジ要素＝{ label, shape(角丸/ピル/リボン等), 背景色/文字色, icon(セット内から選択), サイズ }。
- 標準アイコンセット（設備系：駐車場/エレベーター/ペット/リノベ/オートロック等）を同梱。
- ユーザーが作ったバッジは **BadgePreset** に保存し、他物件でも再利用。
- document 内では通常の「badge 要素」として配置（自由配置・自動レイアウト対象）。

## 10. テンプレ・ギャラリー
- 標準テンプレを数種シード（種別別・縦横別・写真多め/間取り大きめ 等の構図違い）。
- 選択時に初期document化。ユーザーが作った図面を「テンプレとして保存」も可（将来含む）。
- **着手優先順位（ユーザー指定 2026-06-22）**：① 売土地 → ② 売マンション → ③ 売戸建 → ④ 一棟（一棟物）。まず①から用意し順次追加。

## 11. QR
- 中身は設定式：物件詳細URL／自社の物件紹介ページ／連絡先(電話/メール)／外部掲載ページ から選択（複数可）。
- 既定の中身は実装時にユーザーと確定（現時点「未定」）。実装ではまず「物件詳細URL」を仮既定とし切替可能に。
- 生成は qrcode 系ライブラリ。document の qr 要素として配置。

## 12. 出力エンジン
- 形式：**PDF** と **画像(PNG/JPG)**。
- 用紙：**A4横を既定**、A4縦も選択可（テンプレに向き属性）。
- 方式：レンダラのHTMLをヘッドレスブラウザ（既存 playwright/chromium）で `page.pdf()` / screenshot。
  - 本番では chromium 実体が必要（現状 `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`）＝反映時に `playwright install chromium` を実施（ops・ユーザー承認）。
- フォント：図面用フォントをサーバーに用意（日本語含む）し、プレビューと出力で同一フォントを使用。

## 13. 権限・統合・セキュリティ
- 認証：`getApiSession()`。権限：新リソース `sales_sheet`（read/write/export）を追加 or 既存 `property` 準拠（実装時に確定。最小は property:read＋対象物件アクセス可否）。
- 物件アクセス：`canAccessPropertyRecord`（field_staff は自分の物件のみ）。
- 出力API はログイン必須（proxy.ts の公開パスには載せない＝§22Fの cron とは別。人間操作のため）。
- PII：写真/所有者情報の表示はマスキング/権限ルール準拠。ログに blob key やPIIを出さない。
- storage：新規アップロード（間取り/写真）は既存の非public保存（`LOCAL_UPLOAD_ROOT`）＋ read 経路に準拠。

## 14. エラー処理
- 必須要素欠落（例：価格未入力）→エディタ上で明示（出力はブロックしない＝任意項目化）。
- 画像形式/サイズ不正→既存の写真検証ルールで弾く。
- 出力失敗（chromium未導入等）→ユーザーに分かるメッセージ＋ログ（詳細はサーバーログ・PII非出力）。
- 保存競合→楽観ロック（updatedAt）で検知。

## 15. テスト方針
- ドキュメントモデル/スキーマ：バリデーション単体。
- データ自動取り込み：物件→初期document（項目マッピング・権限/マスキング）。
- レンダラ：document→HTML（要素種別ごと・スナップショット）。プレビューと出力が同一HTMLである回帰。
- 自動レイアウト：代表ケースの配分結果（決定的）を単体テスト。
- 出力エンジン：PDF/画像が生成される（サイズ/ページ数）E2E（chromiumあり環境）。
- 権限/アクセス制御・必須/任意バリデーション。

## 16. 技術選定（候補）
- フレーム：既存 Next.js(App Router)/React/Prisma/Tailwind。
- 編集オーバーレイ：HTML要素の移動/拡縮ライブラリ（例 **Moveable** または react-rnd）＋自作の整列/スナップ。
- 描画：**HTML/CSS レンダラ**（ブラウザ/サーバー共通）。※canvas(Konva)案も検討したが、文字/フォント忠実性とPDF流用の点でHTML/CSSを推奨。
- QR：`qrcode`。
- 出力：既存 **playwright**（ヘッドレス chromium）で PDF/画像。
- いずれも**ゼロからは作らず実績あるライブラリを土台**にする。新規依存は package 追加（ユーザー承認の運用に従う）。

## 17. リスクと対策
1. **スマート自動レイアウト（最大リスク）**：§8 の通り、独立プロトタイプを最初に作り感触確認 → 範囲確定。
2. **WYSIWYG ずれ**：プレビューと出力を**同一レンダラ/同一フォント**にすることで構造的に回避。
3. **本番 chromium**：反映時に `playwright install chromium`（ops・承認）。ディスク/メモリは現状余裕。
4. **規模**：大きい。§18 の順で内部実装し、早期に動く核を見せる（長いブラックボックスにしない）。
5. **新規依存・新規テーブル**：package/lockfile 変更・migration はユーザー承認運用に従う。

## 18. 内部実装順序（「全部入り」だが段階的に動かす）
全部を一度に納めるが、内部は次の順で組み、各段で動作確認する：
1. ドキュメントモデル＋レンダラ（HTML/CSS）＋静的プレビュー
2. 出力エンジン（PDF/画像）＝核の往復を最初に成立させる（見たまま出力の土台）
3. データ自動取り込み（実物件→初期document）
4. エディタUI（自由配置：選択/移動/拡縮/重ね順）＋写真管理（枚数自由）
5. テンプレ・ギャラリー（標準数種）
6. スマート自動レイアウト（先行プロトタイプ→本実装）
7. バッジ・デザイナー
8. QR・テーマ色・表示項目・保存/複製・権限/導線の仕上げ

## 19. 確定した決定 / 既定
- 出力：PDF＋画像。用紙 A4横既定（縦も可）。
- 編集：自由配置（手動）＋スマート自動レイアウト（土台）。手動が自動に勝つ。
- 写真：枚数自由。パノラマは自動レイアウトの専用ルール対象。
- QR：設定式。既定の中身は実装時に確定（仮既定＝物件詳細URL）。
- Excel：本機能の主出力にしない（将来の簡易データ版は別途）。
- 端末：**デスクトップ前提**（編集は複雑なため）。閲覧/出力はモバイルでも可。【ユーザー確認済 2026-06-22】
- 用紙：**A4横を既定**【ユーザー確認済】。標準テンプレ着手順＝**売土地→売マンション→売戸建→一棟**【ユーザー指定】。
