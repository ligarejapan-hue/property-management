## 前提(現状の作り)

- 有料取得は1物件×1通ずつ。種類は `certificateType: "owner"`(所有者事項)で**型レベルで固定**
- 二重課金台帳(AuditLog)の鍵は既に `物件×地番×種別` = **種別を含む**ため、
  種類が増えても台帳の設計変更は不要(所有者事項を買った後に全部事項を買うのは正当な別購入)
- 取得経路は2つ: **不動産番号**/**所在+地番**(検索→候補選択→取得)。
  ⚠ただし**有料取得が配線済みなのは所在+地番のみ**。番号経路は実サイトの
  請求フロー判明時に fail-closed のまま止めてある(カートに触れる前に停止)
- 外部サイト制約: **アカウント同時1セッション**・スロットル(最小30秒間隔)・
  課金スイッチ `REGISTRY_FETCH_PURCHASE_ENABLED` 未投入=501休眠
- 類似の前例: 登記PDF一括取込(ImportJob+行テーブル・**画面からの再開方式**で
  数千件を分割処理・中断/再開・スタック検出あり)

## 第1部: 種類の2択(全部事項/所有者事項)

小さい変更。単独でも出せる。

- `certificateType: "owner" | "all"` へ拡張(既定 owner)
- 請求画面の正規化: owner=所有者事項のみON(現行) / all=全部事項のみON。
  ⚠**どちらの場合も「揃えられなければ請求を押さずに中止」の原則は維持**
  (余計なものを買わない)。サイトの初期状態は全部事項ONなので、all は
  「他を全部OFFにできたか」の検証になる
- 取得の確認ダイアログにラジオ(所有者事項=既定/全部事項)。**料金が違う旨を明記**
- 監査 detail に種別を記録(非PII)
- **添付にも種別が分かる印を残す**(@codex 設計指摘)。同じ物件で所有者事項と
  全部事項を両方買うのは正当な使い方だが、既存の添付はどちらも同じ
  「registry.pdf」に見え、**画面で区別できない**。添付のファイル名/表示名に
  安全な定型ラベル(「謄本(所有者事項)」「謄本(全部事項)」・非PII)を含める
- 台帳の鍵は既に種別込み=変更不要

## 第2部: 複数物件の一括取得

### 全体像

```
物件一覧で複数選択(チェックボックス)
  → 「謄本を一括取得」ボタン(registry:auto_fetch 保持者のみ表示)
  → 確認画面: 対象N件の内訳 + 種類(2択) + ⚠課金の明示
  → ジョブ作成(DB) → 進捗画面(何件目/成功/失敗/スキップ)
  → 1件ずつ順に処理(スロットルの実値の間隔・同時1セッション遵守)
  → 完了: 取得したPDFは各物件に添付(単発取得と同じ置き場)
```

### ジョブの持ち方

**専用テーブル**(ImportJob の流用はしない。fileName 必須など取込前提の列が
合わず、無理に載せると後で歪む):

```
registry_fetch_jobs:      id / status(pending|processing|paused|completed|cancelled)
                          / certificate_type / requested_by / counts / timestamps
registry_fetch_job_items: id / job_id / property_id / status(pending|processing|done
                          |failed|skipped|charged_but_failed|charge_unknown)
                          / charge_phase(none|attempting|charged・**請求を押す前に
                          attempting をDBへ書く**。放置復旧はこの列で課金前/課金後を
                          区別する=スキーマに無いと復旧規則が実装できない)
                          / error_code / attachment_id
                          / started_at / updated_at(status/charge_phase を書き換える
                          たびに更新。⚠これが無いと「処理中のまま放置」を**見分ける
                          根拠が無く**、動いている最中の項目を誤って課金不明に倒すか、
                          永久に固まるかのどちらかになる) / charge_attempted_at
                          / processed_at(終端に達した時刻) / property_fingerprint_hash
                          / purchase_key_hash(台帳と同じ 物件×地番/家屋番号×種別 の
                          sha256。**課金境界より前に必ず書く**。⚠これが無いと、
                          charge_unknown の後に物件の地番が編集された場合、いま再計算
                          した鍵では**古い購入試行と同一か判定できず**、ガードが
                          素通りして同じ謄本をもう一度買える)(作成時の物件指紋の
                          sha256。⚠**生の指紋は保存しない**=住所/地番/番号の直列化文字列
                          なので、行に持つと将来のジョブ詳細APIから漏れる。比較は
                          処理時に現在の物件から再計算したハッシュと突き合わせる)
```

migration は additive(新テーブル2つのみ)。

### 処理方式: **画面からの分割実行**(登記PDF一括取込と同型)

- 進捗画面が「次の1件を処理」APIを順に呼ぶ。**タブを閉じると止まる**が、
  ジョブはDBに残るので**開き直せば続きから再開**できる
- ⚠**処理APIはDB側で項目を原子的に掴んでから外部に触る**(@codex 設計指摘)。
  進捗画面が2つのタブで開かれたり、送信の再試行が起きると、同じ項目を
  **二重に処理=二重に課金**し得る。画面の行儀に頼らず、
  updateMany(where: { id, status: "pending" }) の**0行=他が処理中**で弾く
  (登記PDF一括取込が単一処理でも同じ守りを敷いている前例に合わせる)。
  件数集計・paused への遷移も同じCASで直列化する
- ⚠**サーバー常駐の自動実行(systemd timer)にはしない**。お金が動く処理を
  無人で回すのは、実課金の通しテストすら未実施の現段階では踏み込みすぎ。
  将来必要になったら別途設計する(前例: 添付お掃除・巡回の見回り)
- ⚠**「処理中のまま放置」の扱いは取込の流用では危険**(@codex 設計指摘 P1)。
  タブが閉じた/プロセスが再起動した項目は、**請求を押した後・記録する前**で
  止まっている可能性がある。取込と同じ「失敗にして再実行」をすると、
  **記録なき課金**の上に**再購入の二重課金**が乗る。
  - 項目に**課金段階の印**を持つ(請求を押す**前に**DBへ「課金試行中」を書き、
    押した後に「課金済み」へ進める。書けなければ押さない)
  - ⚠**印を書く場所は provider の中の課金境界**(@codex 設計指摘)。今の provider は
    課金境界を呼び出し側に見せていない(内部の chargeState を請求クリック直前に
    切り替えるだけ)。呼び出し前に attempting を書くと**課金前の普通の失敗まで
    課金不明**になり、呼び出し後に書くのでは**クリック直後の死**を取りこぼす。
    provider に **onBeforeCharge / onCharged のフック**を追加し(await される・
    onBeforeCharge の失敗=DBに書けなければ**請求を押さない**)、一括はここで
    DBの印を進める。単発の将来の台帳強化にも同じフックが使える
  - 放置項目のうち課金段階が「試行中」以降のものは**課金不明**として扱い、
    ジョブごと paused にする。**自動では再実行しない**(運用者がマイページを
    確認して手で決める)。課金前で止まった項目だけ従来どおり失敗扱いにできる

### 1件ごとの処理規則

⚠**取得経路は所在+地番に統一する**(@codex 設計指摘)。**不動産番号での有料取得は
まだ配線されていない**(実サイトの請求フロー判明時に fail-closed のまま止めてある。
searchByRealEstateNumber はカートに触れる前に provider_error で停止する)。
「番号があれば番号で」と書くと、番号持ちの物件が**全件失敗**する。
番号経路の有料配線は別設計(要live校正)とし、第1弾のスコープに含めない。

1. **住所+(地番または家屋番号)が揃っていれば所在検索**を実行し、候補と物件登録の
   対応する値を突き合わせる(@codex 設計指摘: 単発の取得は家屋番号のみの建物にも
   対応済み。「地番が無ければスキップ」と書くと**建物物件が一括で退行**する):
   - **家屋番号があれば建物として家屋番号で照合**(単発の取得と同じ判定=
     家屋番号の有無が土地/建物の分岐)。地番との照合は**家屋番号が無い土地だけ**。
     ⚠逆(地番優先)にすると、地番も登録済みの建物が土地として検索され、
     単発では取れる建物が一括で取れない/別物に一致する(@codex 設計指摘)
   - **完全一致がちょうど1件** → その候補で取得
   - ⚠**候補一覧が完全に読めたときだけ判定する**(@codex 設計指摘)。今の provider は
     ページ上限(MAX_DIALOG_PAGES)超過やページ送りの timeout で**部分的な候補**を
     黙って返す(呼び出し側に「途中まで」の印が無い)。部分結果の中の
     「ちょうど1件」は、**読んでいないページに別の一致**が居るかもしれない。
     provider に**完全性の印(truncated)**を追加し、不完全なら skipped(要手動)。
     「あいまいなまま買わない」の保証は完全な一覧の上でしか成立しない
   - 0件 / 複数 / 不一致 → **skipped(要手動)にして課金しない**。
     ⚠一括処理での「たぶんこれ」は禁止。単発画面なら人が候補を見て選べるが、
     一括では見ていないので、**機械が確信できる場合しか買わない**
2. **住所も地番/家屋番号も不足する物件(番号しか無い等)は skipped(要手動)**。理由コードを
   分けて進捗画面に「番号での取得は今後対応」と表示する
3. 失敗の隔離は**課金の前後で変える**(@codex 設計指摘 P1):
   - **課金前**の failed / skipped は残りを止めない(項目ごとに記録して続行)
   - **charged_but_failed が1件でも出たら、ジョブ全体を paused にする**。
     課金境界を越えた失敗の原因(ダウンロードのセレクタずれ・保存失敗・
     アカウント状態)は**次の項目でも再発する**可能性が高く、続行すると
     「払ったのに添付されない」購入を量産する。運用者がマイページを確認して
     から再開する(再開ボタン+確認済みチェック)。該当項目は再実行禁止を明示
4. 台帳は従来どおり項目ごとに照合(30日以内の同一 物件×地番×種別 は再購入させない
   =**一括に同じ物件を2回入れても二重課金しない**)
   - ⚠**未解決の課金試行はすべて二重課金ガードに含める**(@codex 設計指摘 P1)。台帳
     (AuditLog)への記録は**PDFを受け取った後**なので、請求を押してから台帳を書く
     までの間に落ちた項目は**台帳に行が無い**。しかもその項目の課金段階は
     attempting とは限らない(押した後に onCharged で charged へ進んでから落ちる)。
     ガードは「台帳 OR **終端に達していない項目のうち charge_phase が
     attempting または charged のもの**」で判定し、運用者が課金の有無を記録して
     項目を解決するまで新しい購入を許さない。charge_unknown だけを列挙すると
     charged のまま落ちた行が漏れる。⚠照合は**項目に保存した purchase_key_hash**
     と行う(いまの物件から再計算しない=編集で鍵がずれても古い試行を見失わない)
   - ⚠**台帳の照合だけでは同時実行に勝てない**(@codex 設計指摘 P1)。台帳への
     記録は購入後なので、**同じ物件を含む2つのジョブ**(または一括と単発の同時
     実行)が、どちらも「まだ台帳に無い」を見てから両方買う隙間がある。
     単発の取得が外部に触れる前に掴む**物件行のロック**(registryStatus/version の
     CAS)を、一括の処理APIも**同じ物件に対して**必ず通す。掴めなければその項目は
     後回し(rate_limited と同じ「後で再試行」扱い・失敗にしない)
5. **間隔は既存スロットルの実値に従う**(@codex 設計指摘)。コード既定は60秒
   (REGISTRY_FETCH_MIN_INTERVAL_MS で短縮可・本番は30秒設定)。
   ⚠スロットルは「待つ」のではなく**早すぎる呼び出しを rate_limited で弾く**。
   一括側が独自の秒数を決め打ちすると、既定環境では**外部に触る前に全件失敗**する。
   処理APIは rate_limited を**失敗にせず**「次はN秒後」と返し、画面側が
   その値だけ待って再呼び出しする(env値を二重に持たない)。
   ⚠**後回しにするときは、掴んだ項目を必ず pending に戻す**(@codex 設計指摘)。
   CASで processing に掴んだ後に throttle や物件ロックで弾かれた場合、そのまま
   「N秒後」を返すと項目は processing のまま残り、**N秒後の再呼び出しには掴める
   行が無い**=ジョブが固まるか、放置復旧が課金前の後回しを終端の失敗に変換して
   しまう。順序を「**throttle/ロックの確認 → 掴む**」にする(確認してから掴むまでの
   競合は掴みのCASが守る)。やむを得ず掴んだ後に弾かれた経路は、応答を返す前に
   **原子的に pending へ戻す**(戻せなかったら課金不明側に倒す)。
   ⚠**事前確認は「消費しない覗き見(peek)」で行う**(@codex 設計指摘)。今の
   tryAcquire は**確認と同時に権利を消費**し、provider も内部でもう一度
   tryAcquire を呼ぶ。事前確認に tryAcquire を使うと**唯一の権利を事前確認が
   食い潰し**、直後の provider 呼び出しが必ず rate_limited になる=正しく
   待っているのに全件が後回しされ続ける。throttle に非消費の peek
   (nextAvailableAt を返すだけ)を追加し、実際の取得は従来どおり provider が
   自分で行う。peek 通過後の競合で provider が rate_limited を返した場合は、
   上記の「掴んだ項目を pending へ戻す」経路で処理する。
   ⚠**「N秒後」を返すには throttle 側の拡張が要る**(@codex 設計指摘)。今の契約は
   tryAcquire の真偽だけで、rate_limited エラーも残り時間を持たない。
   throttle に nextAvailableAt(または retryAfterMs)を追加し、エラーに載せて
   API 応答まで届ける。これをせず画面が独自に env を読むと二重管理になり、
   既定60秒の環境で早すぎるポーリングを繰り返す。1件ずつ直列(同時1セッション制約)
6. **作成時の物件指紋を項目に保存し、課金前に照合する**(@codex 設計指摘)。
   ジョブ作成から処理まで時間が空く(スロットル間隔×件数)ため、その間に住所や地番が
   編集されると、**確認した時とは別の土地を買う**ことになる。単発の取得が
   既に持つ指紋照合(fingerprintProperty)と同じ守りを一括にも敷く
   (⚠保存するのは**ハッシュのみ**。上記スキーマ欄参照)。
   不一致 → skipped(物件情報が変わった・要手動)。課金しない

### 安全弁

- 1ジョブの上限 **50件**(超過は分割を案内)
- 実行前の確認画面に **件数×種類** を明示し、「N件ぶんの利用料金が発生します」
  の確認チェックを必須にする(単発の confirmed と同じ思想)
- ジョブの**中止ボタン**: 処理中の1件が終わり次第停止(課金済みの件はそのまま・
  実況の中止と同じ「節目で止まる」原則)
- ジョブ作成/処理の門は**単発の購入と同じ readiness 判定**に載せる
  (@codex 設計指摘): 課金スイッチ **AND 所在検索の校正済みフラグ**
  (既存の purchase capability と同一)。スイッチだけで判定すると、校正が
  済んでいない環境で**未校正の有料自動操作**が走る。どちらか欠けたら501
- 権限は **registry:auto_fetch AND property:read** を要求し、さらに**項目ごとに
  canAccessPropertyRecord で物件の可視性を検証**する(@codex 設計指摘)。
  単発の取得APIと同じ三重の門。ジョブ作成時に見えない物件が混ざっていれば
  その項目を作らない(403で全体を落とすのではなく、作成時に除外して件数を明示)。
  処理APIも項目ごとに再検証する(作成後に権限や物件が変わり得るため)。
- **ジョブの操作(進捗閲覧/次を処理/中止/再開)は作成者本人に限定**する
  (@codex 設計指摘)。URLを知った別のスタッフが、**他人が確認した課金ジョブ**を
  進めたり止めたりできてはいけない(取込ジョブの executedBy ガードと同型)。
  - ⚠**管理者の代行だけは許す**(@codex 設計指摘)。課金不明で止まったジョブは
    マイページ確認が要るが、作成者が不在だと**誰も再開も中止もできず永久に
    塞がる**。明示の管理権限を持つ者に限り **進捗閲覧/次を処理/中止/再開の
    すべて**を許可する(@codex 設計指摘: 中止/再開だけだと、再開はできても
    **画面駆動の「次を処理」が作成者限定のままで結局進められない**)。
    監査に「誰が代行したか」を残す。一般スタッフは従来どおり自分のジョブのみ。
  監査はジョブ作成/完了/中止+項目ごと

### 出さないもの(スコープ外)

- 概算**金額**の表示はしない(料金はサイト側で改定があり、誤った金額を出して
  確認させるほうが危険。件数×種類のみ明示し、料金表への参照に留める)
- 地図・図面類の種類追加(発注者判断で2択)
- サーバー常駐の無人実行(上記)
