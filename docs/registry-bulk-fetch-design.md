2. **複数の物件をまたいで一気に取得したい**

## 前提(現状の作り)

- 有料取得は1物件×1通ずつ。種類は `certificateType: "owner"`(所有者事項)で**型レベルで固定**
- 二重課金台帳(AuditLog)の鍵は既に `物件×地番×種別` = **種別を含む**ため、
  種類が増えても台帳の設計変更は不要(所有者事項を買った後に全部事項を買うのは正当な別購入)
- 取得経路は2つ: **不動産番号**/**所在+地番**(検索→候補選択→取得)。
  ⚠ただし**有料取得が配線済みなのは所在+地番のみ**。番号経路は実サイトの
  請求フロー判明時に fail-closed のまま止めてある(カートに触れる前に停止)
- 外部サイト制約: **アカウント同時1セッション**・スロットル(最小30秒間隔)・
  課金スイッチ `REGISTRY_FETCH_PURCHASE_ENABLED` 未投入=501休眠
- 類似の前例: 登記PDF一括取込(ImportJob+行テーブル・**画面からの再開方式**で
  数千件を分割処理・中断/再開・スタック検出あり)

## 第1部: 種類の2択(全部事項/所有者事項)

小さい変更。単独でも出せる。

- `certificateType: "owner" | "all"` へ拡張(既定 owner)
- ⚠**全部事項は過去(抹消)の所有者を物件に取り込まない**(@codex 設計指摘 P1・
  これは業務データの正しさの問題)。全部事項には**抹消された旧所有者**が
  下線(＊)付きで載る。今の解析(pdf-registry-parser)は抹消マーカー＊を
  **落として**現在/抹消を区別せず、process が解析した所有者を**すべて現在の
  所有者として物件に紐づける**。種別を all に広げるだけだと、**旧所有者が
  現在の所有者として登録**され、DMの宛先などが誤る。対策:
  - all のPDFは**現在の所有者だけを反映**するよう解析側で現在/抹消を判別する
    (抹消行=下線＊は現在所有者に含めない)。判別が確実にできないうちは
  - **all はPDFを添付するだけで所有者反映はしない**(owner のときだけ反映)を
    安全側の既定にする
  - **抹消所有者を含む fixture テスト**を必須にする(現在所有者だけが反映される
    ことを固定)
- 請求画面の正規化: owner=所有者事項のみON(現行) / all=全部事項のみON。
  ⚠**どちらの場合も「揃えられなければ請求を押さずに中止」の原則は維持**
  (余計なものを買わない)。サイトの初期状態は全部事項ONなので、all は
  「他を全部OFFにできたか」の検証になる
- 取得の確認ダイアログにラジオ(所有者事項=既定/全部事項)。**料金が違う旨を明記**
- 監査 detail に種別を記録(非PII)
- **添付にも種別が分かる印を残す**(@codex 設計指摘)。同じ物件で所有者事項と
  全部事項を両方買うのは正当な使い方だが、既存の添付はどちらも同じ
  「registry.pdf」に見え、**画面で区別できない**。
  ⚠**ファイル名に入れるだけでは表に出ない**(@codex 設計指摘)。添付画面は
  個人情報保護のため**意図的に生のファイル名を隠し**、謄本を一律
  「registry.pdf」と表示している(ファイル名には所在が入り得るため)。この
  マスクは壊さない。代わりに attachments へ**安全な定型値の列**
  (registry_certificate_type: owner|all・nullable・additive)を足し、
  マスク表示側がこの列から「謄本(所有者事項).pdf」「謄本(全部事項).pdf」の
  **固定ラベル**を組み立てる(ダウンロード名も同じ)。生のファイル名は今後も出さない。
  ⚠**null(種別不明)の既定を必ず定義する**(@codex 設計指摘)。この列は nullable
  なので、**移行前の既存謄本添付と、手動アップロード(種別を持たない経路)は
  すべて null** になる。owner/all だけラベルを定義すると、既存PDFが誤って
  どちらかの種別に見えたり不正な名前になる。**null は従来どおり "registry.pdf"**
  (種別不明の固定ラベル)にする。移行前の添付を UI・ダウンロードヘッダ両方の
  テストで覆う。※PR-A で実装済(registryDisplayName(null)="registry.pdf")。
- ⚠**選んだ種別を、台帳の鍵と provider リクエストの両方へ実際に通す**
  (@codex 設計指摘)。台帳の鍵は種別込みだが、今の呼び出し元は鍵の生成も
  provider への請求も **certificateType: "owner" を直書き**している。ここを
  選択値で差し替えないと、全部事項の購入が**所有者事項の鍵で記録**され、
  (a)正当な所有者事項の購入が30日ガードで弾かれる (b)どちらの謄本を持って
  いるかの記録がずれる。PR-A のスコープにこの配線を明記する
- 台帳の鍵の**形**は既に種別込み=スキーマ変更は不要(通し方だけの問題)

## 第2部: 複数物件の一括取得

### 全体像

```
物件一覧で複数選択(チェックボックス)
  → 「謄本を一括取得」ボタン(registry:auto_fetch 保持者のみ表示)
  → 確認画面: 対象N件の内訳 + 種類(2択) + ⚠課金の明示
  → ジョブ作成(DB) → 進捗画面(何件目/成功/失敗/スキップ)
  → 1件ずつ順に処理(スロットルの実値の間隔・同時1セッション遵守)
  → 完了: 取得したPDFは各物件に添付(単発取得と同じ置き場)
```

### 処理方式: **画面からの分割実行**(登記PDF一括取込と同型)

- 進捗画面が「次の1件を処理」APIを順に呼ぶ。**タブを閉じると止まる**が、
  ジョブはDBに残るので**開き直せば続きから再開**できる
- ⚠**処理APIはDB側で項目を原子的に掴んでから外部に触る**(@codex 設計指摘)。
  進捗画面が2つのタブで開かれたり、送信の再試行が起きると、同じ項目を
  **二重に処理=二重に課金**し得る。画面の行儀に頼らず、
  updateMany(where: { id, status: "pending" }) の**0行=他が処理中**で弾く
  (登記PDF一括取込が単一処理でも同じ守りを敷いている前例に合わせる)。
  件数集計・paused への遷移も同じCASで直列化する
- ⚠**項目の掴みに加えて、ジョブ単位でも「同時に1件だけ」を強制する**
  (@codex 設計指摘 P1)。項目単位のCASだけだと、2つのタブが**別々の項目**を
  同時に掴んで並走できる。並走すると (1)「1件ずつ直列」の前提が崩れ、
  (2)1件目が charged_but_failed でジョブを paused にした**後に**、既に掴んで
  順番待ちしていた2件目が**課金境界を越えられる**。処理APIは
  「そのジョブに processing の項目が1件でもあれば409」で弾く。
  ⚠**この確認と項目の掴みは1つの原子操作にする**(@codex 設計指摘 P1)。
  「確認→掴む」を別々に行うと、2つのリクエストが**どちらも「処理中なし」を
  見てから別々の行を掴める**(確認の時点では本当に誰も居ない)。ジョブ行に
  **実行中項目(active_item_id)を CAS で書く**(where active_item_id IS NULL)
  ことを掴みの本体とし、項目の processing 化は同じ transaction 内で行う。
  終了/後回しの解放も同じ CAS で active_item_id を消す。さらに
  **課金境界の直前(onBeforeCharge の中)でジョブが paused/cancelled になって
  いないかを再確認**してから請求を押す(なっていれば押さずに pending へ戻す)
- ⚠**サーバー常駐の自動実行(systemd timer)にはしない**。お金が動く処理を
  無人で回すのは、実課金の通しテストすら未実施の現段階では踏み込みすぎ。
  将来必要になったら別途設計する(前例: 添付お掃除・巡回の見回り)
- ⚠**「処理中のまま放置」の扱いは取込の流用では危険**(@codex 設計指摘 P1)。
  タブが閉じた/プロセスが再起動した項目は、**請求を押した後・記録する前**で
  止まっている可能性がある。取込と同じ「失敗にして再実行」をすると、
  **記録なき課金**の上に**再購入の二重課金**が乗る。
  - 項目に**課金段階の印**を持つ(請求を押す**前に**DBへ「課金試行中」を書き、
    押した後に「課金済み」へ進める。書けなければ押さない)
  - ⚠**印を書く場所は provider の中の課金境界**(@codex 設計指摘)。今の provider は
    課金境界を呼び出し側に見せていない(内部の chargeState を請求クリック直前に
    切り替えるだけ)。呼び出し前に attempting を書くと**課金前の普通の失敗まで
    課金不明**になり、呼び出し後に書くのでは**クリック直後の死**を取りこぼす。
    provider に **onBeforeCharge / onCharged のフック**を追加し(await される・
    onBeforeCharge の失敗=DBに書けなければ**請求を押さない**)、一括はここで
    DBの印を進める。単発の将来の台帳強化にも同じフックが使える。
    ⚠**フックの await の後に、中断印(chargeState.aborted)をもう一度確認してから
    押す**(@codex 設計指摘 P1)。今のクリック経路は「中断確認→請求」の間に
    await を置かないことで「呼び出し側は timeout として終わったのに課金だけ
    起きる」を防いでいる(既存の設計判断)。awaited なフックをそこに挟むと
    **この守りが破れる**(フックを待っている間に provider が課金前 timeout で
    中断を立て、呼び出しは未課金 timeout として終わっているのに、続きが請求を
    押す=記録なき課金)。フック直後・クリック直前の再確認と、
    「フック中に timeout」の回帰テストを実装の必須条件にする。
    ⚠**フック待ちの間に中断され、クリックを回避できた項目は not_charged で
    決着させる**(@codex 設計指摘 P2)。timeout が呼び出し側へ戻った後に
    onBeforeCharge が attempting を書き、直後の再確認でクリックを回避した項目は
    **確実に未課金**だが、呼び出し側は既に終わっているため誰も決着を書かない=
    二重課金ガードに永遠に残る。onChargeAborted/finally で **not_charged を
    自動記録**し(運用者の手作業を待たない)、上の回帰テストでこの永続状態まで
    検証する。⚠**このとき共通台帳(registry_charge_attempts)の対応行も同じ tx で
    not_charged に解決する**(@codex 設計指摘 P1)。onBeforeCharge が既に共通台帳へ
    未解決行を作っているため、項目側にだけ書くと台帳の行が生きたガード・
    起動時ゲートに残り続ける。**単発は項目すら無い**ので、共通台帳を解決しないと
    再起動後に以後の全課金が止まる。bulk/single 両方でこの解決を行う。
    ⚠**中断の最終化は外側の後片付けより後でも書けるようにする**(@codex 設計指摘)。
    外側リクエストが timeout で通常の終端後片付け(トークン/ロックのクリア)を
    済ませてから遅延フックが settle すると、**所有トークン照合が既に外れていて
    not_charged を書けない**。onBeforeCharge が同レースで attempting を書いていると
    項目が二重課金ガードに残り続ける。対策: adapter が決着するまで**掴みを離さない**
    (リースは心拍で延長)か、実行ごとの**不変の tombstone(実行トークンの記録)**を
    持たせ、中断の最終化はそれに対して CAS する(新しい実行には触らず、自分の
    実行の項目だけ not_charged にできる)。
    ⚠**遅れて走るフックは実行トークンで囲う**(@codex 設計指摘 P1)。timeout で
    呼び出し側が戻った後、リース切れで**別の実行が同じ項目を掴み直している**
    かもしれない。古い実行の onBeforeCharge(attempting)や onChargeAborted
    (not_charged)が、新しい実行の上に書き込むと、**本物の課金の保護を消す**
    (not_charged はガードから外す)。実行ごとに1回きりのトークンを持ち、遅延
    フックと後片付けの CAS は**項目・active_item_id・物件ロックが自分のトークン
    のままか**を条件にする(ずれていれば何も書かない)
  - 放置/運用者による解決の際は、**自分の lock_owner_token と一致する場合に
    限り**物件ロックを元の状態へ戻す(一致しない=別の処理が新しく掛けた鍵なので
    触らない)。
    ⚠**照合の相手は物件側に持たせる**(@codex 設計指摘)。項目側だけに token を
    置いても、ロックの実体(Property.registryStatus)に**どの鍵で施錠されたか**が
    残らないため比較のしようがない=古い項目の復旧が、**後から掛かった別の
    有料取得のロックを上書きして剥がし得る**。properties に
    registry_lock_token(nullable・additive)を追加し、施錠CASで設定・解錠で
    クリア、復旧の書き戻しは **where registry_lock_token = 自分の token** で
    行う(0行=他人の鍵なので触らない)。
    ⚠**registryStatus を書き換える全ての経路を token 対応にする**
    (@codex 設計指摘 P1)。一括だけが token を使っても、**単発の取得の施錠/解錠・
    物件の一括更新・物件アクションの状態変更**は status しか見ずに上書きできる。
    token 付きのロックが第三者に上書きされた後に単発が施錠すると、古い復旧が
    「自分の token に一致」を根拠に**より新しい単発のロックを剥がす**。
    - 単発の取得も施錠時に token を発行し、解錠は token-CAS にする(同じ規約に統一)
    - 手動系(一括更新/アクション)は **registry_lock_token が立っている間は
      registryStatus の変更を409で拒否**する(取得の進行中に手で状態を触らせない)
    - ⚠**registryStatus だけでなく、指紋フィールド(address/lotNumber/
      buildingNumber/realEstateNumber)を書く全 writer も token 中は拒否/token-CAS**
      にする(@codex 設計指摘 P1)。指紋照合/物件CASの後・有料フロー完了前に
      これらが編集されると、取得は**古いスナップショットで購入**した上で、
      PDFと解析所有者を**今や別物になった物件レコード**に添付してしまう。
      既存の PATCH /properties/[id] はこれらを scheduled 無視で受けるので要改修
    - 実装は「registryStatus を書く箇所を grep で全列挙→全てに適用」を必須とする
      ([[fix-all-call-sites-not-one]] と同じ走査型)
  - 放置項目のうち課金段階が「試行中」以降のものは**課金不明**として扱い、
    ジョブごと paused にする。**自動では再実行しない**(運用者がマイページを
    確認して手で決める)。課金前で止まった項目だけ従来どおり失敗扱いにできる

### 1件ごとの処理規則

⚠**取得経路は所在+地番に統一する**(@codex 設計指摘)。**不動産番号での有料取得は
まだ配線されていない**(実サイトの請求フロー判明時に fail-closed のまま止めてある。
searchByRealEstateNumber はカートに触れる前に provider_error で停止する)。
「番号があれば番号で」と書くと、番号持ちの物件が**全件失敗**する。
番号経路の有料配線は別設計(要live校正)とし、第1弾のスコープに含めない。

1. **住所+(地番または家屋番号)が揃っていれば所在検索**を実行し、候補と物件登録の
   対応する値を突き合わせる(@codex 設計指摘: 単発の取得は家屋番号のみの建物にも
   対応済み。「地番が無ければスキップ」と書くと**建物物件が一括で退行**する):
   - **家屋番号があれば建物として家屋番号で照合**(単発の取得と同じ判定=
     家屋番号の有無が土地/建物の分岐)。地番との照合は**家屋番号が無い土地だけ**。
     ⚠逆(地番優先)にすると、地番も登録済みの建物が土地として検索され、
     単発では取れる建物が一括で取れない/別物に一致する(@codex 設計指摘)
   - **完全一致がちょうど1件** → その候補で取得
   - ⚠**候補一覧が完全に読めたときだけ判定する**(@codex 設計指摘)。今の provider は
     ページ上限(MAX_DIALOG_PAGES)超過やページ送りの timeout で**部分的な候補**を
     黙って返す(呼び出し側に「途中まで」の印が無い)。部分結果の中の
     「ちょうど1件」は、**読んでいないページに別の一致**が居るかもしれない。
     provider に**完全性の印(truncated)**を追加し、不完全なら skipped(要手動)。
     「あいまいなまま買わない」の保証は完全な一覧の上でしか成立しない
   - 0件 / 複数 / 不一致 → **skipped(要手動)にして課金しない**。
     ⚠一括処理での「たぶんこれ」は禁止。単発画面なら人が候補を見て選べるが、
     一括では見ていないので、**機械が確信できる場合しか買わない**
2. **住所も地番/家屋番号も不足する物件(番号しか無い等)は skipped(要手動)**。理由コードを
   分けて進捗画面に「番号での取得は今後対応」と表示する
3. 失敗の隔離は**課金の前後で変える**(@codex 設計指摘 P1):
   - **課金前**の失敗は**局所か口座全体かで分ける**(@codex 設計指摘)。
     - **局所**(その物件固有: 候補0件/複数・所在不足・指紋不一致)は残りを
       止めない(項目ごとに記録して続行)
     - **口座全体**(資格情報の失効=auth_failed・利用時間外=service_hours・
       接続不可)は**続けても全件が同じ理由で失敗**し、throttle とログイン試行を
       無駄に消費して全項目を終端にしてしまう。ジョブを **paused**(時間外は
       retry-later)にし、運用者が資格情報を直す/時間内に再開する。
       ジョブを作り直させない。⚠**このとき掴んでいた項目と物件ロックも
       一緒に解放する**(@codex 設計指摘)。項目を processing のまま
       active_item_id を握ったまま止めると、再開しても「処理中あり」ガードに
       永久に弾かれる。逆に項目を終端にすると**資格情報の復旧後に取れる購入を
       恒久的に飛ばす**。原子的な paused 遷移で、項目→pending・active_item_id
       クリア・自分の物件ロック解放を1つの transaction で行う
   - ⚠**charged_but_failed が1件でも出たら、口座全体の課金を止める**
     (@codex 設計指摘 P1: ジョブ単位の paused だけでは足りない)。原因
     (ダウンロードのセレクタずれ・保存失敗・アカウント状態)は**ジョブを
     またいで共有**なので、別のジョブや**単発の取得**が購入待ち行列の後ろで
     待っていると、同じ障害のまま次の課金に踏み込む。DB(registry_fetch_config)に
     **課金停止フラグ**(理由・時刻つき)を持ち、charged_but_failed の記録と同時に
     立てる。一括の処理APIも**単発の取得も**、課金境界の直前(onBeforeCharge)で
     このフラグを確認し、立っていれば請求を押さない。解除は運用者がマイページを
     確認してから(管理画面で明示操作・監査に記録)。
     ⚠**ブレーカーは purchase mutex を握ったまま立てる**(@codex 設計指摘 P1)。
     今の provider は fetchByLocation が reject した瞬間に runExclusivePurchase を
     解放する。呼び出し側が charged_but_failed を記録する前に mutex が空くと、
     **待ち行列の次の請求が onBeforeCharge に入り、まだ立っていないブレーカーを
     見て同じ障害のまま課金**する。失敗フック(onChargeFailed 等)を mutex の
     中で走らせてブレーカーを永続化するか、**永続化が終わるまで mutex を
     離さない**。単発の失敗経路も同じフックを通す。
     ⚠**ダウンロード成功後の永続化も mutex の中に含める**(@codex 設計指摘 P1)。
     provider は PDF を返した時点で mutex を解放するが、**その後**に台帳記録・
     PDF検証・保存(processRegistryPdf)が走る。ここで落ちると charged_but_failed
     だが、既に mutex が空いて次の請求が課金し得る。呼び出し側の**最終化
     コールバックを mutex の中で実行**する(または保存完了まで mutex を握る)=
     課金境界からブレーカー確定までを1つの排他区間にする。
     ⚠**ブレーカーの永続化自体が失敗したときは fail-closed にする**
     (@codex 設計指摘 P1)。課金後失敗と**同時にDB書き込みも失敗**すると
     ブレーカーを永続化できず、mutex 内で走らせても意味が無い(purchase
     キューは fulfill でも reject でも先へ進むため、DB復旧後に次の請求が
     「ブレーカーは立っていない」と見て課金する)。永続化に失敗した場合は
     **プロセス内のフェイルクローズ・ラッチ**を立てて即座に課金を止める。
     ⚠**ただしプロセス内ラッチだけに頼らない**(@codex 設計指摘 P1)。単一
     プロセスの systemd 運用では、**再起動でラッチが消える**一方 DB フラグは
     未設定のままなので、DB 復旧後に誰の復旧も無く課金境界を越えてしまう。
     永続化に失敗したら、(a)DB への停止フラグ書き込みを**成功するまで**
     リトライし続ける、それも不能なら (b)**起動時ゲート**で担保する。
     ゲートの正確な条件(@codex 設計指摘 P1×2):
     - **一括と単発を共通の課金試行台帳(charge-attempt ledger)に記録する**。
       起動時ゲートが job_items しか見ないと、**単発の課金**(ジョブ項目を
       作らず、台帳は provider 応答後に書く)が境界を越えて書き込み失敗した
       場合を見逃す。課金境界の直前に**種別を問わず1本の台帳へ試行を記録**し、
       ゲートはそこを見る。
     - **成功した課金でゲートを塞がない**。成功時も charge_phase=charged を通る
       ので「attempting/charged が残る間ブロック」を素直に書くと、**成功購入の
       後の初回再起動で以後の課金が全部止まる**。ゲートは試行を **resolved に
       できたものだけ**未解決から外す。
       ⚠**resolved は添付の最終化まで終えてから書く**(@codex 設計指摘 P1)。
       購入台帳(AuditLog)は provider 応答直後・**PDF検証/保存(processRegistryPdf)
       より前**に書かれるため、「台帳がある=成功」ではない。保存が失敗し
       ブレーカーの書き込みも失敗した課金済み行を、台帳の存在だけで resolved と
       みなすと、再起動後にゲートを素通りして再課金できる。**台帳の存在は
       あくまで二重購入マーカー**として残し、起動時ゲートを外す resolved は
       **添付/状態の最終化が commit された後**にのみ立てる。
     - ⚠**成功した項目も添付確定後に charge_resolution=charged で決着させる**
       (@codex 設計指摘 P1)。ブレーカー解除の関所は**未解決の job_items**も
       見る。成功項目が charged/unresolved のまま残ると、後で無関係な課金失敗が
       ブレーカーを立てたとき、**過去の成功がこの関所に永久に一致して運用者が
       解除できない**。成功の最終化 tx(添付/状態を確定するのと同じ tx)で、
       job item も **charge_resolution=charged(=決着済み)** にし、未解決の関所
       から外す。ゲート/関所が「未解決」とみなすのは**恒久的な成功証跡
       (charge_resolution!=charged)が無い課金試行だけ**にそろえる。
     - ⚠**項目の status は問わない**: onCharged 後に charged_but_failed+
       ブレーカーの tx が落ちると行は processing のまま・ブレーカー未設定で残る。
       「終端行だけ」を見るゲートはこれを見逃す。
     復旧が終わるまで購入要求を受け付けない。プロセス内ラッチは
     即時停止の速報でしかなく、**恒久的な砦は必ずDB側**に置く。
     以後の課金は**運用者が明示に復旧するまで一律拒否**する(キューを進めない)。
     ⚠**ブレーカー解除と課金決着(charge_resolution の記録)のAPIは
     registry:manage を要求する**(@codex 設計指摘 P1)。通常の
     registry:auto_fetch のままだと、購入を任された一般スタッフが
     口座全体の停止を自分で解除したり、未解決の課金試行を勝手に not_charged と
     記録して**運用者の確認を飛ばして再課金を許して**しまう。これらの状態変更は
     必ず管理権限の壁の内側に置く。
     ⚠**ブレーカー解除は「未解決の課金試行が1つも無いこと」を原子的に確認して
     から行う**(@codex 設計指摘 P1)。フラグだけ先に解除すると、
     onBeforeCharge は「停止解除」を見て、あとは purchase_key_hash 単位のガード
     しか効かないため、**まだ決着していない口座全体の課金失敗が残っていても、
     別の物件の請求は通ってしまう**。解除 tx の中で「charge_phase が
     attempting/charged の未解決行(共通台帳・job_items 両方)がゼロ」を条件にし、
     残っていれば解除を弾く(または同じ tx で決着させる)。フラグ先行解除で
     fail-closed を迂回させない。
     この書き込み失敗経路も回帰テストで覆う
   - **charged_but_failed が1件でも出たら、ジョブ全体を paused にする**。
     課金境界を越えた失敗の原因(ダウンロードのセレクタずれ・保存失敗・
     アカウント状態)は**次の項目でも再発する**可能性が高く、続行すると
     「払ったのに添付されない」購入を量産する。運用者がマイページを確認して
     から再開する(再開ボタン+確認済みチェック)。該当項目は再実行禁止を明示
4. 台帳は従来どおり項目ごとに照合(30日以内の同一 物件×地番×種別 は再購入させない
   =**一括に同じ物件を2回入れても二重課金しない**)
   - ⚠**未解決の課金試行はすべて二重課金ガードに含める**(@codex 設計指摘 P1)。台帳
     (AuditLog)への記録は**PDFを受け取った後**なので、請求を押してから台帳を書く
     までの間に落ちた項目は**台帳に行が無い**。しかもその項目の課金段階は
     attempting とは限らない(押した後に onCharged で charged へ進んでから落ちる)。
     ガードは「台帳 OR **charge_phase が attempting/charged に達した項目
     (終端かどうかを問わない) OR registry_charge_attempts の未解決行**」で判定する
     (⚠**通常の二重課金ガードでも共通台帳を見る**=@codex 設計指摘 P1: 単発は
     ジョブ項目を持たず registry_charge_attempts にしか残らない。この生きた
     ガードが job_items と AuditLog しか見ないと、**ブレーカー解除後・再起動を
     待たず**に、同じ purchase_key_hash の次の請求が素通りして再課金できる。
     起動時ゲートだけでなく**毎回の課金判定でも共通台帳の未解決行を含める**)。
     ⚠**「非終端のみ」に絞らない**(@codex 設計指摘 P1)
     =**台帳を書く前に charged_but_failed で終端に達した行**が関所から
     消える=ダウンロード失敗や台帳書き込み自体の失敗で台帳が無いまま、30日
     ガードを素通りして同じ謄本を再購入できる)。関所から外れるのは、
     (a)台帳に対応する行が書けたとき、または(b)運用者が **charge_resolution=
     not_charged**(マイページで未課金を確認)と記録したとき、のみ(@codex 設計
     指摘: 「未課金と確認」と「課金済みだが未解決」を**永続的に区別できる列が
     要る**。status/error_code に相乗りさせると実際に課金済みの謄本を再購入する)。
     charged と判明した場合は台帳へ手動記録してから外す。charge_unknown だけを
     列挙すると charged のまま落ちた行が漏れる。⚠照合は**項目に保存した purchase_key_hash**
     と行う(いまの物件から再計算しない=編集で鍵がずれても古い試行を見失わない)
   - ⚠**台帳の照合だけでは同時実行に勝てない**(@codex 設計指摘 P1)。台帳への
     記録は購入後なので、**同じ物件を含む2つのジョブ**(または一括と単発の同時
     実行)が、どちらも「まだ台帳に無い」を見てから両方買う隙間がある。
     単発の取得が外部に触れる前に掴む**物件行のロック**(registryStatus/version の
     CAS)を、一括の処理APIも**同じ物件に対して**必ず通す。掴めなければその項目は
     後回し(rate_limited と同じ「後で再試行」扱い・失敗にしない)
5. **間隔は既存スロットルの実値に従う**(@codex 設計指摘)。コード既定は60秒
   (REGISTRY_FETCH_MIN_INTERVAL_MS で短縮可・本番は30秒設定)。
   ⚠スロットルは「待つ」のではなく**早すぎる呼び出しを rate_limited で弾く**。
   一括側が独自の秒数を決め打ちすると、既定環境では**外部に触る前に全件失敗**する。
   処理APIは rate_limited を**失敗にせず**「次はN秒後」と返し、画面側が
   その値だけ待って再呼び出しする(env値を二重に持たない)。
   ⚠**後回しにするときは、掴んだ項目を必ず pending に戻す**(@codex 設計指摘)。
   項目が processing のまま残ると、**N秒後の再呼び出しには掴める行が無い**=
   ジョブが固まるか、放置復旧が課金前の後回しを終端の失敗に変換してしまう。
   ⚠**順序は「throttle の peek → 項目を掴む → 物件ロックを取る」**
   (@codex 設計指摘 P1)。物件ロックの実体は registryStatus の**書き換えを伴う
   CAS**で、消費しない確認が存在しない。「確認してから掴む」をロックに適用
   すると、(a)覗くだけ=確認と取得の間に単発の取得が割り込み**両方が課金に
   届く** (b)先に取る=項目の掴みに失敗したとき**物件が scheduled のまま取り残さ
   れる**、のどちらかになる。安価な内部の掴み(項目CAS)を先に、実体のある予約
   (物件CAS)を後に取り、後回しにする経路では**両方を一緒に**解放する
   (項目→pending・物件→元の状態)。物件CASが取れなければ項目を戻して後回し。
   ⚠**事前確認は「消費しない覗き見(peek)」で行う**(@codex 設計指摘)。今の
   tryAcquire は**確認と同時に権利を消費**し、provider も内部でもう一度
   tryAcquire を呼ぶ。事前確認に tryAcquire を使うと**唯一の権利を事前確認が
   食い潰し**、直後の provider 呼び出しが必ず rate_limited になる=正しく
   待っているのに全件が後回しされ続ける。throttle に非消費の peek
   (nextAvailableAt を返すだけ)を追加し、実際の取得は従来どおり provider が
   自分で行う。peek 通過後の競合で provider が rate_limited を返した場合は、
   上記の「掴んだ項目を pending へ戻す」経路で処理する。
   ⚠**消費する取得(tryAcquire)は排他区間(runExclusivePurchase)の中・外部アクセスの
   直前に移す**(@codex 設計指摘 P2)。今の provider は runExclusivePurchase に入る
   **前**に tryAcquire する。長い検索/取得が mutex を握っている間に、待ち行列の
   各リクエストが**先に権利だけ消費**して並び、保持者が終わると**再確認なしで
   立て続けにアクセス**し、最小間隔(既定60秒)より詰まる恐れがある。事前は
   非消費の peek のまま、権利の消費は mutex の中に入れる。
   ⚠**「N秒後」を返すには throttle 側の拡張が要る**(@codex 設計指摘)。今の契約は
   tryAcquire の真偽だけで、rate_limited エラーも残り時間を持たない。
   throttle に nextAvailableAt(または retryAfterMs)を追加し、エラーに載せて
   API 応答まで届ける。これをせず画面が独自に env を読むと二重管理になり、
   既定60秒の環境で早すぎるポーリングを繰り返す。1件ずつ直列(同時1セッション制約)
6. **作成時の物件指紋を項目に保存し、課金前に照合する**(@codex 設計指摘)。
   ジョブ作成から処理まで時間が空く(スロットル間隔×件数)ため、その間に住所や地番が
   編集されると、**確認した時とは別の土地を買う**ことになる。単発の取得が
   既に持つ指紋照合(fingerprintProperty)と同じ守りを一括にも敷く
   (⚠保存するのは**ハッシュのみ**。上記スキーマ欄参照)。
   不一致 → skipped(物件情報が変わった・要手動)。課金しない

### 安全弁

- 1ジョブの上限 **50件**(超過は分割を案内)
- 実行前の確認画面に **件数×種類** を明示し、「N件ぶんの利用料金が発生します」
  の確認チェックを必須にする(単発の confirmed と同じ思想)
- ジョブの**中止ボタン**: 処理中の1件が終わり次第停止(課金済みの件はそのまま・
  実況の中止と同じ「節目で止まる」原則)
- ジョブ作成/処理の門は**単発の購入と同じ readiness 判定**に載せる
  (@codex 設計指摘): 課金スイッチ **AND 所在検索の校正済みフラグ**
  (既存の purchase capability と同一)。スイッチだけで判定すると、校正が
  済んでいない環境で**未校正の有料自動操作**が走る。どちらか欠けたら501
- 権限は **registry:auto_fetch AND property:read** を要求し、さらに**項目ごとに
  canAccessPropertyRecord で物件の可視性を検証**する(@codex 設計指摘)。
  単発の取得APIと同じ三重の門。ジョブ作成時に見えない物件が混ざっていれば
  その項目を作らない(403で全体を落とすのではなく、作成時に除外して件数を明示)。
  処理APIも項目ごとに再検証する(作成後に権限や物件が変わり得るため)。
  ⚠**進捗/詳細の応答も、毎回 項目ごとに canAccessPropertyRecord で再検証・
  フィルタする**(@codex 設計指摘 P1)。作成者本人チェックだけでは足りない=
  field_staff が担当物件でジョブを作った後に**その物件が別担当へ付け替え**られると、
  作成者チェックは通るのに canAccessPropertyRecord なら拒否される状態になる。
  進捗画面はジョブの対象や項目ごとの結果(=物件を指す情報)を返すので、
  アクセスが外れた物件は**進捗の各応答からも外す**(または当該項目を伏せる)。
  ジョブ作成後の担当替えを回帰テストで覆う。
- **ジョブの操作(進捗閲覧/次を処理/中止/再開)は作成者本人に限定**する
  (@codex 設計指摘)。URLを知った別のスタッフが、**他人が確認した課金ジョブ**を
  進めたり止めたりできてはいけない(取込ジョブの executedBy ガードと同型)。
  - ⚠**代行に使う権限は registry:manage を新設する**(@codex 設計指摘: 今の
    カタログに registry は auto_fetch しか無く、「明示の管理権限」の実体が
    無い。auto_fetch を流用すると**一括を使える全員が他人の課金ジョブを
    操作できてしまう**)。seed で管理者テンプレートに付与し、権限管理画面にも
    表示する(import:manage と同じ owner-vs-operator 型の前例)。migration は
    「テーブルのみ」ではなく権限行の追加も含む(どちらも additive)。
  - ⚠**管理者の代行だけは許す**(@codex 設計指摘)。課金不明で止まったジョブは
    マイページ確認が要るが、作成者が不在だと**誰も再開も中止もできず永久に
    塞がる**。明示の管理権限を持つ者に限り **進捗閲覧/次を処理/中止/再開の
    すべて**を許可する(@codex 設計指摘: 中止/再開だけだと、再開はできても
    **画面駆動の「次を処理」が作成者限定のままで結局進められない**)。
    監査に「誰が代行したか」を残す。一般スタッフは従来どおり自分のジョブのみ。
  監査はジョブ作成/完了/中止+項目ごと
